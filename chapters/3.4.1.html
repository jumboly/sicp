3.4.1  
The Nature of Time in Concurrent Systems
並行システムにおける時間の本質

On the surface, time seems straightforward. It is an ordering imposed on events.
表面的には、時間は単純に見えます。時間とは、イベントに課される順序のことです。
[1]
For any events $A$ and $B$, either $A$ occurs before $B$, $A$ and $B$ are simultaneous, or $A$ occurs after $B$. For instance, returning to the bank account example, suppose that Peter withdraws $10 and Paul withdraws $25 from a joint account that initially contains $100, leaving $65 in the account. Depending on the order of the two withdrawals, the sequence of balances in the account is either $\$100 \rightarrow \$90 \rightarrow\$65$ or $\$100 \rightarrow \$75 \rightarrow\$65$. In a computer implementation of the banking system, this changing sequence of balances could be modeled by successive assignments to a variable balance.
任意のイベント$A$と$B$について、$A$が$B$より前に起こるか、$A$ と$B$が同時であるか、あるいは$A$が$B$より後に起こるかのいずれかです。たとえば、銀行口座の例に戻って、PeterとPaulが初期残高$100の 共同口座からそれぞれ$10と$25を引き出し、口座に$65が残る場合を考えてみましょう。2回の引き出しの順序によって、口座の残高のシーケンスは$\$100 \rightarrow \$90 \rightarrow\$65$か$\$100 \rightarrow \$75 \rightarrow\$65$のどちらかになります。銀行システムをコンピュータで実装する場合、このように変化する残高のシーケンスは、変数balanceへの連続した代入としてモデル化できるでしょう。

In complex situations, however, such a view can be problematic. Suppose that Peter and Paul, and other people besides, are accessing the same bank account through a network of banking machines distributed all over the world. The actual sequence of balances in the account will depend critically on the detailed timing of the accesses and the details of the communication among the machines.
しかし複雑な状況では、このような見方は問題になることがあります。PeterとPaul、さらに他の人々も、世界中に分散配置された銀行端末のネットワークを介して同じ銀行口座にアクセスしていると考えてみてください。口座の残高の実際のシーケンスは、アクセスの詳細なタイミングやマシン間の通信の詳細に決定的に依存することになります。

This indeterminacy in the order of events can pose serious problems in the design of concurrent systems. For instance, suppose that the withdrawals made by Peter and Paul are implemented as two separate threads sharing a common variable balance, each thread specified by the function given in section 3.1.1:
この イベントの順序における不確定性は、並行システムの設計において深刻な問題を引き起こすことがあります。たとえば、PeterとPaulが行う引き出しが、共通の変数balanceを共有する2つの別々のスレッドとして実装されているとします。各スレッドは、3.1.1節で与えられた次の関数によって指定されます： 
function withdraw(amount) {
    if (balance >= amount) {
        balance = balance - amount;
        return balance;
    } else {
        return "Insufficient funds";
    }
}
If the two threads operate independently, then Peter might test the balance and attempt to withdraw a legitimate amount. However, Paul might withdraw some funds in between the time that Peter checks the balance and the time Peter completes the withdrawal, thus invalidating Peter's test.
2つのスレッドが独立して動作すると、Peterは残高をチェックして適正な金額を引き出そうとするかもしれません。 しかし、Peterが残高を確認してから引き出しを完了するまでの間に、Paulが一部の資金を引き出すかもしれません。これによりPeterのチェックは無効になってしまいます。

Things can be worse still. Consider the statement
事態はさらに悪くなる可能性があります。次の文を考えてみましょう： 
balance = balance - amount;
executed as part of each withdrawal process. This consists of three steps: (1) accessing the value of the balance variable; (2) computing the new balance; (3) setting balance to this new value. If Peter and Paul's withdrawals execute this statement concurrently, then the two withdrawals might interleave the order in which they access balance and set it to the new value.
これは各引き出しプロセスの一部として実行され、次の3つのステップから構成されます：(1) balance変数の値にアクセスする、(2) 新しい残高を計算する、(3) balanceをこの新しい値に設定する。PeterとPaulの引き出しがこの文を並行に実行すると、2つの引き出しがbalanceにアクセスして新しい値を設定する順序がインターリーブされる可能性があります。

The timing diagram in figure 3.53 depicts an order of events where balance starts at 100, Peter withdraws 10, Paul withdraws 25, and yet the final value of balance is 75. As shown in the diagram, the reason for this anomaly is that Paul's assignment of 75 to balance is made under the assumption that the value of balance to be decremented is 100. That assumption, however, became invalid when Peter changed balance to 90. This is a catastrophic failure for the banking system, because the total amount of money in the system is not conserved. Before the transactions, the total amount of money was $100. Afterwards, Peter has $10, Paul has $25, and the bank has $75.
図 3.53のタイミング図は、balanceが100から始まり、Peterが10を引き出し、Paulが25を引き出したにもかかわらず、balanceの最終値が75になるイベントの順序を描いています。図に示されているように、この異常の原因は、Paulがbalanceに75を代入するのが、減算対象のbalanceの値が100であるという前提の下で行われている点にあります。しかし、その前提はPeterがbalanceを90に変更した時点で無効になっていました。これは銀行システムにとって破滅的な故障です。なぜなら、システム内のお金の総額が保存されていないからです。取引の前の総額は$100でした。取引の後、Peterは$10、Paulは$25、銀行は$75を持っています。
[2]

The general phenomenon illustrated here is that several threads may share a common state variable. What makes this complicated is that more than one thread may be trying to manipulate the shared state at the same time. For the bank account example, during each transaction, each customer should be able to act as if the other customers did not exist. When customers change the balance in a way that depends on the balance, they must be able to assume that, just before the moment of change, the balance is still what they thought it was.
ここで示されている一般的な現象は、複数のスレッドが共通の 状態変数を共有する可能性があるということです。これを複雑にしているのは、複数のスレッドが同時に共有状態を操作しようとするかもしれないという点です。銀行口座の例では、各取引の間、各顧客は他の顧客が存在しないかのように振る舞えるべきです。顧客たちが残高に依存する形で残高を変更するとき、彼らは、変更の直前の瞬間にも残高が自分の認識通りであると仮定できなければなりません。

Correct behavior of concurrent programs
並行プログラムの正しい動作

The above example typifies the subtle bugs that can creep into concurrent programs. The root of this complexity lies in the assignments to variables that are shared among the different threads. We already know that we must be careful in writing programs that use assignment, because the results of a computation depend on the order in which the assignments occur.
上記の例は、並行プログラムに忍び込む微妙なバグを典型的に示しています。この複雑さの根本原因は、異なるスレッド間で共有される変数への代入にあります。代入を使うプログラムを書く際には注意が必要であることはすでに分かっています。なぜなら、計算結果は代入が行われる順序に依存するからです。
[3]
With concurrent threads we must be especially careful about assignments, because we may not be able to control the order of the assignments made by the different threads. If several such changes might be made concurrently (as with two depositors accessing a joint account) we need some way to ensure that our system behaves correctly. For example, in the case of withdrawals from a joint bank account, we must ensure that money is conserved. To make concurrent programs behave correctly, we may have to place some restrictions on concurrent execution.
並行スレッドでは、代入に特に注意する必要があります。なぜなら、異なるスレッドが行う代入の順序を制御できない場合があるからです。このような変更が（共同口座にアクセスする2人の預金者のように）並行して行われる可能性がある場合、システムが正しく動作することを保証する何らかの方法が必要です。たとえば、共同銀行口座からの引き出しの場合、お金が保存されることを保証しなければなりません。並行プログラムを正しく動作させるために、並行実行にいくつかの制約を課す必要があるかもしれません。

One possible restriction on concurrency would stipulate that no two operations that change any shared state variables can occur at the same time. This is an extremely stringent requirement. For distributed banking, it would require the system designer to ensure that only one transaction could proceed at a time. This would be both inefficient and overly conservative. Figure 3.54 shows Peter and Paul sharing a bank account, where Paul has a private account as well. The diagram illustrates two withdrawals from the shared account (one by Peter and one by Paul) and a deposit to Paul's private account.
並行性に対する1つの可能な制約は、共有状態変数を変更するどの2つの操作も同時に発生できないと規定することでしょう。これは極めて厳しい要件です。分散型銀行業務の場合、この要件ではシステム設計者は一度に1つの取引しか進行できないようにしなければなりません。これは非効率的であると同時に、過度に保守的です。図 3.54は、PeterとPaulが銀行口座を共有しており、さらにPaulが個人口座も持っている状況を示しています。この図は、共有口座からの2回の引き出し（Peterによる1回とPaulによる1回）と、Paulの個人口座への1回の預け入れを描いています。
[4]
The two withdrawals from the shared account must not be concurrent (since both access and update the same account), and Paul's deposit and withdrawal must not be concurrent (since both access and update the amount in Paul's wallet). But there should be no problem permitting Paul's deposit to his private account to proceed concurrently with Peter's withdrawal from the shared account.
共有口座からの2回の引き出しは並行であってはなりません（どちらも同じ口座にアクセスして更新するため）。またPaulの預け入れと引き出しも並行であってはなりません（どちらもPaulの財布の金額にアクセスして更新するため）。しかし、Paulの個人口座への預け入れを、Peterの共有口座からの引き出しと並行して進めることを許容しても問題はないはずです。

A less stringent restriction on concurrency would ensure that a concurrent system produces the same result as if the threads had run sequentially in some order. There are two important aspects to this requirement. First, it does not require the threads to actually run sequentially, but only to produce results that are the same as if they had run sequentially. For the example in figure 3.54, the designer of the bank account system can safely allow Paul's deposit and Peter's withdrawal to happen concurrently, because the net result will be the same as if the two operations had happened sequentially. Second, there may be more than one possible correct result produced by a concurrent program, because we require only that the result be the same as for some sequential order. For example, suppose that Peter and Paul's joint account starts out with $100, and Peter deposits $40 while Paul concurrently withdraws half the money in the account. Then sequential execution could result in the account balance being either $70 or $90 (see exercise 3.38).
より緩やかな並行性への制約は、並行システムがスレッドを何らかの順序で逐次的に実行した場合と同じ結果を生成することを保証するものです。この要件には2つの重要な側面があります。第一に、スレッドを実際に逐次的に実行する必要はなく、逐次的に実行されたかのように同じ結果を生成することだけが求められます。図 3.54の例では、銀行口座システムの設計者は、Paulの預け入れとPeterの引き出しを並行して行うことを安全に許可できます。なぜなら、最終結果は2つの操作が逐次的に行われた場合と同じになるからです。第二に、並行プログラムによって生成される正しい結果は複数存在する可能性があります。なぜなら、結果が何らかの逐次順序での結果と同じであることだけが要求されるからです。たとえば、PeterとPaulの共同口座が$100から始まり、Peterが$40を預け入れるのと並行して、Paulが口座の半分の金額を引き出すとします。すると逐次実行では、口座残高は$70または$90のいずれかになる可能性があります（演習 3.38を参照）。
[5]

There are still weaker requirements for correct execution of concurrent programs. A program for simulating diffusion (say, the flow of heat in an object) might consist of a large number of threads, each one representing a small volume of space, that update their values concurrently. Each thread repeatedly changes its value to the average of its own value and its neighbors' values. This algorithm converges to the right answer independent of the order in which the operations are done; there is no need for any restrictions on concurrent use of the shared values.
並行プログラムの正しい実行には、さらに緩い要件もあります。 拡散（たとえば物体内の熱の流れ）をシミュレートするプログラムは、それぞれが空間の小さな体積を表す多数のスレッドから構成され、それらが値を並行して更新するかもしれません。各スレッドは、自身の値を自身と隣接するものの値の平均に繰り返し変更します。このアルゴリズムは、操作が行われる順序に関係なく正しい答えに収束します。したがって、共有された値の並行利用に制約を設ける必要はありません。
