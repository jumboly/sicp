3.2.1  
The Rules for Evaluation
評価のルール

The overall specification of how the interpreter evaluates a function application remains the same as when we first introduced it in section 1.1.4:
  • To evaluate an application:
    1. Evaluate the subexpressions of the application.
    2. Apply the value of the function subexpression to the values of the argument subexpressions.
The environment model of evaluation replaces the substitution model in specifying what it means to apply a compound function to arguments.
インタプリタが 関数適用 をどのように評価するかの全体的な仕様は、  1.1.4節で最初に導入したときと変わりません。
  • 適用を評価するには：
    1. 適用 の部分式を評価する。
    2. 関数 の部分式の値を、 引数 の部分式の値に適用する。
環境モデルによる評価は、複合 関数 を引数に適用するとはどういう意味かを規定する際に、置換モデルに取って代わるものです。
[1]

In the environment model of evaluation, a function is always a pair consisting of some code and a pointer to an environment. Functions are created in one way only: by evaluating a lambda expression. This produces a function whose code is obtained from the text of the lambda expression and whose environment is the environment in which the lambda expression was evaluated to produce the function. For example, consider the function declaration
環境モデルによる評価では、 関数 は常に、コードと環境へのポインタからなるペアです。 関数 が生成される方法はただ一つ、 ラムダ 式を評価することです。 これにより 関数 が生成されます。そのコード部分は ラムダ 式のテキストから取得され、環境部分はその ラムダ 式が評価されて 関数 が生成された環境です。 たとえば、次の 関数宣言 を考えてみましょう。 
function square(x) {
    return x * x;
}
evaluated in the program environment. The function declaration syntax is equivalent to an underlying implicit lambda expression. It would have been equivalent to have used
を プログラム 環境で評価した場合を考えます。 関数宣言 の構文は、暗黙の ラムダ 式 と等価です。 次のように書いても同じことです。
[2] 
const square = x => x * x;
which evaluates x => x * x and binds square to the resulting value, all in the program environment.
これは x => x * x を評価し、その結果の値に square を束縛します。これらはすべて プログラム 環境の中で行われます。

Figure 3.4 shows the result of evaluating this declaration statement. The global environment encloses the program environment. To reduce clutter, after this figure we will not display the global environment (as it is always the same), but we are reminded of its existence by the pointer from the program environment upward. The function object is a pair whose code specifies that the function has one parameter, namely x, and a function body return x * x;. The environment part of the function is a pointer to the program environment, since that is the environment in which the lambda expression was evaluated to produce the function. A new binding, which associates the function object with the name square, has been added to the program frame.
図 3.4 は、この 宣言文 を評価した結果を示しています。 グローバル環境はプログラム環境を囲んでいます。 図を簡潔にするため、この図以降はグローバル環境を表示しませんが （常に同じなので）、プログラム環境から上向きに伸びるポインタによって その存在を思い出すことができます。 関数 オブジェクトはペアであり、そのコード部分は、この 関数 が1つのパラメータ x を持ち、 関数 本体が return x * x; であることを示しています。 関数 の環境部分はプログラム環境へのポインタです。 なぜなら、 ラムダ 式が評価されて 関数 が生成されたのが、その環境だからです。 関数 オブジェクトを 名前 square に関連付ける新しい束縛が、プログラムフレームに追加されました。

In general, const, function, and let add bindings to frames. Assignment is forbidden on constants, so our environment model needs to distinguish names that refer to constants from names that refer to variables. We indicate that a name is a constant by writing an equal sign after the colon that follows the name. We consider function declarations as equivalent to constant declarations; observe the equal signs after the colons in figure 3.4.
一般に、const、 function、 let はフレームに束縛を追加します。 定数への代入は禁止されているため、環境モデルでは定数を参照する名前と 変数を参照する名前を区別する必要があります。 名前が定数であることを示すために、名前の後のコロンの後に等号を書きます。 関数宣言は定数宣言と等価であるとみなします。 図 3.4のコロンの後の等号に注目してください。
[3]

Now that we have seen how functions are created, we can describe how functions are applied. The environment model specifies: To apply a function to arguments, create a new environment containing a frame that binds the parameters to the values of the arguments. The enclosing environment of this frame is the environment specified by the function. Now, within this new environment, evaluate the function body.
関数 がどのように生成されるかを見たので、次は 関数 がどのように適用されるかを説明します。環境モデルでは次のように規定します。 関数 を引数に適用するには、パラメータを引数の値に束縛するフレームを含む新しい環境を作成します。このフレームの外側の環境は、 関数 によって指定された環境です。そして、この新しい環境の中で 関数 の本体を評価します。

To show how this rule is followed, figure 3.6 illustrates the environment structure created by evaluating the expression square(5) in the program environment, where square is the function generated in figure 3.4. Applying the function results in the creation of a new environment, labeled E1 in the figure, that begins with a frame in which x, the parameter for the function, is bound to the argument 5. Note that name x in environment E1 is followed by a colon with no equal sign, which indicates that the parameter x is treated as a variable. The pointer leading upward from this frame shows that the frame's enclosing environment is the program environment. The program environment is chosen here, because this is the environment that is indicated as part of the square function object. Within E1, we evaluate the body of the function, return x * x;. Since the value of x in E1 is 5, the result is 5 * 5, or 25.
この規則がどのように適用されるかを示すために、 図 3.6 に、 square(5) という式を プログラム 環境で評価したときに生成される環境構造を示します。ここで square は 図 3.4 で生成された 関数 です。 この 関数 を適用すると、図で E1 と名付けられた新しい環境が作成されます。この環境は、 関数 の パラメータ x が引数 5 に束縛されたフレームから始まります。 環境 E1 における名前 x の後に等号のないコロンが付いていることに注目してください。これはパラメータ x が変数として扱われることを示しています。 このフレームから上向きに伸びるポインタは、フレームの外側の環境が プログラム 環境であることを示しています。 プログラム 環境が選ばれるのは、それが square 関数 オブジェクトの一部として示されている環境だからです。E1 の中で、 関数 の本体 return x * x; を評価します。 E1 での x の値は 5 なので、結果は 5 * 5、 すなわち 25 です。
[4]

The environment model of function application can be summarized by two rules:
  • A function object is applied to a set of arguments by constructing a frame, binding the parameters of the function to the arguments of the call, and then evaluating the body of the function in the context of the new environment constructed. The new frame has as its enclosing environment the environment part of the function object being applied. The result of the application is the result of evaluating the return expression of the first return statement encountered while evaluating the function body.
  • A function is created by evaluating a lambda expression relative to a given environment. The resulting function object is a pair consisting of the text of the lambda expression and a pointer to the environment in which the function was created.
関数 適用の環境モデルは、2つのルールにまとめることができます。
  • 関数 オブジェクトを引数の集合に適用するには、フレームを構築し、 関数のパラメータ を呼び出しの引数に束縛し、構築された新しい環境のコンテキストで 関数 の本体を評価します。新しいフレームの外側の環境は、適用される 関数 オブジェクトの環境部分です。 適用の結果は、関数本体を評価する間に最初に出会った return 文の return 式を評価した結果です。
  • 関数 は、与えられた環境に対して ラムダ 式を評価することで生成されます。生成される 関数 オブジェクトは、 ラムダ 式のテキストと、その 関数 が生成された環境へのポインタからなるペアです。

Finally, we specify the behavior of assignment, the operation that forced us to introduce the environment model in the first place. Evaluating the expression $name$ = $value$ in some environment locates the binding of the name in the environment. That is, one finds the first frame in the environment that contains a binding for the name. If the binding is a variable binding—indicated in the frame by just : after the name—that binding is changed to reflect the new value of the variable. Otherwise, if the binding in the frame is a constant binding—indicated in the frame by := after the name—the assignment signals an "assignment to constant" error. If the name is unbound in the environment, then the assignment signals a "variable undeclared" error.
最後に、そもそも環境モデルを導入するきっかけとなった演算である代入の動作を規定します。 ある環境で式 $name$ = $value$ を評価すると、その環境の中でその名前の束縛を探します。 つまり、その名前の束縛を含む最初のフレームを見つけます。 その束縛が変数の束縛—フレーム内で名前の後に : だけが付いているもの—であれば、その束縛は変数の新しい値を反映するように変更されます。 一方、フレーム内の束縛が定数の束縛—フレーム内で名前の後に := が付いているもの—であれば、代入は "assignment to constant" エラーを発生させます。 その名前が環境内で未束縛であれば、代入は "variable undeclared" エラーを発生させます。

These evaluation rules, though considerably more complex than the substitution model, are still reasonably straightforward. Moreover, the evaluation model, though abstract, provides a correct description of how the interpreter evaluates expressions. In chapter 4 we shall see how this model can serve as a blueprint for implementing a working interpreter. The following sections elaborate the details of the model by analyzing some illustrative programs.
これらの評価規則は、置換モデルよりもかなり複雑ですが、それでも十分に理解しやすいものです。さらに、この評価モデルは抽象的ではありますが、インタプリタが式をどのように評価するかの正確な記述を提供しています。第 4章では、このモデルが実際に動作するインタプリタを実装するための設計図としてどのように機能するかを見ていきます。以降の節では、いくつかの具体的なプログラムを分析することで、このモデルの詳細を掘り下げていきます。

[1]
Assignment introduces a subtlety into step 1 of the evaluation rule. As shown in exercise , the presence of assignment allows us to write expressions that will produce different values depending on the order in which the subexpressions in a combination are evaluated. To eliminate such ambiguities, JavaScript specifies left-to-right evaluation of the subexpressions of combinations and of the argument expressions of applications.
代入は、評価規則のステップ1に微妙な問題をもたらします。 練習問題 で示すように、 代入があると、組み合わせの部分式が評価される順序によって 異なる値を生成する式を書くことが可能になります。 このような曖昧さを排除するために、 JavaScript では組み合わせの部分式と適用の引数式を 左から右の順に評価すると定めています。
[2]
Footnote undefined in chapter 1 mentions subtle differences between the two in full JavaScript, which we will ignore in this book.
第1章の脚注 undefinedで、 完全な JavaScript ではこの2つの間に微妙な違いがあることに触れていますが、 本書ではこの違いを無視します。
[3]
We mentioned in footnote undefined in chapter 1 that the full JavaScript language allows assignment to names that are declared with function declarations.
第1章の脚注 undefinedで、 完全な JavaScript では関数宣言で宣言された名前への代入が許可されていることに触れました。
[4]
This example does not make use of the fact that the parameter x is a variable, but recall the function make_withdraw in section 3.1.1, which relied on its parameter being a variable.
この例ではパラメータ x が変数であるという事実を利用していませんが、  3.1.1節の関数 make_withdraw では、パラメータが変数であることに 依存していたことを思い出してください。
