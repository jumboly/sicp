5.5.5  
An Example of Compiled Code
コンパイル済みコードの例

Now that we have seen all the elements of the compiler, let us examine an example of compiled code to see how things fit together. We will compile the declaration of a recursive factorial function by passing as first argument to compile the result of applying parse to a string representation of the program (here using back quotes `$\ldots$`, which work like single and double quotation marks but allow the string to span multiple lines):
コンパイラのすべての要素を見てきたので、コンパイル済みコードの例を調べて、すべてがどのように組み合わさるかを確認しましょう。再帰的な factorial 関数 の 宣言 を compile の第一引数として、プログラムの文字列表現に parse を適用した結果を渡して （ここでは バッククォート `$\ldots$` を使用しています。これはシングルクォートやダブルクォートと同様に機能しますが、文字列を複数行にまたがって記述できます） コンパイルします： 
compile(parse(`
function factorial(n) {
    return n === 1
           ? 1
           : factorial(n - 1) * n;
}
              `),
        "val",
        "next");
We have specified that the value of the declaration should be placed in the val register. We don't care what the compiled code does after executing the declaration, so our choice of "next" as the linkage descriptor is arbitrary.
宣言 の値を val レジスタに格納するよう指定しています。 宣言 の実行後にコンパイル済みコードが何をするかは問わないので、リンケージ記述子として "next" を選んでいますが、これは任意の選択です。

The function compile determines that it was given a function declaration, so it transforms it to a constant declaration and then calls compile_declaration. This compiles code to compute the value to be assigned (targeted to val), followed by code to install the declaration, followed by code to put the value of the declaration (which is the value undefined) into the target register, followed finally by the linkage code. The env register is preserved around the computation of the value, because it is needed in order to install the declaration. Because the linkage is "next", there is no linkage code in this case. The skeleton of the compiled code is thus
関数 compile は関数宣言が与えられたと判定し、それを定数宣言に変換してから compile_declaration を呼び出します。これは 代入される値を計算するコード（ターゲットは val）、続いて 宣言 を設定するコード、続いて 宣言の値（値 undefined） をターゲットレジスタに格納するコード、そして最後にリンケージコードをコンパイルします。 env レジスタ は、 宣言 を設定するために必要なので、値の計算の前後で保存されます。リンケージが "next" なので、この場合はリンケージコードはありません。コンパイル済みコードの骨格は次のようになります。
$\langle{}$save env if modified by code to compute value$\rangle$ $\langle{}$compilation of declaration value, target val, linkage "next"$\rangle$ $\langle{}$restore env if saved above$\rangle$ perform(list(op("assign_symbol_value"), constant("factorial"), reg("val"), reg("env"))), assign("val", constant(undefined))

The expression that is compiled to produce the value for the name factorial is a lambda expression whose value is the function that computes factorials. The function compile handles this by calling compile_lambda_expression, which compiles the function body, labels it as a new entry point, and generates the instruction that will combine the function body at the new entry point with the runtime environment and assign the result to val. The sequence then skips around the compiled function code, which is inserted at this point. The function code itself begins by extending the function's declaration environment by a frame that binds the parameter n to the function argument. Then comes the actual function body. Since this code for the value of the name doesn't modify the env register, the optional save and restore shown above aren't generated. (The function code at entry1 isn't executed at this point, so its use of env is irrelevant.) Therefore, the skeleton for the compiled code becomes
名前 factorial の値を生成するためにコンパイルされる式は、階乗を計算する 関数 を値とする ラムダ 式です。 関数 compile は compile_lambda_expression を呼び出してこれを処理します。この関数は 関数 本体をコンパイルし、新しいエントリポイントとしてラベルを付け、新しいエントリポイントの 関数 本体を実行時環境と結合して結果を val に代入する命令を生成します。次に、この地点に挿入されるコンパイル済み 関数 コードをスキップします。 関数 コード自体は、 関数の宣言 環境にパラメータ n を 関数 の引数に束縛するフレームを拡張することから始まります。そして実際の 関数 本体が続きます。 名前 の値のためのこのコードは env レジスタを変更しないので、上で示したオプションの save と restore は生成されません。（entry1 の 関数 コードはこの時点では実行されないので、env の使用は関係ありません。）したがって、コンパイル済みコードの骨格は次のようになります。
$\texttt{ }\texttt{ }$assign("val", list(op("make_compiled_function"), label("entry1"), reg("env"))), go_to(label("after_lambda2")), "entry1", assign("env", list(op("compiled_function_env"), reg("fun"))), assign("env", list(op("extend_environment"), constant(list("n")), reg("argl"), reg("env"))), $\langle{}$compilation of function body$\rangle$ "after_lambda2", perform(list(op("assign_symbol_value"), constant("factorial"), reg("val"), reg("env"))), assign("val", constant(undefined))

A function body is always compiled (by compile_lambda_body) with target val and linkage "next". The body in this case consists of a single return statement:
関数 本体は常に（ compile_lambda_body によって） ターゲット val、リンケージ "next" でコンパイルされます。この場合、 本体 は単一の return 文 で構成されています：
[1] 
return n === 1
       ? 1
       : factorial(n - 1) * n;
The function compile_return_statement generates code to revert the stack using the marker and to restore the continue register, and then compiles the return expression with target val and linkage "return", because its value is to be returned from the function.
関数 compile_return_statement は、マーカーを使ってスタックを元に戻し、continue レジスタを復元するコードを生成し、次に return 式をターゲット val、リンケージ "return" でコンパイルします。その値は関数から返されるものだからです。
The return expression is a conditional expression, for which compile_conditional generates code that first computes the predicate (targeted to val), then checks the result and branches around the true branch if the predicate is false. Registers env and continue are preserved around the predicate code, since they may be needed for the rest of the conditional expression. The true and false branches are both compiled with target val and linkage "return". (That is, the value of the conditional, which is the value computed by either of its branches, is the value of the function.)
return 式は条件式であり、 compile_conditional が まず述語を計算し（ターゲットは val）、結果をチェックして述語が偽であれば真の分岐を飛び越えるコードを生成します。レジスタ env と continue は、 条件 式の残りの部分で必要になる可能性があるので、述語コードの前後で保存されます。 真の分岐と偽の分岐はともにターゲット val、リンケージ "return" でコンパイルされます。（つまり、条件式の値、すなわちどちらかの分岐で計算された値が 関数 の値となります。）
$\texttt{ }\texttt{ }$revert_stack_to_marker(), restore("continue"), $\langle{}$save continue, env if modified by predicate and needed by branches$\rangle$ $\langle{}$compilation of predicate, target val, linkage "next"$\rangle$ $\langle{}$restore continue, env if saved above$\rangle$ test(list(op("is_falsy"), reg("val"))), branch(label("false_branch4")), "true_branch3", $\langle{}$compilation of true branch, target val, linkage "return"$\rangle$ "false_branch4", $\langle{}$compilation of false branch, target val, linkage "return"$\rangle$ "after_cond5",

The predicate n === 1 is a function application (after transformation of the operator combination).
述語 n === 1 は 関数適用です（演算子の組み合わせの変換後）。
This looks up the function expression (the symbol "===") and places this value in fun. It then assembles the arguments 1 and the value of n into argl. Then it tests whether fun contains a primitive or a compound function, and dispatches to a primitive branch or a compound branch accordingly. Both branches resume at the after_call label. The compound branch must set up continue to jump past the primitive branch and push a marker to the stack to match the revert operation in the compiled return statement of the function. The requirements to preserve registers around the evaluation of the function and argument expressions don't result in any saving of registers, because in this case those evaluations don't modify the registers in question.
これは 関数式（シンボル "==="） を探索し、その値を fun に格納します。次に引数 1 と n の値を argl に組み立てます。そして fun がプリミティブ 関数 か複合 関数 かをテストし、それに応じてプリミティブ分岐または複合分岐にディスパッチします。両方の分岐は after_call ラベルで合流します。 複合分岐では、continue をプリミティブ分岐の後に飛ぶように設定し、コンパイル済み関数の return 文のリバート操作に対応するマーカーをスタックにプッシュする必要があります。 関数式と引数式 の評価の前後でレジスタを保存する必要はありません。この場合、それらの評価は対象のレジスタを変更しないからです。
$\texttt{ }\texttt{ }$assign("fun", list(op("lookup_symbol_value"), constant("==="), reg("env"))), assign("val", constant(1)), assign("argl", list(op("list"), reg("val"))), assign("val", list(op("lookup_symbol_value"), constant("n"), reg("env"))), assign("argl", list(op("pair"), reg("val"), reg("argl"))), test(list(op("is_primitive_function"), reg("fun"))), branch(label("primitive_branch6")), "compiled_branch7", assign("continue", label("after_call8")), save("continue"), push_marker_to_stack(), assign("val", list(op("compiled_function_entry"), reg("fun"))), go_to(reg("val")), "primitive_branch6", assign("val", list(op("apply_primitive_function"), reg("fun"), reg("argl"))), "after_call8",

The true branch, which is the constant 1, compiles (with target val and linkage "return") to
真の分岐は定数 1 であり、（ターゲット val、リンケージ "return" で）次のようにコンパイルされます。
$\texttt{ }\texttt{ }$assign("val", constant(1)), go_to(reg("continue")),
The code for the false branch is another function call, where the function is the value of the symbol "*", and the arguments are n and the result of another function call (a call to factorial). Each of these calls sets up fun and argl and its own primitive and compound branches. Figure 5.22 shows the complete compilation of the declaration of the factorial function. Notice that the possible save and restore of continue and env around the predicate, shown above, are in fact generated, because these registers are modified by the function call in the predicate and needed for the function call and the "return" linkage in the branches.
偽の分岐のコードは別の 関数 呼び出しで、 関数 はシンボル "*" の値であり、引数は n と別の 関数 呼び出し（factorial の呼び出し）の結果です。これらの呼び出しのそれぞれが fun と argl を設定し、それぞれ独自のプリミティブ分岐と複合分岐を持ちます。図 5.22に factorial 関数 の 宣言 の完全なコンパイル結果を示します。上で示した continue と env の save と restore が実際に生成されていることに注目してください。これらのレジスタは述語内の 関数 呼び出しによって変更され、分岐内の 関数 呼び出しと "return" リンケージで必要とされるからです。

Exercise 5.36
Compile the iterative factorial function
反復的な階乗 関数 をコンパイルしてください。 
function factorial(n) {
    function iter(product, counter) {
        return counter > n
               ? product
               : iter(product * counter, counter + 1);
    }
    return iter(1, 1);
}

What order of evaluation does our compiler produce for arguments of an application? Is it left-to-right (as mandated by the ECMAScript specification), right-to-left, or some other order? Where in the compiler is this order determined? Modify the compiler so that it produces some other order of evaluation.
