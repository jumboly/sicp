3.5.5  
Modularity of Functional Programs and Modularity of Objects
関数型プログラムのモジュール性とオブジェクトのモジュール性

As we saw in section 3.1.2, one of the major benefits of introducing assignment is that we can increase the modularity of our systems by encapsulating, or hiding, parts of the state of a large system within local variables. Stream models can provide an equivalent modularity without the use of assignment. As an illustration, we can reimplement the Monte Carlo estimation of $\pi$, which we examined in section 3.1.2, from a stream-processing point of view.
3.1.2節で見たように、代入の導入がもたらす主要な利点の一つは、大きなシステムの状態の一部をローカル変数内にカプセル化（あるいは隠蔽）することで、システムのモジュール性を高められる点でした。ストリームモデルは、代入を使わずに同等のモジュール性を提供できます。その例として、3.1.2節で扱った$\pi$のモンテカルロ推定を、ストリーム処理の観点から再実装してみましょう。

The key modularity issue was that we wished to hide the internal state of a random-number generator from programs that used random numbers. We began with a function rand_update, whose successive values furnished our supply of random numbers, and used this to produce a random-number generator:
モジュール性に関する重要な論点は、乱数を使うプログラムから乱数生成器の内部状態を隠したい、という点でした。まず、連続する値が乱数の供給源となる関数rand_updateから始め、これを使って乱数生成器を作りました。 
function make_rand() {
    let x = random_init;
    return () => {
               x = rand_update(x);
               return x;
           };
}
const rand = make_rand();

In the stream formulation there is no random-number generator per se, just a stream of random numbers produced by successive calls to rand_update:
ストリームによる定式化では、乱数生成器それ自体としては存在せず、rand_updateを連続的に呼び出して生成される乱数のストリームがあるだけです。 
const random_numbers =
    pair(random_init,
         () => stream_map(rand_update, random_numbers));
We use this to construct the stream of outcomes of the Cesàro experiment performed on consecutive pairs in the random_numbers stream:
これを使って、random_numbersストリーム中の連続するペアに対して行ったチェザロ（Cesàro）の実験の結果のストリームを構築します。 
function map_successive_pairs(f, s) {
    return pair(f(head(s), head(stream_tail(s))),
                () => map_successive_pairs(
                          f,
                          stream_tail(stream_tail(s))));
}
const dirichlet_stream =
    map_successive_pairs((r1, r2) => gcd(r1, r2) === 1,
                         random_numbers);
The dirichlet_stream is now fed to a monte_carlo function, which produces a stream of estimates of probabilities. The results are then converted into a stream of estimates of $\pi$. This version of the program doesn't need a parameter telling how many trials to perform. Better estimates of $\pi$ (from performing more experiments) are obtained by looking farther into the pi stream:
このdirichlet_streamをmonte_carlo関数に渡すと、確率の推定のストリームが生成されます。そしてその結果を$\pi$の推定のストリームに変換します。このバージョンのプログラムでは、試行を何回行うかを指定するパラメータは必要ありません。$\pi$のより良い推定値（より多くの実験を行った結果）は、piストリームの先を覗き込むことで得られます。 
function monte_carlo(experiment_stream, passed, failed) {      
    function next(passed, failed) {
        return pair(passed / (passed + failed),
                    () => monte_carlo(stream_tail(experiment_stream),
                                      passed, failed));
    }
    return head(experiment_stream)
           ? next(passed + 1, failed)
           : next(passed, failed + 1);
}
const pi = stream_map(p => math_sqrt(6 / p),
                      monte_carlo(dirichlet_stream, 0, 0));
There is considerable modularity in this approach, because we still can formulate a general monte_carlo function that can deal with arbitrary experiments. Yet there is no assignment or local state.
このアプローチにはかなりのモジュール性があります。なぜなら、任意の実験を扱える汎用のmonte_carlo関数を依然として定式化できるからです。それでいて、代入もローカル状態もまったくありません。

A functional-programming view of time
関数型プログラミングから見た時間

Let us now return to the issues of objects and state that were raised at the beginning of this chapter and examine them in a new light. We introduced assignment and mutable objects to provide a mechanism for modular construction of programs that model systems with state. We constructed computational objects with local state variables and used assignment to modify these variables. We modeled the temporal behavior of the objects in the world by the temporal behavior of the corresponding computational objects.
ここで、本章の冒頭で提起したオブジェクトと状態の問題に戻り、それらを新しい光のもとで考察してみましょう。私たちは、状態を持つシステムをモデル化するプログラムをモジュール的に構築するための機構として、代入とミュータブルなオブジェクトを導入しました。そして、ローカル状態変数を持つ計算オブジェクトを構築し、代入を使ってそれらの変数を変更しました。現実世界のオブジェクトの時間的な振る舞いを、対応する計算オブジェクトの時間的な振る舞いによってモデル化したのです。

Now we have seen that streams provide an alternative way to model objects with local state. We can model a changing quantity, such as the local state of some object, using a stream that represents the time history of successive states. In essence, we represent time explicitly, using streams, so that we decouple time in our simulated world from the sequence of events that take place during evaluation. Indeed, because of the presence of delayed evaluation there may be little relation between simulated time in the model and the order of events during the evaluation.
さて、ローカル状態を持つオブジェクトをモデル化するもうひとつのやり方をストリームが提供してくれることを見てきました。あるオブジェクトのローカル状態のような変化する量を、連続する状態の時間履歴を表すストリームを使ってモデル化できます。本質的に、ストリームを使って時間を明示的に表現しているため、シミュレートされた世界での時間を、評価中に起こるイベントの順序から切り離せます。実際、遅延評価の存在により、モデル内のシミュレートされた時間と、評価中のイベントの順序との間にはほとんど関係がない場合もあります。

In order to contrast these two approaches to modeling, let us reconsider the implementation of a withdrawal processor that monitors the balance in a bank account. In section 3.1.3 we implemented a simplified version of such a processor:
モデル化に対するこれら2つのアプローチを対比するため、銀行口座の残高を監視する引き出しプロセッサの実装を再考してみましょう。3.1.3節では、このようなプロセッサの簡略版を実装しました。 
function make_simplified_withdraw(balance) {
    return amount => {
               balance = balance - amount;
               return balance;
           };
}
Calls to make_simplified_withdraw produce computational objects, each with a local state variable balance that is decremented by successive calls to the object. The object takes an amount as an argument and returns the new balance. We can imagine the user of a bank account typing a sequence of inputs to such an object and observing the sequence of returned values shown on a display screen.
make_simplified_withdrawの呼び出しは計算オブジェクトを生成します。各オブジェクトはローカル状態変数balanceを持ち、オブジェクトへの連続した呼び出しによって減算されます。オブジェクトはamountを引数として受け取り、新しい残高を返します。銀行口座のユーザーがこのようなオブジェクトに一連の入力を入力し、ディスプレイ画面に表示される返される値の列を観察する様子を思い浮かべることができます。

Alternatively, we can model a withdrawal processor as a function that takes as input a balance and a stream of amounts to withdraw and produces the stream of successive balances in the account:
あるいは、引き出しプロセッサを、残高と引き出す金額のストリームを入力として受け取り、口座の連続した残高のストリームを生成する関数としてモデル化することもできます。 
function stream_withdraw(balance, amount_stream) {      
    return pair(balance,
                () => stream_withdraw(balance - head(amount_stream),
                                      stream_tail(amount_stream)));   
}
The function stream_withdraw implements a well-defined mathematical function whose output is fully determined by its input. Suppose, however, that the input amount_stream is the stream of successive values typed by the user and that the resulting stream of balances is displayed. Then, from the perspective of the user who is typing values and watching results, the stream process has the same behavior as the object created by make_simplified_withdraw. However, with the stream version, there is no assignment, no local state variable, and consequently none of the theoretical difficulties that we encountered in section 3.1.3. Yet the system has state!
関数stream_withdrawは、出力が入力によって完全に決定される、定義の明確な数学関数を実装しています。しかし、入力amount_streamがユーザーがタイプした連続した値のストリームであり、結果として得られる残高のストリームが表示されるとしましょう。すると、値を入力して結果を見るユーザーの観点からは、このストリームプロセスはmake_simplified_withdrawによって作られたオブジェクトと同じふるまいをします。しかし、ストリーム版では代入もローカル状態変数もなく、その結果として3.1.3節で遭遇した理論的な困難もまったくありません。それでもシステムは状態を持つのです！

This is really remarkable. Even though stream_withdraw implements a well-defined mathematical function whose behavior does not change, the user's perception here is one of interacting with a system that has a changing state. One way to resolve this paradox is to realize that it is the user's temporal existence that imposes state on the system. If the user could step back from the interaction and think in terms of streams of balances rather than individual transactions, the system would appear stateless.
これは実に注目すべきことです。 stream_withdraw はふるまいが変わらない定義の明確な数学関数を実装しているにもかかわらず、ここでのユーザーの知覚は変化する状態を持つシステムと相互作用しているというものです。このパラドックスを解消する一つの方法は、システムに状態を課しているのはユーザーの時間的な存在であると認識することです。もしユーザーが相互作用から一歩退いて、個々の取引ではなく残高のストリームという観点で考えることができたなら、システムは状態を持たないように見えるでしょう。
[1]

From the point of view of one part of a complex process, the other parts appear to change with time. They have hidden time-varying local state. If we wish to write programs that model this kind of natural decomposition in our world (as we see it from our viewpoint as a part of that world) with structures in our computer, we make computational objects that are not functional—they must change with time. We model state with local state variables, and we model the changes of state with assignments to those variables. By doing this we make the time of execution of a computation model time in the world that we are part of, and thus we get objects in our computer.
複雑なプロセスのある部分の視点からすると、他の部分は時間とともに変化するように見えます。それらは隠れた時間とともに変化するローカル状態を持っています。もし我々が、我々の世界（その世界の一部としての我々の視点から見たもの）におけるこの種の自然な分解を、コンピュータ内の構造でモデル化するプログラムを書きたいのであれば、関数的でない計算オブジェクト—つまり時間とともに変化しなければならないオブジェクトを作ることになります。我々は状態をローカル状態変数でモデル化し、状態の変化をそれらの変数への代入でモデル化します。こうすることで、計算が実行される時間を、我々が住んでいる世界の時間のモデルとして使うことになり、その結果としてコンピュータ内にオブジェクトが生まれるのです。

Modeling with objects is powerful and intuitive, largely because this matches the perception of interacting with a world of which we are part. However, as we've seen repeatedly throughout this chapter, these models raise thorny problems of constraining the order of events and of synchronizing multiple processes. The possibility of avoiding these problems has stimulated the development of functional programming languages, which do not include any provision for assignment or mutable data. In such a language, all functions implement well-defined mathematical functions of their arguments, whose behavior does not change. The functional approach is extremely attractive for dealing with concurrent systems.
オブジェクトによるモデリングは強力で直観的です。それは主として、我々が一部であるところの世界との相互作用についての知覚にこの方法が合致しているからです。しかし、本章を通じて繰り返し見てきたように、これらのモデルはイベントの順序を制約することと複数のプロセスを同期することに関する厄介な問題を引き起こします。これらの問題を回避できる可能性は、 関数型プログラミング言語の開発を促してきました。関数型プログラミング言語は代入やミュータブルなデータのための仕組みを一切含みません。そのような言語では、すべての 関数 は引数についての定義の明確な数学関数を実装し、その振る舞いは変化しません。関数型のアプローチは 並行システムを扱う上で極めて魅力的です。
[2]

On the other hand, if we look closely, we can see time-related problems creeping into functional models as well. One particularly troublesome area arises when we wish to design interactive systems, especially ones that model interactions between independent entities. For instance, consider once more the implementation of a banking system that permits joint bank accounts. In a conventional system using assignment and objects, we would model the fact that Peter and Paul share an account by having both Peter and Paul send their transaction requests to the same bank-account object, as we saw in section 3.1.3. From the stream point of view, where there are no objects per se, we have already indicated that a bank account can be modeled as a process that operates on a stream of transaction requests to produce a stream of responses. Accordingly, we could model the fact that Peter and Paul have a joint bank account by merging Peter's stream of transaction requests with Paul's stream of requests and feeding the result to the bank-account stream process, as shown in figure 3.65.
一方で、注意深く見ると、関数型のモデルにも時間に関係する問題が忍び込んでくるのがわかります。特に厄介な領域が現れるのは、対話的システム、とりわけ独立したエンティティ同士の相互作用をモデル化するシステムを設計したいときです。たとえば、共同銀行口座を許可する銀行システムの実装を改めて考えてみましょう。代入とオブジェクトを使う従来のシステムでは、3.1.3節で見たように、Peter と Paul が口座を共有している事実を、Peter と Paul の両方が同じ銀行口座オブジェクトに取引リクエストを送ることでモデル化します。ストリームの観点からは、オブジェクトそのものというものはありませんが、銀行口座は取引リクエストのストリームに対して動作して応答のストリームを生成するプロセスとしてモデル化できることをすでに示しました。これに応じて、Peter と Paul が共同銀行口座を持っている事実は、図 3.65に示すように、Peter の取引リクエストのストリームと Paul のリクエストのストリームをマージし、その結果を銀行口座ストリームプロセスに渡すことでモデル化できます。

The trouble with this formulation is in the notion of merge. It will not do to merge the two streams by simply taking alternately one request from Peter and one request from Paul. Suppose Paul accesses the account only very rarely. We could hardly force Peter to wait for Paul to access the account before he could issue a second transaction. However such a merge is implemented, it must interleave the two transaction streams in some way that is constrained by real time as perceived by Peter and Paul, in the sense that, if Peter and Paul meet, they can agree that certain transactions were processed before the meeting, and other transactions were processed after the meeting.
この定式化で問題なのはマージという概念です。二つのストリームを 単にピーターからの要求とポールからの要求を交互に取り出してマージする のでは駄目です。ポールがごくまれにしか口座にアクセスしないとしましょう。 ポールが口座にアクセスするまでピーターが次の取引を発行できずに待たされる ようなことを強いるわけにはいきません。 そのようなマージがどう実装されるにせよ、二つの取引ストリームを何らかの 形で交互に並べる必要があり、その並べ方はピーターとポールが知覚する 実時間によって制約されます。つまり、ピーターとポールが 出会ったとき、ある取引が出会いより前に処理され、別の取引が出会いより 後に処理されたと両者が合意できる必要があるのです。
[3]
This is precisely the same constraint that we had to deal with in section 3.4.1, where we found the need to introduce explicit synchronization to ensure a correct order of events in concurrent processing of objects with state. Thus, in an attempt to support the functional style, the need to merge inputs from different agents reintroduces the same problems that the functional style was meant to eliminate.
これはまさに、3.4.1節で扱わざるを 得なかったのと同じ制約です。そこでは、状態を持つオブジェクトの並行処理 においてイベントの正しい順序を保証するために、明示的な 同期を導入する必要があることを見ました。このように、関数型のスタイルを 支援しようとする中で、異なるエージェントからの入力をマージする必要性が、 関数型のスタイルが取り除こうとしていた問題を再び持ち込むことになるのです。

We began this chapter with the goal of building computational models whose structure matches our perception of the real world we are trying to model. We can model the world as a collection of separate, time-bound, interacting objects with state, or we can model the world as a single, timeless, stateless unity. Each view has powerful advantages, but neither view alone is completely satisfactory. A grand unification has yet to emerge.
我々はこの章を、モデル化しようとしている現実世界についての我々の知覚と 構造が一致する計算モデルを構築するという目標とともに始めました。世界を、 状態を持つ別々の時間に縛られた相互作用するオブジェクトの集まりとして モデル化することもできますし、世界を単一の時間に依存しない状態を持たない 統一体としてモデル化することもできます。どちらの見方にも強力な利点が ありますが、どちらの見方単独では完全に満足できるものではありません。 大統一はまだ現れていないのです。
[4]

The object model approximates the world by dividing it into separate pieces. The functional model does not modularize along object boundaries.
