5.5.2  
Compiling Components
コンポーネント のコンパイル

In this section and the next we implement the code generators to which the compile function dispatches.
この節と次の節では、compile 関数 がディスパッチするコードジェネレータを実装します。

Compiling linkage code
リンケージコードのコンパイル

In general, the output of each code generator will end with instructions—generated by the function compile_linkage—that implement the required linkage. If the linkage is "return" then we must generate the instruction go_to(reg("continue")). This needs the continue register and does not modify any registers. If the linkage is "next", then we needn't include any additional instructions. Otherwise, the linkage is a label, and we generate a go_to to that label, an instruction that does not need or modify any registers.
一般に、各コードジェネレータの出力は、 関数 compile_linkage が生成する命令—要求されたリンケージを実装する命令—で終わります。リンケージが "return" であれば、命令 go_to(reg("continue")) を生成しなければなりません。この命令は continue レジスタを必要としますが、どのレジスタも変更しません。リンケージが "next" であれば、追加の命令を含める必要はありません。それ以外の場合、リンケージはラベルであり、そのラベルへの go_to を生成します。この命令はレジスタを必要とせず、変更もしません。
function compile_linkage(linkage) {
    return linkage === "return"
           ? make_instruction_sequence(list("continue"), null,
                                       list(go_to(reg("continue"))))
           : linkage === "next"
           ? make_instruction_sequence(null, null, null)
           : make_instruction_sequence(null, null, 
                                       list(go_to(label(linkage))));
}
The linkage code is appended to an instruction sequence by preserving the continue register, since a "return" linkage will require the continue register: If the given instruction sequence modifies continue and the linkage code needs it, continue will be saved and restored.
リンケージコードは、continue レジスタを preserving しながら命令列に追加されます。 "return" リンケージは continue レジスタを必要とするためです。与えられた命令列が continue を変更し、リンケージコードがそれを必要とする場合、continue は保存されて復元されます。
function end_with_linkage(linkage, instruction_sequence) {
    return preserving(list("continue"),
                      instruction_sequence,
                      compile_linkage(linkage));
}

Compiling simple components
単純な コンポーネント のコンパイル

The code generators for literal expressions and names construct instruction sequences that assign the required value to the target register and then proceed as specified by the linkage descriptor.
リテラル式と名前 のコードジェネレータは、必要な値をターゲットレジスタに代入し、リンケージ記述子で指定されたとおりに処理を続行する命令列を構築します。

The literal value is extracted at compile time from the component being compiled and put into the constant part of the assign instruction. For a name, an instruction is generated to use the lookup_symbol_value operation when the compiled program is run, to look up the value associated with a symbol in the current environment. Like a literal value, the symbol is extracted at compile time from the component being compiled. Thus symbol_of_name(component) is executed only once, when the program is being compiled, and the symbol appears as a constant in the assign instruction.
リテラル値はコンパイル時にコンパイル対象のコンポーネントから抽出され、assign 命令の定数部分に配置されます。名前の場合は、コンパイルされたプログラムの実行時に lookup_symbol_value 演算を使用して、現在の環境でシンボルに関連付けられた値を検索する命令が生成されます。リテラル値と同様に、シンボルはコンパイル時にコンパイル対象のコンポーネントから抽出されます。したがって、symbol_of_name(component) はプログラムのコンパイル時に一度だけ実行され、シンボルは assign 命令内の定数として現れます。

function compile_literal(component, target, linkage) {
    const literal = literal_value(component);
    return end_with_linkage(linkage,
               make_instruction_sequence(null, list(target),
                   list(assign(target, constant(literal)))));
}
function compile_name(component, target, linkage) {
    const symbol = symbol_of_name(component);
    return end_with_linkage(linkage,
               make_instruction_sequence(list("env"), list(target),
                   list(assign(target,
                               list(op("lookup_symbol_value"),
                                    constant(symbol),
                                    reg("env"))))));
}
These assignment instructions modify the target register, and the one that looks up a symbol needs the env register.
これらの 代入命令はターゲットレジスタを変更し、 シンボル を検索する方は env レジスタを必要とします。

Assignments and declarations are handled much as they are in the interpreter. The function compile_assignment_declaration recursively generates code that computes the value to be associated with the symbol and appends to it a two-instruction sequence that updates the value associated with the symbol in the environment and assigns the value of the whole component (the assigned value for an assignment or undefined for a declaration) to the target register. The recursive compilation has target val and linkage "next" so that the code will put its result into val and continue with the code that is appended after it. The appending is done preserving env, since the environment is needed for updating the symbol–value association and the code for computing the value could be the compilation of a complex expression that might modify the registers in arbitrary ways.
代入と 宣言 は、インタプリタとほぼ同じ方法で処理されます。 関数 compile_assignment_declaration は、シンボルに関連付ける値を計算するコードを再帰的に生成し、環境中のシンボルと値の関連付けを更新してコンポーネント全体の値（代入の場合は代入値、宣言の場合は undefined）をターゲットレジスタに代入する2命令のシーケンスを追加します。再帰的コンパイルではターゲットを val、リンケージを "next" とするので、コードは結果を val に入れ、その後に追加されたコードに続きます。追加は env を保存しながら行われます。シンボルと値の関連付けの更新に環境が必要であり、値を計算するコードは複雑な式のコンパイルで、レジスタを任意に変更する可能性があるためです。 
function compile_assignment(component, target, linkage) {
    return compile_assignment_declaration(
               assignment_symbol(component),
               assignment_value_expression(component),
               reg("val"),
               target, linkage);
}

function compile_declaration(component, target, linkage) {
    return compile_assignment_declaration(
               declaration_symbol(component),
               declaration_value_expression(component),
               constant(undefined),
               target, linkage);
}
function compile_assignment_declaration(
             symbol, value_expression, final_value,
             target, linkage) {
    const get_value_code = compile(value_expression, "val", "next");
    return end_with_linkage(linkage,
               preserving(list("env"),
                   get_value_code,
                   make_instruction_sequence(list("env", "val"),
                                             list(target),
                       list(perform(list(op("assign_symbol_value"),
                                         constant(symbol),
                                         reg("val"),
                                         reg("env"))),
                            assign(target, final_value)))));
}
The appended two-instruction sequence requires env and val and modifies the target. Note that although we preserve env for this sequence, we do not preserve val, because the get_value_code is designed to explicitly place its result in val for use by this sequence. (In fact, if we did preserve val, we would have a bug, because this would cause the previous contents of val to be restored right after the get_value_code is run.)
追加された2命令のシーケンスは env と val を必要とし、ターゲットを変更します。このシーケンスに対して env は保存しますが、val は保存しないことに注意してください。 get_value_code は、このシーケンスで使用するために結果を明示的に val に置くように設計されているためです。（実際、val を保存すると、 get_value_code の実行直後に val の以前の内容が復元されてしまうため、バグになります。）

Compiling conditionals
条件式 のコンパイル

The code for a conditional compiled with a given target and linkage has the form
与えられたターゲットとリンケージでコンパイルされた 条件式 のコードは、次の形式になります。
$\langle{}$compilation of predicate, target val, linkage "next"$\rangle$ test(list(op("is_falsy"), reg("val"))), branch(label("false_branch")), "true_branch", $\langle{}$compilation of consequent with given target and given linkage or after_cond$\rangle$ "false_branch", $\langle{}$compilation of alternative with given target and linkage$\rangle$ "after_cond"

To generate this code, we compile the predicate, consequent, and alternative, and combine the resulting code with instructions to test the predicate result and with newly generated labels to mark the true and false branches and the end of the conditional.
このコードを生成するために、述語、帰結部、代替部をコンパイルし、述語の結果をテストする命令と、真の分岐と偽の分岐および条件式の末尾を示す新しく生成されたラベルを組み合わせます。
[1]
In this arrangement of code, we must branch around the true branch if the test is false. The only slight complication is in how the linkage for the true branch should be handled. If the linkage for the conditional is "return" or a label, then the true and false branches will both use this same linkage. If the linkage is "next", the true branch ends with a jump around the code for the false branch to the label at the end of the conditional.
このコード配置では、テストが偽の場合に真の分岐を飛び越える必要があります。唯一のやや複雑な点は、真の分岐のリンケージをどう扱うかです。条件式のリンケージが "return" またはラベルであれば、真の分岐と偽の分岐はどちらもこの同じリンケージを使用します。リンケージが "next" であれば、真の分岐は偽の分岐のコードを飛び越えて条件式の末尾のラベルへジャンプするコードで終わります。
function compile_conditional(component, target, linkage) {
    const t_branch = make_label("true_branch");
    const f_branch = make_label("false_branch");
    const after_cond = make_label("after_cond");
    const consequent_linkage =
            linkage === "next" ? after_cond : linkage;
    const p_code = compile(conditional_predicate(component),
                           "val", "next");
    const c_code = compile(conditional_consequent(component),
                           target, consequent_linkage);
    const a_code = compile(conditional_alternative(component),
                           target, linkage);
    return preserving(list("env", "continue"),
             p_code,
             append_instruction_sequences(
               make_instruction_sequence(list("val"), null,
                 list(test(list(op("is_falsy"), reg("val"))),
                      branch(label(f_branch)))),
               append_instruction_sequences(
                 parallel_instruction_sequences(
                   append_instruction_sequences(t_branch, c_code),
                   append_instruction_sequences(f_branch, a_code)),
                 after_cond)));
}
The env register is preserved around the predicate code because it could be needed by the true and false branches, and continue is preserved because it could be needed by the linkage code in those branches. The code for the true and false branches (which are not executed sequentially) is appended using a special combiner parallel_instruction_sequences described in section 5.5.4.
env レジスタ は述語コードの周囲で保存されます。真の分岐と偽の分岐で必要になる可能性があるためです。また、continue はそれらの分岐のリンケージコードで必要になる可能性があるため保存されます。真の分岐と偽の分岐のコード（これらは逐次的に実行されるわけではありません）は、5.5.4節で説明する特殊な結合子 parallel_instruction_sequences を使って追加されます。

Compiling sequences
シーケンスのコンパイル

The compilation of statement sequences parallels their evaluation in the explicit-control evaluator with one exception: If a return statement appears anywhere in a sequence, we treat it as if it were the last statement. Each statement of the sequence is compiled—the last statement (or a return statement) with the linkage specified for the sequence, and the other statements with linkage "next" (to execute the rest of the sequence). The instruction sequences for the individual statements are appended to form a single instruction sequence, such that env (needed for the rest of the sequence) and continue (possibly needed for the linkage at the end of the sequence) are preserved.
文のシーケンスのコンパイルは、明示的制御評価器における評価と並行しますが、一つだけ例外があります。シーケンスのどこかに return 文が現れた場合、それを最後の文であるかのように扱います。 シーケンスの各文がコンパイルされます。最後の文（または return 文）にはシーケンスに指定されたリンケージが使われ、それ以外の文にはリンケージ "next" が使われます（シーケンスの残りを実行するためです）。個々の文の命令列は追加されて単一の命令列を形成し、env（シーケンスの残りで必要） と continue（シーケンスの末尾のリンケージで必要になる可能性がある）が保存されます。
[2] 
function compile_sequence(seq, target, linkage) {
    return is_empty_sequence(seq)
           ? compile_literal(make_literal(undefined), target, linkage)
           : is_last_statement(seq) ||
                 is_return_statement(first_statement(seq))
           ? compile(first_statement(seq), target, linkage)
           : preserving(list("env", "continue"),
                 compile(first_statement(seq), target, "next"),
                 compile_sequence(rest_statements(seq), 
                                  target, linkage));
}
Treating a return statement as if it were the last statement in a sequence avoids compiling any dead code after the return statement that can never be executed. Removing the is_return_statement check does not change the behavior of the object program; however, there are many reasons not to compile dead code, which are beyond the scope of this book (security, compilation time, size of the object code, etc.), and many compilers give warnings for dead code.
return 文をシーケンスの最後の文であるかのように扱うことで、return 文の後にある決して実行されないデッドコードのコンパイルを回避できます。is_return_statement のチェックを取り除いてもオブジェクトプログラムの動作は変わりませんが、デッドコードをコンパイルしない理由は多数あり（セキュリティ、コンパイル時間、オブジェクトコードのサイズなど）、本書の範囲を超えます。多くのコンパイラはデッドコードに対して警告を出します。
[3]

Compiling blocks
ブロックのコンパイル

A block is compiled by prepending an assign instruction to the compiled body of the block. The assignment extends the current environment by a frame that binds the names declared in the block to the value "*unassigned*". This operation both needs and modifies the env register.
ブロックは、コンパイルされたブロック本体の前に assign 命令を追加することでコンパイルされます。この代入は、ブロック内で宣言された名前を値 "*unassigned*" に束縛するフレームで現在の環境を拡張します。この操作は env レジスタを必要とし、かつ変更します。
function compile_block(stmt, target, linkage) {
    const body = block_body(stmt);
    const locals = scan_out_declarations(body);
    const unassigneds = list_of_unassigned(locals);
    return append_instruction_sequences(
               make_instruction_sequence(list("env"), list("env"),
                   list(assign("env", list(op("extend_environment"),
                                           constant(locals),
                                           constant(unassigneds),
                                           reg("env"))))),
               compile(body, target, linkage));
}

Compiling lambda expressions
ラムダ 式のコンパイル

Lambda expressions construct functions. The object code for a lambda expression must have the form
ラムダ式は 関数を 構成します。ラムダ式のオブジェクトコードは次の形式でなければなりません。
$\langle{}$construct function object and assign it to target register$\rangle$ $\langle{}$linkage$\rangle$
When we compile the lambda expression, we also generate the code for the function body. Although the body won't be executed at the time of function construction, it is convenient to insert it into the object code right after the code for the lambda expression. If the linkage for the lambda expression is a label or "return", this is fine. But if the linkage is "next", we will need to skip around the code for the function body by using a linkage that jumps to a label that is inserted after the body. The object code thus has the form
ラムダ式をコンパイルするとき、関数本体のコードも生成します。本体は関数の構成時には実行されませんが、ラムダ式のコードの直後にオブジェクトコードに挿入しておくのが便利です。ラムダ式のリンケージがラベルまたは "return" であればこれで問題ありません。しかしリンケージが "next" の場合は、本体の後に挿入されたラベルへジャンプするリンケージを使って、関数本体のコードを飛び越える必要があります。したがって、オブジェクトコードは次の形式になります。
$\langle{}$construct function object and assign it to target register$\rangle$ $\langle{}$code for given linkage$\rangle$ $or$ go_to(label("after_lambda")) $\langle{}$compilation of function body$\rangle$ "after_lambda"

The function compile_lambda_expression generates the code for constructing the function object followed by the code for the function body. The function object will be constructed at run time by combining the current environment (the environment at the point of declaration) with the entry point to the compiled function body (a newly generated label).
関数 compile_lambda_expression は、関数オブジェクトを構成するコードと、それに続く関数本体のコードを生成します。関数オブジェクトは実行時に、現在の環境（宣言時点の環境）とコンパイルされた関数本体へのエントリポイント（新しく生成されたラベル）を組み合わせて構成されます。
[4] 
function compile_lambda_expression(exp, target, linkage) {
    const fun_entry = make_label("entry");
    const after_lambda = make_label("after_lambda");
    const lambda_linkage =
            linkage === "next" ? after_lambda : linkage;
    return append_instruction_sequences(
               tack_on_instruction_sequence(
                   end_with_linkage(lambda_linkage,
                       make_instruction_sequence(list("env"),
                                                 list(target),
                           list(assign(target,
                                    list(op("make_compiled_function"),
                                         label(fun_entry),
                                         reg("env")))))),
                   compile_lambda_body(exp, fun_entry)),
               after_lambda);
}
The function compile_lambda_expression uses the special combiner tack_on_instruction_sequence (from section 5.5.4) rather than append_instruction_sequences to append the function body to the lambda expression code, because the body is not part of the sequence of instructions that will be executed when the combined sequence is entered; rather, it is in the sequence only because that was a convenient place to put it.
関数 compile_lambda_expression は、関数本体をラムダ式のコードに追加するために、 append_instruction_sequences ではなく、特殊な結合子 tack_on_instruction_sequence （5.5.4節から）を使用します。なぜなら、本体は結合された列に入ったときに実行される命令列の一部ではなく、そこに置くのが便利だったからにすぎません。

The function compile_lambda_body constructs the code for the body of the function. This code begins with a label for the entry point. Next come instructions that will cause the runtime evaluation environment to switch to the correct environment for evaluating the function body—namely, the environment of the function, extended to include the bindings of the parameters to the arguments with which the function is called. After this comes the code for the function body, augmented to ensure that it ends with a return statement. The augmented body is compiled with target val so that its return value will be placed in val. The linkage descriptor passed to this compilation is irrelevant, as it will be ignored. Since a linkage argument is required, we arbitrarily pick "next".
関数 compile_lambda_body は、関数本体のコードを構成します。このコードはエントリポイントのラベルから始まります。次に、実行時の評価環境を関数本体の評価に適した正しい環境に切り替える命令が来ます。すなわち、関数の環境を、パラメータを関数が呼び出された引数に束縛するよう拡張した環境です。その後に、関数本体のコードが来ます。本体は return 文で終わることが保証されるよう拡張されます。 拡張された本体はターゲット val でコンパイルされるので、戻り値は val に格納されます。このコンパイルに渡されるリンケージ記述子は無視されるため、関係ありません。リンケージ引数は必須なので、任意に "next" を選びます。
[5] 
function compile_lambda_body(exp, fun_entry) {
    const params  = lambda_parameter_symbols(exp);
    return append_instruction_sequences(
        make_instruction_sequence(list("env", "fun", "argl"),
                                  list("env"),
            list(fun_entry,
                 assign("env",
                        list(op("compiled_function_env"),
                             reg("fun"))),
                 assign("env",
                        list(op("extend_environment"),
                             constant(params),
                             reg("argl"),
                             reg("env"))))),
        compile(append_return_undefined(lambda_body(exp)),
                "val", "next"));
}

To ensure that all functions end by executing a return statement, compile_lambda_body appends to the lambda body a return statement whose return expression is the literal undefined. To do so, it uses the function append_return_undefined, which constructs the parser's tagged-list representation (from section 4.1.2) of a sequence consisting of the body and a return undefined; statement.
すべての関数が return 文の実行で終わることを保証するために、compile_lambda_body はラムダ本体に、戻り式がリテラル undefined である return 文を追加します。そのために関数 append_return_undefined を使用します。この関数は、本体と return undefined; 文から成るシーケンスのパーサーのタグ付きリスト表現（4.1.2節から）を構成します。
function append_return_undefined(body) {
    return list("sequence", list(body,
                                 list("return_statement",
                                      list("literal", undefined))));
}
This simple transformation of lambda bodies is a third way to ensure that a function that does not return explicitly has the return value undefined. In the metacircular evaluator, we used a return-value object, which also played a role in stopping a sequence evaluation. In the explicit-control evaluator, functions that did not return explicitly continued to an entry point that stored undefined in val. See exercise 5.34 for a more elegant way to handle insertion of return statements.
このラムダ本体の単純な変換は、明示的に return しない関数の戻り値を undefined にする3つ目の方法です。メタ循環評価器では、シーケンスの評価を停止する役割も果たす戻り値オブジェクトを使いました。明示的制御評価器では、明示的に return しない関数は val に undefined を格納するエントリポイントに続きました。return 文の挿入をより洗練された方法で扱うには、練習問題 5.34を参照してください。
