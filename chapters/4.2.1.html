4.2.1  
Normal Order and Applicative Order
正規順序と適用順序

In section 1.1, where we began our discussion of models of evaluation, we noted that JavaScript is an applicative-order language, namely, that all the arguments to JavaScript functions are evaluated when the function is applied. In contrast, normal-order languages delay evaluation of function arguments until the actual argument values are needed. Delaying evaluation of function arguments until the last possible moment (e.g., until they are required by a primitive operation) is called lazy evaluation.
節 1.1で評価モデルの議論を始めたとき、 JavaScript は適用順序（applicative-order）の言語であること、すなわち JavaScript の 関数 へのすべての引数は、 関数 が適用されるときに評価されることを述べました。これに対して、正規順序（normal-order）の言語では、 関数 の引数の評価は、実際の引数値が必要になるまで遅延されます。 関数 の引数の評価を最後の瞬間まで（たとえばプリミティブな演算で必要とされるまで）遅延させることを、 遅延評価（lazy evaluation）と呼びます。
[1]
Consider the function
次の 関数 を考えてみましょう。 
function try_me(a, b) {
    return a === 0 ? 1 : b;
}
Evaluating try_me(0, head(null)); signals an error in JavaScript. With lazy evaluation, there would be no error. Evaluating the statement would return 1, because the argument head(null) would never be evaluated.
try_me(0, head(null)); を評価すると、JavaScript では エラーが発生します。しかし遅延評価では、エラーは起こりません。この 文 を評価すると 1 が返されます。なぜなら、引数 head(null) は決して評価されないからです。

An example that exploits lazy evaluation is the declaration of a function unless
遅延評価を活用する例として、 関数 unless の 宣言 があります。 
function unless(condition, usual_value, exceptional_value) {
    return condition ? exceptional_value : usual_value;
}
that can be used in statements such as
この関数は、次のような 文 で使用できます。 
unless(is_null(xs), head(xs), display("error: xs should not be null"));
This won't work in an applicative-order language because both the usual value and the exceptional value will be evaluated before unless is called (compare exercise 1.6). An advantage of lazy evaluation is that some functions, such as unless, can do useful computation even if evaluation of some of their arguments would produce errors or would not terminate.
これは適用順序の言語ではうまくいきません。なぜなら、通常値と例外値の両方が unless の呼び出し前に評価されてしまうからです （練習問題 1.6を参照）。遅延評価の利点は、 unless のような一部の 関数が、 引数の一部の評価がエラーを生じたり終了しなかったりする場合でも、有用な計算を行えることです。

If the body of a function is entered before an argument has been evaluated we say that the function is non-strict in that argument. If the argument is evaluated before the body of the function is entered we say that the function is strict in that argument.
引数が評価される前に 関数 の本体に入る場合、その 関数 はその引数に関して 非正格（non-strict）であると言います。 関数 の本体に入る前に引数が評価される場合、その 関数 はその引数に関して 正格（strict）であると言います。
[2]
In a purely applicative-order language, all functions are strict in each argument. In a purely normal-order language, all compound functions are non-strict in each argument, and primitive functions may be either strict or non-strict. There are also languages (see exercise 4.29) that give programmers detailed control over the strictness of the functions they define.
純粋な適用順序の言語では、すべての 関数 は各引数に関して正格です。純粋な正規順序の言語では、すべての複合 関数 は各引数に関して非正格であり、プリミティブ 関数 は正格にも非正格にもなり得ます。また、プログラマに自分が定義する 関数 の正格性を細かく制御できる言語もあります （練習問題 4.29を参照）。

A striking example of a function that can usefully be made non-strict is pair (or, in general, almost any constructor for data structures). One can do useful computation, combining elements to form data structures and operating on the resulting data structures, even if the values of the elements are not known. It makes perfect sense, for instance, to compute the length of a list without knowing the values of the individual elements in the list. We will exploit this idea in section 4.2.3 to implement the streams of chapter 3 as lists formed of non-strict pairs.
非正格にすることが有用な 関数 の顕著な例は、 pair です（あるいは一般に、データ構造のほぼすべてのコンストラクタが該当します）。要素の値がわからなくても、要素を組み合わせてデータ構造を形成し、そのデータ構造を操作するという有用な計算を行うことができます。たとえば、リストの個々の要素の値を知らなくてもリストの長さを計算するのは完全に理にかなっています。この考え方を節 4.2.3で活用して、第 3章のストリームを非正格な ペア で形成されるリストとして実装します。

Exercise 4.23
Suppose that (in ordinary applicative-order JavaScript) we define unless as shown above and then define factorial in terms of unless as
（通常の適用順序の JavaScript で）上で示したように unless を定義し、次に unless を使って factorial を次のように定義したとします。 
function factorial(n) {
    return unless(n === 1,
                  n * factorial(n - 1),
                  1);
}
What happens if we attempt to evaluate factorial(5)? Will our functions work in a normal-order language?
factorial(5) を評価しようとすると何が起きるでしょうか？ この 関数 は正規順序の言語で正しく動作するでしょうか？
(provided by GitHub user joeng03) When evaluated in default ('strict') mode, the code undergoes applicative order reduction and runs into an infinite loop because it needs to evaluate the arguments of the unless function, but the factorial function does not have a terminating condition. When evaluated in lazy mode, the code undergoes normal order reduction. It produces the correct output because the unless function is applied before its arguments are evaluated.
（GitHub ユーザー joeng03 による回答） デフォルトの「正格」モードで評価すると、コードは適用順序の簡約を行い、unless 関数の引数を評価する必要がありますが、factorial 関数に終了条件がないため無限ループに陥ります。 遅延モードで評価すると、コードは正規順序の簡約を行います。unless 関数がその引数の評価より先に適用されるため、正しい出力が得られます。
Exercise 4.24
Ben Bitdiddle and Alyssa P. Hacker disagree over the importance of lazy evaluation for implementing things such as unless. Ben points out that it's possible to implement unless in applicative order as a syntactic form. Alyssa counters that, if one did that, unless would be merely syntax, not a function that could be used in conjunction with higher-order functions. Fill in the details on both sides of the argument. Show how to implement unless as a derived component (like operator combination), by catching in evaluate applications whose function expression is the name unless. Give an example of a situation where it might be useful to have unless available as a function, rather than as a syntactic form.
Ben Bitdiddle と Alyssa P. Hacker は、 unless のようなものを実装するために遅延評価がどれほど重要かについて意見が分かれています。Ben は、適用順序でも unless を 構文 形式として実装できると指摘します。Alyssa は、そうすると unless は単なる構文であって、高階 関数 と組み合わせて使える 関数 ではなくなると反論します。両方の主張の詳細を埋めてください。 unless を派生コンポーネント（演算子の組み合わせのように）として実装する方法を、 evaluate の中で関数式が名前 unless であるような関数適用を捕捉することで示してください。 unless を構文形式ではなく関数として 利用できると有用な状況の例を挙げてください。
There is currently no solution available for this exercise. This textbook adaptation is a community effort. Do consider contributing by providing a solution for this exercise, using a Pull Request in Github.
[1]
The difference between the lazy terminology and the normal-order terminology is somewhat fuzzy. Generally, lazy refers to the mechanisms of particular evaluators, while normal-order refers to the semantics of languages, independent of any particular evaluation strategy. But this is not a hard-and-fast distinction, and the two terminologies are often used interchangeably.
遅延（lazy）という用語と正規順序（normal-order）という用語の違いはやや曖昧です。一般に、遅延は特定の評価器のメカニズムを指し、正規順序は特定の評価戦略とは独立に言語の意味論を指します。しかしこれは厳密な区別ではなく、二つの用語はしばしば互換的に使われます。
[2]
The strict versus non-strict terminology means essentially the same as applicative-order versus normal-order, except that it refers to individual functions and arguments rather than to the language as a whole. At a conference on programming languages you might hear someone say, The normal-order language Hassle has certain strict primitives. Other functions take their arguments by lazy evaluation.
正格（strict）対非正格（non-strict）という用語は、本質的には適用順序対正規順序と同じ意味ですが、言語全体ではなく個々の 関数 と引数に対して用いられる点が異なります。プログラミング言語の学会で、正規順序の言語 Hassle には、いくつかの正格なプリミティブがあります。その他の 関数 は遅延評価で引数を受け取ります。のような発言を耳にするかもしれません。
