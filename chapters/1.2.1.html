1.2.1  
Linear Recursion and Iteration
線形再帰と反復

We begin by considering the factorial function, defined by
まず 階乗関数について考えましょう。階乗は次のように定義されます。
\[ \begin{array}{lll} n! &=& n\cdot(n-1)\cdot(n-2)\cdots3\cdot2\cdot1 \end{array} \]
There are many ways to compute factorials. One way is to make use of the observation that $n!$ is equal to $n$ times $(n-1)!$ for any positive integer $n$:
階乗を計算する方法はたくさんあります。1つの方法は、任意の正の整数 $n$ について $n!$ が $n$ と $(n-1)!$ の積に等しいという観察を利用することです。
\[ \begin{array}{lll} n! &=& n\cdot\left[(n-1)\cdot(n-2)\cdots3\cdot2\cdot1\right] \quad = \quad n \cdot(n-1)! \end{array} \]
Thus, we can compute $n!$ by computing $(n-1)!$ and multiplying the result by $n$. If we add the stipulation that 1! is equal to 1, this observation translates directly into a computer function:
したがって、$(n-1)!$ を計算し、その結果に $n$ を掛けることで $n!$ を計算できます。1! が 1 に等しいという条件を加えれば、この観察はそのまま関数に変換できます。 
function factorial(n) {
    return n === 1 
           ? 1
           : n * factorial(n - 1);
}
We can use the substitution model of section 1.1.5 to watch this function in action computing 6!, as shown in figure 1.6.
1.1.5節の置換モデルを使って、この 関数が 6! を計算する様子を見てみましょう。figure 1.6に示します。

Now let's take a different perspective on computing factorials. We could describe a rule for computing $n!$ by specifying that we first multiply 1 by 2, then multiply the result by 3, then by 4, and so on until we reach $n$. More formally, we maintain a running product, together with a counter that counts from 1 up to $n$. We can describe the computation by saying that the counter and the product simultaneously change from one step to the next according to the rule
今度は別の視点から階乗の計算を考えましょう。$n!$ を計算するルールとして、まず 1 に 2 を掛け、次にその結果に 3 を掛け、さらに 4 を掛け、$n$ に達するまで続けるという方法を記述できます。より形式的に言えば、積の累積値（product）と、1 から $n$ まで数えるカウンター（counter）を管理します。この計算は、カウンターと積が次のルールに従って各ステップで同時に変化するものとして記述できます。
\[ \begin{array}{lll} \textrm{product} & \leftarrow & \textrm{counter} \cdot \textrm{product}\\ \textrm{counter} & \leftarrow & \textrm{counter} + 1 \end{array} \]
and stipulating that $n!$ is the value of the product when the counter exceeds $n$.
そして、カウンターが $n$ を超えたときの積の値が $n!$ であると定めます。

Once again, we can recast our description as a function for computing factorials:
ここでもまた、この記述を階乗を計算する関数として書き換えることができます。
[1] 
function factorial(n) {
    return fact_iter(1, 1, n);
}
function fact_iter(product, counter, max_count) {
    return counter > max_count
           ? product
           : fact_iter(counter * product,
                       counter + 1,
                       max_count);
}
As before, we can use the substitution model to visualize the process
前と同様に、置換モデルを使ってプロセスを可視化できます。
of computing $6!$, as shown in figure 1.8.
$6!$ の計算プロセスは figure 1.8のとおりです。

Compare the two processes. From one point of view, they seem hardly different at all. Both compute the same mathematical function on the same domain, and each requires a number of steps proportional to $n$ to compute $n!$. Indeed, both processes even carry out the same sequence of multiplications, obtaining the same sequence of partial products. On the other hand, when we consider the shapes of the two processes, we find that they evolve quite differently.
2つのプロセスを比較してみましょう。ある観点からは、ほとんど違いがないように見えます。どちらも同じ定義域で同じ数学的関数を計算し、$n!$ を計算するのに $n$ に比例するステップ数を必要とします。実際、どちらのプロセスも同じ掛け算の列を実行し、同じ部分積の列を得ます。しかし一方で、2つのプロセスの 「形」を考えると、その発展のしかたはまったく異なることがわかります。

Consider the first process. The substitution model reveals a shape of expansion followed by contraction, indicated by the arrow in figure 1.6. The expansion occurs as the process builds up a chain of deferred operations (in this case, a chain of multiplications). The contraction occurs as the operations are actually performed. This type of process, characterized by a chain of deferred operations, is called a recursive process. Carrying out this process requires that the interpreter keep track of the operations to be performed later on. In the computation of $n!$, the length of the chain of deferred multiplications, and hence the amount of information needed to keep track of it, grows linearly with $n$ (is proportional to $n$), just like the number of steps. Such a process is called a linear recursive process.
最初のプロセスを考えましょう。置換モデルは、figure 1.6の矢印で示されるように、まず膨張し、その後収縮する形を明らかにします。膨張は、プロセスが 遅延された演算の連鎖（この場合は掛け算の連鎖）を積み上げていくときに起こります。収縮は、その演算が実際に実行されるときに起こります。このような遅延された演算の連鎖で特徴づけられるプロセスを 再帰的プロセスと呼びます。このプロセスを実行するには、インタプリタが後で実行すべき演算を追跡し続ける必要があります。$n!$ の計算では、遅延された掛け算の連鎖の長さ、つまりそれを追跡するために必要な情報量は、ステップ数と同様に $n$ に対して 線形に増加します（$n$ に比例します）。このようなプロセスを 線形再帰的プロセスと呼びます。

By contrast, the second process does not grow and shrink. At each step, all we need to keep track of, for any $n$, are the current values of the names product, counter, and max_count. We call this an iterative process. In general, an iterative process is one whose state can be summarized by a fixed number of state variables, together with a fixed rule that describes how the state variables should be updated as the process moves from state to state and an (optional) end test that specifies conditions under which the process should terminate. In computing $n!$, the number of steps required grows linearly with $n$. Such a process is called a linear iterative process.
対照的に、2番目のプロセスは膨張も収縮もしません。任意の $n$ について、各ステップで追跡する必要があるのは、名前 product、counter、max_count の現在の値だけです。これを 反復的プロセスと呼びます。一般に、反復的プロセスとは、固定個数の 状態変数と、プロセスが状態から状態へ移るときに状態変数がどのように更新されるべきかを記述する固定のルール、そしてプロセスが終了すべき条件を規定する（省略可能な）終了テストによって、その状態を要約できるプロセスのことです。$n!$ の計算では、必要なステップ数は $n$ に対して線形に増加します。このようなプロセスを 線形反復的プロセスと呼びます。

The contrast between the two processes can be seen in another way. In the iterative case, the state variables provide a complete description of the state of the process at any point. If we stopped the computation between steps, all we would need to do to resume the computation is to supply the interpreter with the values of the three state variables. Not so with the recursive process. In this case there is some additional hidden information, maintained by the interpreter and not contained in the state variables, which indicates where the process is in negotiating the chain of deferred operations. The longer the chain, the more information must be maintained.
2つのプロセスの違いは別の見方もできます。反復的な場合、状態変数はプロセスの任意の時点の状態を完全に記述します。ステップの間で計算を止めたとしても、計算を再開するには3つの状態変数の値をインタプリタに与えるだけで済みます。再帰的プロセスではそうはいきません。この場合、状態変数には含まれず、インタプリタによって管理される追加の「隠された」情報があり、それが遅延された演算の連鎖のどこにプロセスがいるかを示しています。連鎖が長くなるほど、維持すべき情報も増えます。
[2]

In contrasting iteration and recursion, we must be careful not to confuse the notion of a recursive process with the notion of a recursive function. When we describe a function as recursive, we are referring to the syntactic fact that the function declaration refers (either directly or indirectly) to the function itself. But when we describe a process as following a pattern that is, say, linearly recursive, we are speaking about how the process evolves, not about the syntax of how a function is written. It may seem disturbing that we refer to a recursive function such as fact_iter as generating an iterative process. However, the process really is iterative: Its state is captured completely by its three state variables, and an interpreter need keep track of only three names in order to execute the process.
反復と再帰を対比するとき、再帰的プロセスの概念と再帰的 関数の概念を混同しないよう注意しなければなりません。関数を再帰的と言うとき、それは関数宣言が（直接的または間接的に）その関数自身を参照しているという構文上の事実を指しています。しかし、プロセスがたとえば線形再帰的なパターンに従うと言うとき、それはプロセスがどのように発展するかについて述べているのであって、関数がどう書かれているかという構文についてではありません。再帰的な関数である fact_iter が反復的プロセスを生成すると言うのは、違和感があるかもしれません。しかし、そのプロセスは本当に反復的です。その状態は3つの状態変数で完全に捉えられ、インタプリタはプロセスを実行するために3つの名前だけを追跡すればよいのです。

One reason that the distinction between process and function may be confusing is that most implementations of common languages (including C, Java, and Python) are designed in such a way that the interpretation of any recursive function consumes an amount of memory that grows with the number of function calls, even when the process described is, in principle, iterative. As a consequence, these languages can describe iterative processes only by resorting to special-purpose looping constructs such as $\texttt{do}$, $\texttt{repeat}$, $\texttt{until}$, $\texttt{for}$, and $\texttt{while}$. The implementation of JavaScript we shall consider in chapter 5 does not share this defect. It will execute an iterative process in constant space, even if the iterative process is described by a recursive function.
プロセスと関数の区別が混乱を招く理由の1つは、一般的な言語のほとんどの実装（C、Java、Python を含む）が、再帰的な関数の解釈において、記述されるプロセスが原理的には反復的であっても、関数呼び出しの回数に応じてメモリ消費量が増加するように設計されていることにあります。その結果、これらの言語では、反復的プロセスを記述するのに $\texttt{do}$、$\texttt{repeat}$、$\texttt{until}$、$\texttt{for}$、$\texttt{while}$ といった専用の「ループ構文」に頼るしかありません。chapter 5で扱う JavaScript の実装には、この欠点がありません。反復的プロセスが再帰的な関数で記述されていても、定数空間で実行します。
An implementation with this property is called tail-recursive.
このような性質を持つ実装を 末尾再帰的と呼びます。
[3]
With a tail-recursive implementation, iteration can be expressed using the ordinary function call mechanism, so that special iteration constructs are useful only as syntactic sugar.
末尾再帰的な実装があれば、 反復は通常の関数呼び出しの仕組みで表現でき、特別な反復構文は 糖衣構文としてのみ有用です。
[4]

Exercise 1.9
Each of the following two functions defines a method for adding two positive integers in terms of the functions inc, which increments its argument by 1, and dec, which decrements its argument by 1.
以下の2つの関数は、引数を 1 増やす inc と引数を 1 減らす dec を使って、2つの正の整数を加算する方法を定義しています。 
function plus(a, b) {
    return a === 0 ? b : inc(plus(dec(a), b)); 
}

function plus(a, b) {
    return a === 0 ? b : plus(dec(a), inc(b));
}
Using the substitution model, illustrate the process generated by each function in evaluating plus(4, 5);. Are these processes iterative or recursive?
置換モデルを使って、plus(4, 5); を評価するときに各関数が生成するプロセスを図示してください。これらのプロセスは反復的ですか、再帰的ですか。
The process generated by the first function is recursive.
最初の関数が生成するプロセスは再帰的です。

The process generated by the second function is iterative.

Tail recursion has long been known as a compiler optimization trick. A coherent semantic basis for tail recursion was provided by Carl Hewitt (1977), who explained it in terms of the message-passing model of computation that we shall discuss in chapter 3. Inspired by this, Gerald Jay Sussman and Guy Lewis Steele Jr. (see Steele 1975) constructed a tail-recursive interpreter for Scheme. Steele later showed how tail recursion is a consequence of the natural way to compile function calls (Steele 1977). The IEEE standard for Scheme requires that Scheme implementations be tail-recursive. The ECMA standard for JavaScript eventually followed suit with ECMAScript 2015 (ECMA 2015). Note, however, that as of this writing (2021), most implementations of JavaScript do not comply with this standard with respect to tail recursion.
末尾再帰は、コンパイラの最適化技法として古くから知られていました。末尾再帰の一貫した意味論的基盤は、 Carl Hewitt (1977) によって与えられ、chapter 3で議論する 「メッセージパッシング」計算モデルの観点から説明されました。これに触発されて、Gerald Jay Sussman と Guy Lewis Steele Jr.（Steele 1975 参照）は Scheme の末尾再帰インタプリタを構築しました。Steele は後に、末尾再帰が関数呼び出しをコンパイルする自然な方法の帰結であることを 示しました（Steele 1977）。Scheme の IEEE 標準は、Scheme の実装が 末尾再帰的であることを要求しています。JavaScript の ECMA 標準も最終的に ECMAScript 2015（ECMA 2015）でこれに続きました。ただし、この執筆時点（2021年）では、ほとんどの JavaScript 実装は末尾再帰に関してこの標準に準拠していません。
