4.4.3  
Is Logic Programming Mathematical Logic?
論理プログラミングは数学的論理学なのか？

The means of combination used in the query language may at first seem identical to the operations and, or, and not of mathematical logic, and the application of query-language rules is in fact accomplished through a legitimate method of inference.
クエリ言語で使われる結合の手段は、一見すると数学的論理学の演算 and、or、 not と同一に見えるかもしれません。そして実際、 クエリ言語のルール適用は正当な 推論の方法によって行われています。
[1]
This identification of the query language with mathematical logic is not really valid, though, because the query language provides a control structure that interprets the logical statements procedurally. We can often take advantage of this control structure. For example, to find all of the supervisors of programmers we could formulate a query in either of two logically equivalent forms:
しかし、クエリ言語を数学的論理学と同一視するのは実際には正しくありません。 なぜなら、クエリ言語は論理的文を手続き的に解釈する 制御構造を提供するからです。この制御構造を活用できることは よくあります。例えば、プログラマ全員の上司を見つけるために、 論理的に等価な2つの形式のいずれかでクエリを定式化できます：
and(job($x, list("computer", "programmer")),
    supervisor($x, $y))
or
あるいは
and(supervisor($x, $y),
    job($x, list("computer", "programmer")))
If a company has many more supervisors than programmers, it is better to use the first form rather than the second, because the data base must be scanned for each intermediate result (frame) produced by the first clause of the and.
もし会社に プログラマよりもはるかに多くの上司がいる場合、 2番目の形式よりも1番目の形式を使う方がよいでしょう。 なぜなら、and の最初の節が生成する中間結果（フレーム） ごとにデータベースをスキャンしなければならないからです。

The aim of logic programming is to provide the programmer with techniques for decomposing a computational problem into two separate problems: what is to be computed, and how this should be computed. This is accomplished by selecting a subset of the statements of mathematical logic that is powerful enough to be able to describe anything one might want to compute, yet weak enough to have a controllable procedural interpretation. The intention here is that, on the one hand, a program specified in a logic programming language should be an effective program that can be carried out by a computer. Control (how to compute) is effected by using the order of evaluation of the language. We should be able to arrange the order of clauses and the order of subgoals within each clause so that the computation is done in an order deemed to be effective and efficient. At the same time, we should be able to view the result of the computation (what to compute) as a simple consequence of the laws of logic.
論理プログラミングの目的は、計算問題を2つの別々の問題に分解する技法を プログラマに提供することです： 何を計算するかと、どのように 計算するかです。これは、数学的論理学の文のうち、 計算したいものは何でも記述できるほど強力でありながら、 制御可能な手続き的解釈を持てるほど弱い部分集合を選ぶことで達成されます。 ここでの意図は、一方で、論理プログラミング言語で記述されたプログラムが コンピュータで実行できる有効なプログラムであるべきだということです。 制御（どのように計算するか）は言語の評価順序を使って実現されます。 節の順序と各節内のサブゴールの順序を適切に配置して、 効果的かつ効率的な順序で計算が行われるようにできるべきです。 同時に、計算結果（何を計算するか）を 論理法則の単なる帰結として見ることもできるべきです。

Our query language can be regarded as just such a procedurally interpretable subset of mathematical logic. An assertion represents a simple fact (an atomic proposition). A rule represents the implication that the rule conclusion holds for those cases where the rule body holds. A rule has a natural procedural interpretation: To establish the conclusion of the rule, establish the body of the rule. Rules, therefore, specify computations. However, because rules can also be regarded as statements of mathematical logic, we can justify any inference accomplished by a logic program by asserting that the same result could be obtained by working entirely within mathematical logic.
私たちのクエリ言語は、まさにそのような手続き的に解釈可能な 数学的論理学の部分集合と見なすことができます。アサーションは 単純な事実（原子命題）を表します。ルールは、ルール本体が成り立つ場合に ルールの結論が成り立つという含意を表します。ルールには自然な手続き的解釈があります： ルールの結論を確立するには、ルールの本体を確立します。 したがって、ルールは計算を指定します。しかし、ルールは 数学的論理学の文とも見なせるので、論理プログラムによって達成される あらゆる推論は、数学的論理学の中だけで作業しても 同じ結果が得られると主張することで正当化できます。
[2]

Infinite loops
無限ループ

A consequence of the procedural interpretation of logic programs is that it is possible to construct hopelessly inefficient programs for solving certain problems. An extreme case of inefficiency occurs when the system falls into infinite loops in making deductions. As a simple example, suppose we are setting up a data base of famous marriages, including
論理プログラムの手続き的解釈の帰結として、 特定の問題を解くために絶望的に非効率なプログラムを構築してしまう可能性があります。 非効率性の極端な例は、推論中にシステムが無限ループに陥る場合です。 簡単な例として、有名な結婚のデータベースを構築しているとしましょう。 次のようなデータが含まれています：
assert(married("Minnie", "Mickey"))
If we now ask
ここで次のように問い合わせると
married("Mickey", $who)
we will get no response, because the system doesn't know that if $A$ is married to $B$, then $B$ is married to $A$. So we assert the rule
応答は得られません。システムは、$A$ が $B$ と結婚しているなら $B$ は $A$ と 結婚しているということを知らないからです。そこで次のルールをアサートします：
assert(rule(married($x, $y), 
            married($y, $x)))
and again query
そして再び次のように問い合わせます：
married("Mickey", $who)
Unfortunately, this will drive the system into an infinite loop, as follows:
  • The system finds that the married rule is applicable; that is, the rule conclusion married($x, $y) unifies with the query pattern married("Mickey", $who) to produce a frame in which $x is bound to "Mickey" and $y is bound to $who. So the interpreter proceeds to evaluate the rule body married($y, $x) in this frame—in effect, to process the query married($who, "Mickey").
  • One answer, married("Minnie", "Mickey"), appears directly as an assertion in the data base.
  • The married rule is also applicable, so the interpreter again evaluates the rule body, which this time is equivalent to married("Mickey", $who).
残念ながら、これによりシステムは次のような無限ループに陥ります：
  • システムは married ルールが適用可能であることを見つけます。 つまり、ルールの結論 married($x, $y) が クエリパターン married("Mickey", $who) と ユニファイされ、 $x が "Mickey" に束縛され、 $y が $who に束縛されるフレームが生成されます。 そしてインタプリタはこのフレームでルール本体 married($y, $x) の評価に進みます—事実上、クエリ married($who, "Mickey") を処理することになります。
  • 一つの答え married("Minnie", "Mickey") がデータベースにアサーションとして直接見つかります。
  • married ルールも適用可能なので、 インタプリタは再びルール本体を評価します。今度は married("Mickey", $who) と等価になります。
The system is now in an infinite loop. Indeed, whether the system will find the simple answer married("Minnie", "Mickey") before it goes into the loop depends on implementation details concerning the order in which the system checks the items in the data base. This is a very simple example of the kinds of loops that can occur. Collections of interrelated rules can lead to loops that are much harder to anticipate, and the appearance of a loop can depend on the order of clauses in an and (see exercise 4.62) or on low-level details concerning the order in which the system processes queries.
これでシステムは無限ループに陥ります。実際、ループに入る前にシステムが 単純な答え married("Minnie", "Mickey") を見つけるかどうかは、システムがデータベース内の項目をチェックする順序に関する 実装の詳細に依存します。これは発生しうるループの非常に単純な例です。 相互に関連するルールの集まりは、予測がはるかに困難なループにつながる可能性があり、 ループの発生は and 内の節の順序 （練習問題 4.62 を参照）や、 システムがクエリを処理する順序に関する低レベルの詳細に依存することがあります。
[3]

Problems with not
not の問題点

Another quirk in the query system concerns not. Given the data base of section 4.4.1, consider the following two queries:
クエリシステムのもう一つの問題点は not に関するものです。 4.4.1 節のデータベースが与えられているとして、 次の2つのクエリを考えてみましょう：
and(supervisor($x, $y),
    not(job($x, list("computer", "programmer"))))

and(not(job($x, list("computer", "programmer"))),
    supervisor($x, $y))
These two queries do not produce the same result. The first query begins by finding all entries in the data base that match supervisor($x, $y), and then filters the resulting frames by removing the ones in which the value of $x satisfies job($x,list("computer", "programmer")). The second query begins by filtering the incoming frames to remove those that can satisfy job($x, list("computer","programmer")). Since the only incoming frame is empty, it checks the data base for patterns that satisfy job($x, list("computer", "programmer")). Since there generally are entries of this form, the not clause filters out the empty frame and returns an empty stream of frames. Consequently, the entire compound query returns an empty stream.
この2つのクエリは同じ結果を生成しません。最初のクエリは、 データベース内で supervisor($x, $y) に一致するすべてのエントリを見つけることから始め、 次に $x の値が job($x,list("computer", "programmer")) を満たすフレームを取り除くことで結果のフレームをフィルタリングします。 2番目のクエリは、入力フレームのうち job($x, list("computer","programmer")) を満たすものを取り除くフィルタリングから始めます。 入力フレームは空のフレームだけなので、データベースで job($x, list("computer", "programmer")) を満たすパターンがあるかどうかをチェックします。 一般にこの形式のエントリは存在するので、not 節は 空のフレームをフィルタリングで除外し、空のフレームストリームを返します。 その結果、複合クエリ全体が空のストリームを返します。

The trouble is that our implementation of not really is meant to serve as a filter on values for the variables. If a not clause is processed with a frame in which some of the variables remain unbound (as does $x in the example above), the system will produce unexpected results. Similar problems occur with the use of javascript_predicate—the JavaScript predicate can't work if some of its variables are unbound. See exercise 4.74.
問題は、not の実装が本来、 変数の値に対するフィルタとして機能することを意図している点です。 not 節が、一部の変数がまだ未束縛のままの フレームで処理されると（上の例の $x のように）、システムは予期しない結果を生成します。同様の問題は javascript_predicate の使用でも発生します— JavaScript の述語は変数の一部が未束縛だと機能しません。 練習問題 4.74 を参照してください。

There is also a much more serious way in which the not of the query language differs from the not of mathematical logic. In logic, we interpret the statement not $P$ to mean that $P$ is not true. In the query system, however, not $P$ means that $P$ is not deducible from the knowledge in the data base. For example, given the personnel data base of section 4.4.1, the system would happily deduce all sorts of not statements, such as that Ben Bitdiddle is not a baseball fan, that it is not raining outside, and that $2 + 2$ is not 4.
クエリ言語の not が 数学的論理学の not と異なる、さらに深刻な点もあります。 論理学では、not $P$ という文は $P$ が真ではないことを意味すると解釈します。 しかしクエリシステムでは、not $P$ は $P$ がデータベース内の知識からは演繹できないことを意味します。 例えば、4.4.1 節の人事データベースが与えられると、 システムは Ben Bitdiddle は野球ファンではない、外は雨が降っていない、 $2 + 2$ は 4 ではない、 といったあらゆる種類の not 文を喜んで演繹してしまいます。
[4]
In other words, the not of logic programming languages reflects the so-called closed world assumption that all relevant information has been included in the data base.
つまり、論理プログラミング言語の not は、 すべての関連情報がデータベースに含まれているという、いわゆる 閉世界仮定を反映しています。
[5]

Exercise 4.67

  1. Change the assertions in the data base such that there is only one kind of relationship information, namely related. The first item then describes the relationship.   2. Write rules that determine if a list ends in the word "grandson".
  3. Use this to express a rule that allows one to derive the relationship 
    list(pair("great", $rel), $x, $y)

We must qualify this statement by agreeing that, in speaking of the inference accomplished by a logic program, we assume that the computation terminates. Unfortunately, even this qualified statement is false for our implementation of the query language (and also false for programs in Prolog and most other current logic programming languages) because of our use of not and javascript_predicate. As we will describe below, the not implemented in the query language is not always consistent with the not of mathematical logic, and javascript_predicate introduces additional complications. We could implement a language consistent with mathematical logic by simply removing not and javascript_predicate from the language and agreeing to write programs using only simple queries, and, and or. However, this would greatly restrict the expressive power of the language. One of the major concerns of research in logic programming was to find ways to achieve more consistency with mathematical logic without unduly sacrificing expressive power.

This is not a problem of the logic but one of the procedural interpretation of the logic provided by our interpreter. We could write an interpreter that would not fall into a loop here. For example, we could enumerate all the proofs derivable from our assertions and our rules in a breadth-first rather than a depth-first order. However, such a system makes it more difficult to take advantage of the order of deductions in our programs.
