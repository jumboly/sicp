5.5.6  
Lexical Addressing
レキシカルアドレッシング

One of the most common optimizations performed by compilers is the optimization of name lookup. Our compiler, as we have implemented it so far, generates code that uses the lookup_symbol_value operation of the evaluator machine. This searches for a name by comparing it with each name that is currently bound, working frame by frame outward through the runtime environment. This search can be expensive if the frames are deeply nested or if there are many names. For example, consider the problem of looking up the value of x while evaluating the expression x * y * z in an application of the function of five arguments that is returned by
コンパイラが行う最も一般的な最適化の1つは、 名前 の検索の最適化です。これまでに実装した私たちのコンパイラは、評価器マシンの lookup_symbol_value 演算を使うコードを生成します。この演算は、現在束縛されている各 名前 と比較しながら、実行時環境の中をフレームごとに外側に向かって検索します。フレームが深くネストしていたり、多数の 名前 がある場合、この検索はコストが高くなる可能性があります。たとえば、次の式から返される 5引数の関数 の適用において、式 x * y * z を評価する際に x の値を検索する問題を考えてみましょう。 
((x, y) =>
   (a, b, c, d, e) =>
     ((y, z) => x * y * z)(a * b * x, c + d + x))(3, 4)
Each time lookup_symbol_value searches for x, it must determine that the symbol "x" is not equal to "y" or "z" (in the first frame), nor to "a", "b", "c", "d", or "e" (in the second frame). Because our language is lexically scoped, the runtime environment for any component will have a structure that parallels the lexical structure of the program in which the component appears. Thus, the compiler can know, when it analyzes the above expression, that each time the function is applied the binding for x in x * y * z will be found two frames out from the current frame and will be the first binding in that frame.
lookup_symbol_value が x を検索するたびに、シンボル "x" が "y" や "z"（最初のフレーム内）と等しくなく、 "a"、 "b"、 "c"、 "d"、 "e"（2番目のフレーム内）とも等しくないことを判定しなければなりません。 私たちの言語は レキシカルスコープなので、任意の コンポーネント の実行時環境は、その コンポーネント が現れるプログラムのレキシカル構造と並行する構造を持ちます。 したがって、コンパイラは上の式を解析する際に、 関数 が適用されるたびに、 x * y * z における x の束縛 が、現在のフレームから2つ外側のフレームにあり、そのフレームの最初の 束縛 であることがわかります。

We can exploit this fact by inventing a new kind of name-lookup operation, lexical_address_lookup, that takes as arguments an environment and a lexical address that consists of two numbers: a frame number, which specifies how many frames to pass over, and a displacement number, which specifies how many bindings to pass over in that frame. The operation lexical_address_lookup will produce the value of the name stored at that lexical address relative to the current environment. If we add the lexical_address_lookup operation to our machine, we can make the compiler generate code that references names using this operation, rather than lookup_symbol_value. Similarly, our compiled code can use a new lexical_address_assign operation instead of assign_symbol_value. With lexical addressing, there is no need to include any symbolic references to names in the object code, and frames do not need to include symbols at run time.
この事実を利用するために、新しい種類の 名前検索 演算 lexical_address_lookup を考案できます。この演算は環境と レキシカルアドレスを引数として受け取ります。レキシカルアドレスは2つの数で構成されます。フレーム番号は何個のフレームを飛ばすかを指定し、変位番号はそのフレーム内で何個の 束縛 を飛ばすかを指定します。 lexical_address_lookup 演算 は、現在の環境からの相対的なレキシカルアドレスに格納されている 名前 の値を返します。 lexical_address_lookup 演算をマシンに追加すれば、コンパイラに lookup_symbol_value の代わりにこの演算を使って 名前 を参照するコードを生成させることができます。同様に、コンパイル済みコードは assign_symbol_value の代わりに、新しい lexical_address_assign 演算を使えます。 レキシカルアドレッシングを使えば、オブジェクトコードに名前へのシンボル的な参照を含める必要がなくなり、フレームも実行時にシンボルを含む必要がなくなります。

In order to generate such code, the compiler must be able to determine the lexical address of a name it is about to compile a reference to. The lexical address of a name in a program depends on where one is in the code. For example, in the following program, the address of x in expression $e_1$ is (2,0)—two frames back and the first name in the frame. At that point y is at address (0,0) and c is at address (1,2). In expression $e_2$, x is at (1,0), y is at (1,1), and c is at (0,2).
このようなコードを生成するために、コンパイラは参照をコンパイルしようとしている 名前 のレキシカルアドレスを決定できなければなりません。プログラム中の 名前 のレキシカルアドレスは、コード中のどこにいるかによって変わります。たとえば、以下のプログラムでは、式 $e_1$ における x のアドレスは (2,0) です—2つ前のフレームの最初の 名前 です。その位置では y はアドレス (0,0) にあり、c はアドレス (1,2) にあります。 式 $e_2$ では、 x は (1,0)、 y は (1,1)、 c は (0,2) にあります。
((x, y) => (a, b, c, d, e) => ((y, z) => $e_1$)($e_2$, c + d + x))(3, 4);

One way for the compiler to produce code that uses lexical addressing is to maintain a data structure called a compile-time environment. This keeps track of which bindings will be at which positions in which frames in the runtime environment when a particular name-access operation is executed. The compile-time environment is a list of frames, each containing a list of symbols. There will be no values associated with the symbols, since values are not computed at compile time. (Exercise 5.46 will change this, as an optimization for constants.) The compile-time environment becomes an additional argument to compile and is passed along to each code generator. The top-level call to compile uses a compile-time-environment that includes the names of all primitive functions and primitive values. When the body of a lambda expression is compiled, compile_lambda_body extends the compile-time environment by a frame containing the function's parameters, so that the body is compiled with that extended environment. Similarly, when the body of a block is compiled, compile_block extends the compile-time environment by a frame containing the scanned-out local names of the body. At each point in the compilation, compile_name and compile_assignment_declaration use the compile-time environment in order to generate the appropriate lexical addresses.
コンパイラがレキシカルアドレッシングを使うコードを生成する方法の1つは、 コンパイル時環境と呼ばれるデータ構造を維持することです。これは、特定の 名前アクセス 演算が実行される際に、実行時環境のどのフレームのどの位置にどの 束縛 があるかを追跡します。コンパイル時環境はフレームのリストで、各フレームは シンボル のリストを含みます。 コンパイル時には値は計算されないので、シンボルに関連付けられた値はありません。 （練習問題 5.46では、定数の最適化としてこれを変更します。） コンパイル時環境は compile への追加の引数となり、各コード生成器に引き渡されます。compile のトップレベル呼び出しでは、 すべてのプリミティブ関数とプリミティブな値の名前を含むコンパイル時環境を使います。 ラムダ式の本体 がコンパイルされる際、 compile_lambda_body は 関数 のパラメータを含むフレームでコンパイル時環境を拡張し、 本体がその拡張された環境でコンパイルされるようにします。 同様に、ブロックの本体がコンパイルされる際、 compile_block は本体の スキャンアウトされたローカル名を含むフレームでコンパイル時環境を拡張します。 コンパイルの各時点で、 compile_name と compile_assignment_declaration は、適切なレキシカルアドレスを生成するためにコンパイル時環境を使います。

Exercises 5.41 through 5.44 describe how to complete this sketch of the lexical-addressing strategy in order to incorporate lexical lookup into the compiler. Exercises 5.45 and 5.46 describe other uses for the compile-time environment.
練習問題 5.41から 5.44では、レキシカルアドレッシング戦略のこのスケッチを完成させ、レキシカル検索をコンパイラに組み込む方法を説明します。 練習問題 5.45と 5.46では、コンパイル時環境の別の用途を説明します。

Exercise 5.45
In JavaScript, an attempt to assign a new value to a name that is declared as a constant leads to an error. Exercise 4.11 shows how to detect such errors at run time. With the techniques presented in this section, we can detect attempts to assign a new value to a constant at compile time. Exercise 5.46
Knowledge about constants at compile time opens the door to many optimizations that allow us to generate more efficient object code. In addition to the extension of the compile-time environment in exercise 5.45 to indicate names declared as constants, we may store the value of a constant if it is known at compile time, or other information that can help us optimize the code.
  1. A constant declaration such as const $name$ = $literal$; allows us to replace all occurrences of $name$ within the scope of the declaration by $literal$ so that $name$ doesn't have to be looked up in the runtime environment. This optimization is called constant propagation. Use an extended compile-time environment to store literal constants, and modify compile_name to use the stored constant in the generated assign instruction instead of the lookup_symbol_value operation.
  2. Function declaration is a derived component that expands to constant declaration. Let us assume that the names of primitive functions in the global environment are also considered constants. If we further extend our compile-time environment to keep track of which names refer to compiled functions and which ones to primitive functions, we can move the test that checks whether a function is compiled or primitive from run time to compile time. This makes the object code more efficient because it replaces a test that must be performed once per function application in the generated code by one that is performed by the compiler. Using such an extended compile-time environment, modify compile_function_call so that if it can be determined at compile time whether the called function is compiled or primitive, only the instructions in the compiled_branch or the primitive_branch are generated.
  3. Replacing constant names with their literal values as in part (a) paves the way for another optimization, namely replacing applications of primitive functions to literal values with the compile-time computed result. This optimization, called constant folding, replaces expressions such as 40 + 2 by 42 by performing the addition in the compiler. Extend the compiler to perform constant folding for arithmetic operations on numbers and for string concatenation.
コンパイル時に定数についての知識があると、より効率的なオブジェクトコードを生成できる多くの最適化への道が開けます。練習問題 5.45で定数として宣言された名前を示すように コンパイル時環境を拡張したのに加えて、コンパイル時にわかっている定数の値や、コードの最適化に役立つ他の情報を格納することもできます。
  1. const $name$ = $literal$; のような定数宣言があると、宣言のスコープ内の $name$ のすべての出現を $literal$ で置き換えることができ、$name$ を実行時環境で検索する必要がなくなります。この最適化は定数伝播と呼ばれます。拡張されたコンパイル時環境を使ってリテラル定数を格納し、 compile_name を変更して、生成される assign 命令で lookup_symbol_value 演算の代わりに格納された定数を使うようにしてください。
  2. 関数宣言は定数宣言に展開される派生コンポーネントです。グローバル環境にあるプリミティブ関数の名前も定数と見なすことにしましょう。 どの名前がコンパイル済み関数を参照し、どの名前がプリミティブ関数を参照するかを追跡するようにコンパイル時環境をさらに拡張すれば、関数がコンパイル済みかプリミティブかを判定するテストを実行時からコンパイル時に移すことができます。これにより、生成されたコードで関数適用ごとに1回実行しなければならないテストをコンパイラが実行するものに置き換えられるため、オブジェクトコードが効率的になります。このような拡張されたコンパイル時環境を使って、 compile_function_call を変更し、呼び出される関数がコンパイル済みかプリミティブかをコンパイル時に判定できる場合、 compiled_branch または primitive_branch の命令のみを生成するようにしてください。
  3. (a) のように定数名をリテラル値で置き換えると、別の最適化への道が開けます。すなわち、リテラル値へのプリミティブ関数の適用をコンパイル時に計算した結果で置き換えることです。この最適化は定数畳み込みと呼ばれ、コンパイラ内で加算を実行することにより 40 + 2 のような式を 42 で置き換えます。数値に対する算術演算と文字列の連結について定数畳み込みを実行するようにコンパイラを拡張してください。
