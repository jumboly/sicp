4.1.5  
Data as Programs
プログラムとしてのデータ

In thinking about a JavaScript program that evaluates JavaScript statements and expressions, an analogy might be helpful. One operational view of the meaning of a program is that a program is a description of an abstract (perhaps infinitely large) machine. For example, consider the familiar program to compute factorials:
JavaScript の JavaScript の文と 式を評価するプログラムについて考えるとき、一つのアナロジーが役に立つかもしれません。プログラムの意味に関する一つの操作的な見方は、 プログラムとは抽象的な（おそらく無限に大きな）機械の記述であるというものです。例えば、おなじみの階乗を計算するプログラムを考えてみましょう。 
function factorial(n) {
    return n === 1
           ? 1
           : factorial(n - 1) * n;
}
We may regard this program as the description of a machine containing parts that decrement, multiply, and test for equality, together with a two-position switch and another factorial machine. (The factorial machine is infinite because it contains another factorial machine within it.) Figure 4.4 is a flow diagram for the factorial machine, showing how the parts are wired together.
このプログラムは、デクリメント、乗算、等値テストを行う部品と、2つの位置を持つスイッチ、そしてもう一つの階乗機械を含む 機械の記述と見なすことができます。（階乗機械は、その内部にさらに別の階乗機械を含んでいるため、無限です。）図 4.4は階乗機械のフロー図で、各部品がどのように接続されているかを示しています。

In a similar way, we can regard the evaluator as a very special machine that takes as input a description of a machine. Given this input, the evaluator configures itself to emulate the machine described. For example, if we feed our evaluator the definition of factorial, as shown in figure 4.6, the evaluator will be able to compute factorials.
同様に、評価器は機械の記述を入力として受け取る非常に特殊な 機械と見なすことができます。この入力を受け取ると、評価器は記述された機械をエミュレートするように自身を構成します。例えば、 図 4.6に 示すように、評価器にfactorialの定義を与えると、評価器は階乗を計算できるようになります。

From this perspective, our evaluator is seen to be a universal machine. It mimics other machines when these are described as JavaScript programs.
この観点から見ると、私たちの評価器は 万能機械（universal machine）であることがわかります。 それは、他の機械が JavaScript のプログラムとして記述されたとき、それらの機械を模倣します。
[1]
This is striking. Try to imagine an analogous evaluator for electrical circuits. This would be a circuit that takes as input a signal encoding the plans for some other circuit, such as a filter. Given this input, the circuit evaluator would then behave like a filter with the same description. Such a universal electrical circuit is almost unimaginably complex. It is remarkable that the program evaluator is a rather simple program.
これは驚くべきことです。電気回路に対する同様の評価器を想像してみてください。それは、フィルタのような別の回路の設計図を符号化した信号を入力として受け取る回路でしょう。この入力が与えられると、その回路評価器はその記述と同じフィルタのように振る舞います。このような万能電気回路はほとんど想像できないほど複雑です。プログラム評価器がかなり単純なプログラムであるということは注目に値します。
[2]

Another striking aspect of the evaluator is that it acts as a bridge between the data objects that are manipulated by our programming language and the programming language itself. Imagine that the evaluator program (implemented in JavaScript) is running, and that a user is typing programs to the evaluator and observing the results. From the perspective of the user, an input program such as x * x; is a program in the programming language, which the evaluator should execute. From the perspective of the evaluator, however, the program is simply a string or—after parsing—a tagged-list representation that is to be manipulated according to a well-defined set of rules.
評価器のもう一つの注目すべき側面は、プログラミング言語によって操作されるデータオブジェクトとプログラミング言語そのものとの橋渡しをすることです。評価器プログラム （JavaScript で実装されたもの） が実行されていて、ユーザーが評価器に プログラム を入力して結果を観察しているところを想像してください。ユーザーの視点からすると、 x * x; のような入力 プログラム は、評価器が実行すべきプログラミング言語の プログラム です。 しかし評価器の視点からすると、そのプログラムは単なる文字列、あるいは—パース（構文解析）の後は—明確に定義された一連の規則に従って操作されるべきタグ付きリスト表現にすぎません。

That the user's programs are the evaluator's data need not be a source of confusion. In fact, it is sometimes convenient to ignore this distinction, and to give the user the ability to explicitly evaluate a string as a JavaScript statement, using JavaScript's primitive function eval that takes as argument a string. It parses the string and—provided that it is syntactically correct—evaluates the resulting representation in the environment in which eval is applied. Thus,
ユーザーのプログラムが評価器のデータであるということは、混乱の元になる必要はありません。実際、この区別を無視して、ユーザーに文字列を JavaScript の文として明示的に評価する機能を与えることが便利な場合があります。JavaScript のプリミティブ関数evalは文字列を引数として受け取り、その文字列をパースし—構文的に正しければ—結果の表現をevalが適用された環境で評価します。したがって、 
eval("5 * 5;");
and
と
evaluate(parse("5 * 5;"), the_global_environment);
will both return 25.
はどちらも 25 を返します。
[3]

Exercise 4.15
Given a one-argument function f and an object a, f is said to halt on a if evaluating the expression f(a) returns a value (as opposed to terminating with an error message or running forever). Show that it is impossible to write a function halts that correctly determines whether f halts on a for any function f and object a. Use the following reasoning: If you had such a function halts, you could implement the following program:
1引数の 関数 f とオブジェクトaが与えられたとき、式 f(a) を評価して値が返される場合（エラーメッセージで終了したり永久に実行し続けたりするのではなく）、 f はaに対して停止する（halt）と言います。 任意の 関数 f とオブジェクトaに対して、 f がaに対して停止するかどうかを正しく判定する 関数 halts を書くことが不可能であることを示してください。次の推論を使います。もしそのような 関数 halts があれば、次のプログラムを実装できるでしょう。 
function run_forever() { return run_forever(); }

function strange(f) {
    return halts(f, f)
           ? run_forever()
           : "halted";
}
Now consider evaluating the expression strange(strange) and show that any possible outcome (either halting or running forever) violates the intended behavior of halts.
ここで、式 strange(strange) を評価することを考え、あり得る結果（停止するか永久に実行し続けるか）のどちらも haltsの意図された振る舞いに矛盾することを示してください。
[4]
There is currently no solution available for this exercise. This textbook adaptation is a community effort. Do consider contributing by providing a solution for this exercise, using a Pull Request in Github.
[1]
The fact that the machines are described in JavaScript is inessential. If we give our evaluator a JavaScript program that behaves as an evaluator for some other language, say C, the JavaScript evaluator will emulate the C evaluator, which in turn can emulate any machine described as a C program. Similarly, writing a JavaScript evaluator in C produces a C program that can execute any JavaScript program. The deep idea here is that any evaluator can emulate any other. Thus, the notion of what can in principle be computed (ignoring practicalities of time and memory required) is independent of the language or the computer, and instead reflects an underlying notion of computability. This was first demonstrated in a clear way by Alan M. Turing (1912–1954), whose 1936 paper laid the foundations for theoretical computer science. In the paper, Turing presented a simple computational model—now known as a Turing machine—and argued that any effective process can be formulated as a program for such a machine. (This argument is known as the Church–Turing thesis.) Turing then implemented a universal machine, i.e., a Turing machine that behaves as an evaluator for Turing-machine programs. He used this framework to demonstrate that there are well-posed problems that cannot be computed by Turing machines (see exercise 4.15), and so by implication cannot be formulated as effective processes. Turing went on to make fundamental contributions to practical computer science as well. For example, he invented the idea of structuring programs using general-purpose subroutines. See Hodges 1983 for a biography of Turing.
機械が JavaScript で記述されているという事実は本質的ではありません。もし評価器に、他の言語、例えば C の評価器として振る舞う JavaScript プログラムを与えれば、 JavaScript の評価器は C の評価器をエミュレートし、その C の評価器はさらに C プログラムとして記述された任意の機械をエミュレートできます。同様に、C で JavaScript の評価器を書けば、任意の JavaScript プログラムを実行できる C プログラムが得られます。ここでの深い考えは、どんな評価器でも他のどんな評価器でもエミュレートできるということです。したがって、原理的に何が計算できるかという概念は（必要な時間とメモリの実際的な問題を無視すれば）言語やコンピュータに依存せず、 計算可能性（computability）という根底にある概念を反映しています。これを最初に明確に示したのは、 アラン・M・チューリング（1912–1954）で、彼の1936年の論文は理論 計算機科学の基礎を築きました。その論文でチューリングは、単純な計算モデル—現在 チューリングマシンとして知られているもの—を提示し、あらゆる有効な手順（effective process）はそのような機械のプログラムとして定式化できると主張しました。（この主張は チャーチ＝チューリングのテーゼとして知られています。）チューリングはその後、万能機械、すなわちチューリングマシンのプログラムに対する評価器として振る舞うチューリングマシンを実装しました。彼はこの枠組みを使って、チューリングマシンでは計算できない明確に定義された問題が存在することを証明し（練習問題 4.15を参照）、したがってそれらは有効な手順として定式化できないことを示しました。チューリングはその後、実用的な計算機科学にも根本的な貢献をしました。例えば、汎用サブルーチンを使って プログラムを構造化するというアイデアを発明しました。チューリングの伝記については Hodges 1983を参照してください。
[2]
Some people find it counterintuitive that an evaluator, which is implemented by a relatively simple function, can emulate programs that are more complex than the evaluator itself. The existence of a universal evaluator machine is a deep and wonderful property of computation. Recursion theory, a branch of mathematical logic, is concerned with logical limits of computation. Douglas Hofstadter's beautiful book Gödel, Escher, Bach (1979) explores some of these ideas.
比較的単純な 関数で 実装された評価器が、評価器自体よりも複雑なプログラムをエミュレートできるということを直感に反すると感じる人もいます。万能評価器機械の存在は、計算の深く素晴らしい性質です。 再帰理論（Recursion theory）は数理論理学の一分野で、計算の論理的限界を扱います。 ダグラス・ホフスタッターの美しい書籍Gödel, Escher, Bach（1979）は、これらの考えの一部を探求しています。
[3]
Note that eval may not be available in the JavaScript environment that you are using, or its use may be restricted for security reasons.
evalは、お使いの JavaScript 環境では利用できない場合や、セキュリティ上の理由で使用が制限されている場合があります。
[4]
Although we stipulated that halts is given a function object, notice that this reasoning still applies even if halts can gain access to the function's text and its environment. This is Turing's celebrated Halting Theorem, which gave the first clear example of a noncomputable problem, i.e., a well-posed task that cannot be carried out as a computational function.
halts には 関数 オブジェクトが与えられると規定しましたが、たとえ halts が 関数の テキストとその環境にアクセスできたとしても、この推論は依然として成り立つことに注意してください。 これはチューリングの有名な 停止定理（Halting Theorem）であり、 計算不可能（noncomputable）な問題、すなわち計算的な 関数として 遂行できない明確に定義された課題の最初の明確な例を示しました。
