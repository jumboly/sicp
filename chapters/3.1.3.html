3.1.3  
The Costs of Introducing Assignment
代入を導入するコスト

As we have seen, assignment enables us to model objects that have local state. However, this advantage comes at a price. Our programming language can no longer be interpreted in terms of the substitution model of function application that we introduced in section 1.1.5. Moreover, no simple model with nice mathematical properties can be an adequate framework for dealing with objects and assignment in programming languages.
これまで見てきたように、 代入 を使うことで、ローカル状態を持つオブジェクトをモデル化できるようになります。しかし、この利点には代償があります。私たちのプログラミング言語は、1.1.5 節で導入した 関数 適用の置換モデルでは解釈できなくなります。さらに、良い数学的性質を持つ単純なモデルでは、プログラミング言語におけるオブジェクトと代入を扱うための適切な枠組みにはなりません。

So long as we do not use assignments, two evaluations of the same function with the same arguments will produce the same result, so that functions can be viewed as computing mathematical functions. Programming without any use of assignments, as we did throughout the first two chapters of this book, is accordingly known as functional programming.
代入を使わない限り、同じ 関数 を同じ引数で2回評価すれば同じ結果が得られるので、 関数 は数学的関数を計算するものと見なすことができます。本書の最初の2章で行ったように、代入を一切使わないプログラミングは、 関数型プログラミングとして知られています。

To understand how assignment complicates matters, consider a simplified version of the make_withdraw function of section 3.1.1 that does not bother to check for an insufficient amount:
代入がどのように物事を複雑にするかを理解するために、3.1.1 節の make_withdraw 関数 の簡略版で、残高不足のチェックを省いたものを考えてみましょう： 
function make_simplified_withdraw(balance) {
    return amount => {
               balance = balance - amount;
               return balance;
           };
}

const W = make_simplified_withdraw(25);

W(20);

5
W(10);

-5
Compare this function with the following make_decrementer function, which does not use assignment:
この 関数 を、 代入 を使わない次の make_decrementer 関数 と比較してみましょう： 
function make_decrementer(balance) {
    return amount => balance - amount;
}
The function make_decrementer returns a function that subtracts its input from a designated amount balance, but there is no accumulated effect over successive calls, as with make_simplified_withdraw:
関数 make_decrementer は、指定された金額 balance から入力を引いた値を返す 関数 ですが、make_simplified_withdraw とは異なり、連続した呼び出しにわたる累積的な効果はありません： 
const D = make_decrementer(25);

D(20);

5
D(10);

15
We can use the substitution model to explain how make_decrementer works. For instance, let us analyze the evaluation of the expression
置換モデルを使って make_decrementer の動作を説明できます。例えば、次の式の評価を分析してみましょう。 
make_decrementer(25)(20)
We first simplify the function expression of the application by substituting $25$ for balance in the body of make_decrementer. This reduces the expression to
まず、 適用の関数式 を簡約するために、 make_decrementer の本体中の balance に $25$ を置換します。これにより式は次のように簡約されます。 
(amount => 25 - amount)(20)
Now we apply the function by substituting 20 for amount in the body of the lambda expression:
次に、 ラムダ 式の本体中の amount に 20 を置換して 関数 を適用します： 
25 - 20
The final answer is 5.
最終的な答えは 5 です。

Observe, however, what happens if we attempt a similar substitution analysis with make_simplified_withdraw:
しかし、make_simplified_withdraw に対して同様の置換分析を試みるとどうなるか見てみましょう： 
make_simplified_withdraw(25)(20)
We first simplify the function expression by substituting 25 for balance in the body of make_simplified_withdraw. This reduces the expression to
まず、make_simplified_withdraw の 本体中の balance に 25 を置換して、 関数式 を簡約します。これにより 式 は次のように簡約されます。
[1] 
(amount => {
     balance = 25 - amount; 
     return 25;
 })(20)
Now we apply the function by substituting 20 for amount in the body of the lambda expression:
次に、 ラムダ式 の本体中の amount に 20 を置換して 関数 を適用します： 
balance = 25 - 20;
return 25;
If we adhered to the substitution model, we would have to say that the meaning of the function application is to first set balance to 5 and then return 25 as the value of the expression. This gets the wrong answer. In order to get the correct answer, we would have to somehow distinguish the first occurrence of balance (before the effect of the assignment) from the second occurrence of balance (after the effect of the assignment), and the substitution model cannot do this.
置換モデルに従うと、この 関数 適用の意味は、まず balance を 5 に設定し、次に式の値として 25 を返すということになります。これは間違った答えです。正しい答えを得るには、 代入の効果が及ぶ前の balance の最初の出現と、 代入 の効果が及んだ後の balance の2番目の出現を何らかの方法で区別しなければなりませんが、置換モデルではそれができません。

The trouble here is that substitution is based ultimately on the notion that the name in our language are essentially symbols for values.
ここでの問題は、置換が最終的に、 言語中の名前は本質的に値を表すシンボルである という考えに基づいているということです。
This worked well for constants. But a variable, whose value can change with assignment, cannot simply be a name for a value. A variable somehow refers to a place where a value can be stored, and the value stored at this place can change.
これは定数に対してはうまく機能しました。しかし、代入によって値が変わりうる変数は、単に値の名前であるとは言えません。変数はどういうわけか、値を格納できる場所を指し示しており、その場所に格納されている値は変化しうるのです。
In section 3.2 we will see how environments play this role of place in our computational model.
3.2 節では、私たちの計算モデルにおいて環境がこの場所の役割をどのように果たすかを見ていきます。

Sameness and change
同一性と変化

The issue surfacing here is more profound than the mere breakdown of a particular model of computation. As soon as we introduce change into our computational models, many notions that were previously straightforward become problematical. Consider the concept of two things being the same.
ここで浮上している問題は、特定の計算モデルが破綻するという以上に深遠なものです。計算モデルに変化を導入した途端、以前は単純明快だった多くの概念が問題をはらむようになります。2つのものが同じであるという概念について考えてみましょう。

Suppose we call make_decrementer twice with the same argument to create two functions:
make_decrementer を同じ引数で2回呼び出して、2つの 関数 を作るとしましょう： 
const D1 = make_decrementer(25);

const D2 = make_decrementer(25);
Are D1 and D2 the same? An acceptable answer is yes, because D1 and D2 have the same computational behavior—each is a function that subtracts its input from 25. In fact, D1 could be substituted for D2 in any computation without changing the result.
D1 と D2 は同じでしょうか？ 答えは「はい」で差し支えありません。なぜなら、D1 と D2 は同じ計算上の振る舞いを持つからです—どちらも入力を 25 から引く 関数 です。実際、どんな計算においても D1 を D2 に置き換えても結果は変わりません。

Contrast this with making two calls to make_simplified_withdraw:
これを、 make_simplified_withdraw を2回呼び出す場合と対比してみましょう： 
const W1 = make_simplified_withdraw(25);

const W2 = make_simplified_withdraw(25);
Are W1 and W2 the same? Surely not, because calls to W1 and W2 have distinct effects, as shown by the following sequence of interactions:
W1 と W2 は同じでしょうか？ 明らかに同じではありません。W1 と W2 への呼び出しは異なる効果を持つからです。次のやり取りのシーケンスで示されるとおりです： 
W1(20);

5
W1(20);

-15
W2(20);

5
Even though W1 and W2 are equal in the sense that they are both created by evaluating the same expression, make_simplified_withdraw(25), it is not true that W1 could be substituted for W2 in any expression without changing the result of evaluating the expression.
W1 と W2 はどちらも同じ式 make_simplified_withdraw(25) を評価して作られたという意味では等しいのですが、任意の式で W1 を W2 に置き換えても式の評価結果が変わらないとは言えません。

A language that supports the concept that equals can be substituted for equals in an expression without changing the value of the expression is said to be referentially transparent. Referential transparency is violated when we include assignment in our computer language. This makes it tricky to determine when we can simplify expressions by substituting equivalent expressions. Consequently, reasoning about programs that use assignment becomes drastically more difficult.
式の中で等しいものを等しいもので置き換えても式の値が変わらないという概念をサポートする言語は、 参照透過的であると言われます。コンピュータ言語に 代入 を含めると、参照透過性は破られます。これにより、等価な式で置き換えて式を簡約できるかどうかの判断が難しくなります。その結果、代入を使うプログラムについて推論することは格段に難しくなります。

Once we forgo referential transparency, the notion of what it means for computational objects to be the same becomes difficult to capture in a formal way. Indeed, the meaning of same in the real world that our programs model is hardly clear in itself. In general, we can determine that two apparently identical objects are indeed the same one only by modifying one object and then observing whether the other object has changed in the same way. But how can we tell if an object has changed other than by observing the same object twice and seeing whether some property of the object differs from one observation to the next? Thus, we cannot determine change without some a priori notion of sameness, and we cannot determine sameness without observing the effects of change.
参照透過性を放棄すると、計算オブジェクトが同じであるとはどういう意味かを形式的に捉えることが難しくなります。実際、プログラムがモデル化する現実世界における同じの意味自体が、決して明確ではありません。一般に、見かけ上同一の2つのオブジェクトが本当に同じものであると判定するには、一方のオブジェクトを変更して、もう一方のオブジェクトも同じように変化したかどうかを観察するしかありません。しかし、同じオブジェクトを2回観察して何らかの性質が変わったかどうかを見る以外に、オブジェクトが変化したかどうかをどうやって判定できるのでしょうか？ このように、同一性の先験的な概念なしに変化を判定することはできず、変化の効果を観察しなければ同一性を判定できないのです。

As an example of how this issue arises in programming, consider the situation where Peter and Paul have a bank account with $100 in it. There is a substantial difference between modeling this as
プログラミングにおいてこの問題がどのように生じるかの例として、ピーターとポールが 100ドルの入った銀行口座を持っている状況を考えてみましょう。これを次のようにモデル化する場合と 
const peter_acc = make_account(100);
const paul_acc = make_account(100);
and modeling it as
次のようにモデル化する場合とでは、大きな違いがあります。
const peter_acc = make_account(100);
const paul_acc = peter_acc;
In the first situation, the two bank accounts are distinct. Transactions made by Peter will not affect Paul's account, and vice versa. In the second situation, however, we have defined paul_acc to be the same thing as peter_acc. In effect, Peter and Paul now have a joint bank account, and if Peter makes a withdrawal from peter_acc Paul will observe less money in paul_acc. These two similar but distinct situations can cause confusion in building computational models. With the shared account, in particular, it can be especially confusing that there is one object (the bank account) that has two different names (peter_acc and paul_acc); if we are searching for all the places in our program where paul_acc can be changed, we must remember to look also at things that change peter_acc.
最初の状況では、2つの銀行口座は別物です。ピーターの取引はポールの口座に影響を与えず、その逆も同様です。しかし、2番目の状況では、 paul_acc を peter_acc と同じものとして定義しています。事実上、ピーターとポールは共同口座を持つことになり、ピーターが peter_acc から引き出しを行うと、ポールは paul_acc の残高が減っているのを観察します。この2つの似ているが異なる状況は、計算モデルの構築において混乱を引き起こしかねません。特に共有口座の場合、1つのオブジェクト（銀行口座）が2つの異なる名前 （peter_acc と paul_acc） を持つことは特に紛らわしくなります。プログラム中で paul_acc が変更されうるすべての箇所を探す場合、peter_acc を変更するものも見ることを忘れてはなりません。
[2]

With reference to the above remarks on sameness and change, observe that if Peter and Paul could only examine their bank balances, and could not perform operations that changed the balance, then the issue of whether the two accounts are distinct would be moot. In general, so long as we never modify data objects, we can regard a compound data object to be precisely the totality of its pieces. For example, a rational number is determined by giving its numerator and its denominator. But this view is no longer valid in the presence of change, where a compound data object has an identity that is something different from the pieces of which it is composed. A bank account is still the same bank account even if we change the balance by making a withdrawal; conversely, we could have two different bank accounts with the same state information. This complication is a consequence, not of our programming language, but of our perception of a bank account as an object. We do not, for example, ordinarily regard a rational number as a changeable object with identity, such that we could change the numerator and still have the same rational number.
上記の同一性と変化に関する考察を踏まえると、もしピーターとポールが銀行残高を確認するだけで、残高を変更する操作を行えなかったとしたら、2つの口座が別物かどうかという問題は意味をなさないことに注目してください。一般に、データオブジェクトを決して変更しない限り、複合データオブジェクトはまさにその部品の全体であると見なすことができます。例えば、有理数はその分子と分母を与えることで決定されます。しかし、変化がある場合、この見方はもはや有効ではありません。変化がある場合、複合データオブジェクトは、それを構成する部品とは異なるアイデンティティを持ちます。銀行口座は引き出しによって残高を変更しても依然として同じ銀行口座です。逆に、同じ状態情報を持つ2つの異なる銀行口座があることもありえます。この複雑さは、プログラミング言語の結果ではなく、 銀行口座をオブジェクトとして認識することの結果です。例えば、有理数を、分子を変えても同じ有理数のままであるようなアイデンティティを持つ変更可能なオブジェクトだと通常は見なしません。

Pitfalls of imperative programming
命令型プログラミングの落とし穴

In contrast to functional programming, programming that makes extensive use of assignment is known as imperative programming. In addition to raising complications about computational models, programs written in imperative style are susceptible to bugs that cannot occur in functional programs. For example, recall the iterative factorial program from section 1.2.1 (here using a conditional statement instead of a conditional expression):
関数型プログラミングとは対照的に、代入を多用するプログラミングは 命令型プログラミングとして知られています。計算モデルに関する複雑さを生むことに加えて、命令型スタイルで書かれたプログラムは、関数型プログラムでは起こりえないバグの影響を受けやすくなります。例えば、 1.2.1 節 の反復的な階乗プログラムを思い出してください （ここでは条件式の代わりに条件文を使っています）： 
function factorial(n) {
    function iter(product, counter) {
        if (counter > n) {
            return product;
        } else {
            return iter(counter * product,
                        counter + 1);
        }
    }
    return iter(1, 1);
}
Instead of passing arguments in the internal iterative loop, we could adopt a more imperative style by using explicit assignment to update the values of the variables product and counter:
内部の反復ループで引数を渡す代わりに、明示的な代入を使って変数 product と counter の値を更新する、より命令型のスタイルを採用することもできます： 
function factorial(n) {
    let product = 1;
    let counter = 1;
    function iter() {
        if (counter > n) {
            return product;
        } else {
            product = counter * product;
            counter = counter + 1;
            return iter();
        }
    }
    return iter();
}
This does not change the results produced by the program, but it does introduce a subtle trap. How do we decide the order of the assignments? As it happens, the program is correct as written. But writing the assignments in the opposite order
これはプログラムの結果を変えませんが、微妙な罠を導入します。代入の順序をどう決めればよいのでしょうか？ たまたま、このプログラムは書かれたとおりで正しいのです。しかし、代入を逆の順序で書くと 
counter = counter + 1;
product = counter * product;
would have produced a different, incorrect result. In general, programming with assignment forces us to carefully consider the relative orders of the assignments to make sure that each statement is using the correct version of the variables that have been changed. This issue simply does not arise in functional programs.
異なる、 誤った結果を生むことになります。一般に、代入を使ったプログラミングでは、各文が変更された変数の正しいバージョンを使っていることを確認するために、代入の相対的な順序を慎重に考慮しなければなりません。この問題は関数型プログラムでは単に発生しません。
[3]

The complexity of imperative programs becomes even worse if we consider applications in which several processes execute concurrently. We will return to this in section 3.4. First, however, we will address the issue of providing a computational model for expressions that involve assignment, and explore the uses of objects with local state in designing simulations.
複数のプロセスが並行実行するアプリケーションを考えると、命令型プログラムの複雑さはさらに悪化します。これについては 3.4 節で再び取り上げます。しかしまず、代入を含む式に対する計算モデルを提供する問題に取り組み、シミュレーションの設計におけるローカル状態を持つオブジェクトの利用法を探ります。

Exercise 3.8
When we defined the evaluation model in section 1.1.3, we said that the first step in evaluating an expression is to evaluate its subexpressions. But we never specified the order in which the subexpressions should be evaluated (e.g., left to right or right to left). When we introduce assignment, the order in which the operands of an operator combination are evaluated can make a difference to the result. Define a simple function f such that evaluating f(0) + f(1) will return 0 if the operands of + are evaluated from left to right but will return 1 if the operands are evaluated from right to left.
1.1.3 節で評価モデルを定義したとき、 式を評価する最初のステップはその部分式を評価することだと述べました。しかし、部分式をどの順序で評価すべきか（例えば、左から右か、右から左か）は指定しませんでした。 代入を導入すると、演算子の組み合わせのオペランドが評価される順序が結果に影響を与えることがあります。 f(0) + f(1) を評価したとき、 + のオペランド が左から右に評価されれば 0 を返し、 オペランド が右から左に評価されれば 1 を返すような、単純な 関数 f を定義してください。 
let v = -0.5;
function f(x) {
    v = x + v;
    return v;
}

We don't substitute for the occurrence of balance in the assignment because the name in an assignment is not evaluated. If we did substitute for it, we would get 25 = 25 - amount;, which makes no sense.
代入 における balance の出現に対しては置換を行いません。なぜなら、 代入 における名前は評価されないからです。もし置換してしまうと、 25 = 25 - amount; となり、意味をなしません。

The phenomenon of a single computational object being accessed by more than one name is known as aliasing. The joint bank account situation illustrates a very simple example of an alias. In section 3.3 we will see much more complex examples, such as distinct compound data structures that share parts. Bugs can occur in our programs if we forget that a change to an object may also, as a side effect, change a different object because the two different objects are actually a single object appearing under different aliases. These so-called side-effect bugs are so difficult to locate and to analyze that some people have proposed that programming languages be designed in such a way as to not allow side effects or aliasing (Lampson et al. 1981; Morris, Schmidt, and Wadler 1980).
1つの計算オブジェクトが複数の名前でアクセスされる現象は、 エイリアシングとして知られています。共同銀行口座の状況は、エイリアスの非常に単純な例を示しています。3.3 節では、部分を共有する別の複合データ構造など、はるかに複雑な例を見ていきます。オブジェクトへの変更が、副作用として 別のオブジェクトも変更しうることを忘れると、プログラムにバグが生じます。なぜなら、2つの別のオブジェクトは実際には異なるエイリアスの下に現れる1つのオブジェクトだからです。このいわゆる副作用バグは、発見と分析が非常に困難なため、副作用やエイリアシングを許さないようにプログラミング言語を設計すべきだと提案する人もいます （Lampson et al. 1981； Morris, Schmidt, and Wadler 1980）。
[3]
In view of this, it is ironic that introductory programming is most often taught in a highly imperative style. This may be a vestige of a belief, common throughout the 1960s and 1970s, that programs that call functions must inherently be less efficient than programs that perform assignments. (Steele (1977) debunks this argument.) Alternatively it may reflect a view that step-by-step assignment is easier for beginners to visualize than function call. Whatever the reason, it often saddles beginning programmers with should I set this variable before or after that one concerns that can complicate programming and obscure the important ideas.
これを考えると、プログラミング入門が極めて命令型のスタイルで教えられることが多いのは皮肉なことです。これは、1960年代から1970年代にかけて一般的だった、 関数 を呼び出すプログラムは代入を行うプログラムよりも本質的に効率が悪いに違いないという信念の名残かもしれません。（Steele (1977) がこの主張を論駁しています。）あるいは、ステップごとの代入の方が 関数 呼び出しよりも初学者にとってイメージしやすいという見方を反映しているのかもしれません。理由が何であれ、初学者プログラマはこの変数をあの変数の前に設定すべきか、それとも後にすべきかという懸念に悩まされることが多く、それがプログラミングを複雑にし、重要な考え方を見えにくくしています。
