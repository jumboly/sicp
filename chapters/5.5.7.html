5.5.7  
Interfacing Compiled Code to the Evaluator
コンパイル済みコードと評価器のインターフェース

We have not yet explained how to load compiled code into the evaluator machine or how to run it. We will assume that the explicit-control-evaluator machine has been defined as in section 5.4.4, with the additional operations specified in footnote 5 (section 5.5.2). We will implement a function compile_and_go that compiles a JavaScript program, loads the resulting object code into the evaluator machine, and causes the machine to run the code in the evaluator global environment, print the result, and enter the evaluator's driver loop. We will also modify the evaluator so that interpreted components can call compiled functions as well as interpreted ones. We can then put a compiled function into the machine and use the evaluator to call it:
コンパイル済みコードを評価器マシンにロードする方法や、それを実行する方法についてはまだ説明していません。明示的制御評価器マシンは、5.4.4節で定義したとおりに、脚注 5（5.5.2節）で指定された追加の操作を含めて定義されているものとします。ここでは、 関数 compile_and_go を実装します。これは JavaScript プログラム をコンパイルし、結果のオブジェクトコードを評価器マシンにロードし、評価器のグローバル環境でそのコードを実行させ、結果を表示し、評価器のドライバループに入ります。また、解釈実行される コンポーネント がコンパイル済み 関数 だけでなく解釈実行される 関数 も呼び出せるように評価器を修正します。これにより、コンパイル済み 関数 をマシンに組み込み、評価器を使ってそれを呼び出すことができます。 
compile_and_go(parse(`
function factorial(n) {
    return n === 1
           ? 1
           : factorial(n - 1) * n;
}
                     `));

EC-evaluate value:
undefined
EC-evaluate input:
factorial(5);
EC-evaluate value:
120

To allow the evaluator to handle compiled functions (for example, to evaluate the call to factorial above), we need to change the code at apply_dispatch (section 5.4.1) so that it recognizes compiled functions (as distinct from compound or primitive functions) and transfers control directly to the entry point of the compiled code:
評価器がコンパイル済み 関数 を扱えるようにするには（たとえば、上の factorial の呼び出しを評価するために）、 apply_dispatch （5.4.1節）のコードを変更して、コンパイル済み 関数 を（複合 関数 やプリミティブ 関数とは 別に）認識し、コンパイル済みコードのエントリポイントに直接制御を移すようにする必要があります。
[1] 
"apply_dispatch",
  test(list(op("is_primitive_function"), reg("fun"))),
  branch(label("primitive_apply")),
  test(list(op("is_compound_function"), reg("fun"))),
  branch(label("compound_apply")),
  test(list(op("is_compiled_function"), reg("fun"))),
  branch(label("compiled_apply")),
  go_to(label("unknown_function_type")),

"compiled_apply",
  push_marker_to_stack(),
  assign("val", list(op("compiled_function_entry"), reg("fun"))),
  go_to(reg("val")),
At compiled_apply, as at compound_apply, we push a marker to the stack so that a return statement in the compiled function can revert the stack to this state. Note that there is no save of continue at compiled_apply before the marking of the stack, because the evaluator was arranged so that at apply_dispatch, the continuation would be at the top of the stack.
compiled_apply では、compound_apply と同様に、コンパイル済み関数内の return 文がスタックをこの状態に戻せるように、マーカーをスタックにプッシュします。 スタックのマーキングの前に compiled_apply で continue を save していないことに注意してください。これは、apply_dispatch の時点で継続がスタックの先頭にあるように評価器が設計されているためです。

To enable us to run some compiled code when we start the evaluator machine, we add a branch instruction at the beginning of the evaluator machine, which causes the machine to go to a new entry point if the flag register is set.
評価器マシンの起動時にコンパイル済みコードを実行できるようにするために、評価器マシンの先頭に branch 命令を追加します。これは、flag レジスタが設定されている場合に、マシンを新しいエントリポイントに分岐させます。
[2] $\texttt{ }\texttt{ }$branch(label("external_entry")), // branches if flag is set "read_evaluate_print_loop", perform(list(op("initialize_stack"))), $\ldots$
The code at external_entry assumes that the machine is started with val containing the location of an instruction sequence that puts a result into val and ends with go_to(reg("continue")). Starting at this entry point jumps to the location designated by val, but first assigns continue so that execution will return to print_result, which prints the value in val and then goes to the beginning of the evaluator's read-evaluate-print loop.
external_entry のコード は、マシンが起動時に val に、結果を val に格納して go_to(reg("continue")) で終わる命令列の場所が入っていると仮定しています。このエントリポイントから開始すると、val が指す場所にジャンプしますが、その前に continue を設定して、実行が print_result に戻るようにします。ここで val の値が表示され、その後評価器の read-evaluate-print ループの先頭に進みます。
[3] 
"external_entry",
  perform(list(op("initialize_stack"))),
  assign("env", list(op("get_current_environment"))),
  assign("continue", label("print_result")),
  go_to(reg("val")),

Now we can use the following function to compile a function declaration, execute the compiled code, and run the read-evaluate-print loop so we can try the function. Because we want the compiled code to proceed to the location in continue with its result in val, we compile the program with a target of val and a linkage of "return". In order to transform the object code produced by the compiler into executable instructions for the evaluator register machine, we use the function assemble from the register-machine simulator (section 5.2.2).
これで、次の 関数 を使って 関数宣言 をコンパイルし、コンパイル済みコードを実行し、 read-evaluate-print ループを実行して 関数を 試すことができます。コンパイル済みコードが結果を val に入れて continue の場所に 進む ようにしたいので、 プログラム をターゲット val、リンケージ "return" でコンパイルします。コンパイラが生成したオブジェクトコードを評価器レジスタマシン用の実行可能な命令に変換するために、レジスタマシンシミュレータの 関数 assemble を使います（5.2.2節）。
For the interpreted program to refer to the names that are declared at top level in the compiled program, we scan out the top-level names and extend the global environment by binding these names to "*unassigned*", knowing that the compiled code will assign them the correct values.
解釈実行されるプログラムがコンパイル済みプログラムのトップレベルで宣言された名前を参照できるようにするために、 トップレベルの名前をスキャンアウトし、それらの名前を "*unassigned*" に束縛してグローバル環境を拡張します。コンパイル済みコードが正しい値を代入することがわかっているからです。
We then initialize the val register to point to the list of instructions, set the flag so that the evaluator will go to external_entry, and start the evaluator.
次に、val レジスタを命令のリストを指すように初期化し、評価器が external_entry に進むように flag を設定して、評価器を起動します。 
function compile_and_go(program) {
    const instrs = assemble(instructions(compile(program,
                                                 "val", "return")),
                            eceval);
    const toplevel_names = scan_out_declarations(program);
    const unassigneds = list_of_unassigned(toplevel_names);
    set_current_environment(extend_environment(
                               toplevel_names,
                               unassigneds, 
                               the_global_environment));
    set_register_contents(eceval, "val", instrs);
    set_register_contents(eceval, "flag", true);
    return start(eceval);
}

If we have set up stack monitoring, as at the end of section 5.4.4, we can examine the stack usage of compiled code:
5.4.4節の末尾のように スタックの監視を設定していれば、コンパイル済みコードのスタック使用状況を調べることができます。 
compile_and_go(parse(`

}

Compare this example with the evaluation of factorial(5) using the interpreted version of the same function, shown at the end of section 5.4.4. The interpreted version required 151 pushes and a maximum stack depth of 28. This illustrates the optimization that results from our compilation strategy.
この例を、5.4.4節の末尾に示した、同じ 関数 の解釈実行版による factorial(5) の評価と比較してみましょう。 解釈実行版では151回のプッシュと最大スタック深さ28が必要でした。 これは、私たちのコンパイル戦略による最適化の効果を示しています。

Interpretation and compilation
解釈実行とコンパイル

With the programs in this section, we can now experiment with the alternative execution strategies of interpretation and compilation.
この節のプログラムを使えば、解釈実行とコンパイルという2つの代替実行戦略を実験できるようになりました。
[4]
An interpreter raises the machine to the level of the user program; a compiler lowers the user program to the level of the machine language. We can regard the JavaScript language (or any programming language) as a coherent family of abstractions erected on the machine language. Interpreters are good for interactive program development and debugging because the steps of program execution are organized in terms of these abstractions, and are therefore more intelligible to the programmer. Compiled code can execute faster, because the steps of program execution are organized in terms of the machine language, and the compiler is free to make optimizations that cut across the higher-level abstractions.
インタプリタはマシンをユーザープログラムのレベルに引き上げます。コンパイラはユーザープログラムをマシン語のレベルに引き下げます。 JavaScript 言語（あるいは任意のプログラミング言語）は、マシン語の上に築かれた一貫性のある抽象の体系と見なすことができます。 インタプリタは対話的なプログラム開発とデバッグに適しています。プログラム実行のステップがこれらの抽象に基づいて構成されるため、プログラマにとってより理解しやすいからです。 コンパイル済みコードはより高速に実行できます。プログラム実行のステップがマシン語に基づいて構成され、コンパイラは高レベルの抽象を横断する最適化を自由に行えるからです。
[5]

The alternatives of interpretation and compilation also lead to different strategies for porting languages to new computers. Suppose that we wish to implement JavaScript for a new machine. One strategy is to begin with the explicit-control evaluator of section 5.4 and translate its instructions to instructions for the new machine. A different strategy is to begin with the compiler and change the code generators so that they generate code for the new machine. The second strategy allows us to run any JavaScript program on the new machine by first compiling it with the compiler running on our original JavaScript system, and linking it with a compiled version of the runtime library.
解釈実行とコンパイルという2つの選択肢は、新しいコンピュータに言語を 移植する際の戦略にも違いをもたらします。新しいマシンに JavaScript を実装したいとしましょう。一つの戦略は、5.4節の明示的制御評価器から始めて、その命令を新しいマシンの命令に翻訳することです。別の戦略は、コンパイラから始めて、コード生成器を変更して新しいマシン用のコードを生成させることです。2番目の戦略では、元の JavaScript システム上で動作するコンパイラでプログラムをまずコンパイルし、ランタイムライブラリのコンパイル済みバージョンとリンクすることで、新しいマシン上で任意の JavaScript プログラムを実行できます。
[6]
Better yet, we can compile the compiler itself, and run this on the new machine to compile other JavaScript programs.
さらに良いことに、コンパイラ自身をコンパイルして、新しいマシン上でそれを実行し、他の JavaScript プログラムをコンパイルすることもできます。
[7]
Or we can compile one of the interpreters of section 4.1 to produce an interpreter that runs on the new machine.
あるいは、4.1節のインタプリタの一つをコンパイルして、新しいマシン上で動作するインタプリタを作ることもできます。

Exercise 5.47
By comparing the stack operations used by compiled code to the stack operations used by the evaluator for the same computation, we can determine the extent to which the compiler optimizes use of the stack, both in speed (reducing the total number of stack operations) and in space (reducing the maximum stack depth). Comparing this optimized stack use to the performance of a special-purpose machine for the same computation gives some indication of the quality of the compiler.
  1. Exercise 5.28 asked you to determine, as a function of $n$, the number of pushes and the maximum stack depth needed by the evaluator to compute $n!$ using the recursive factorial function given above. Exercise 5.13 asked you to do the same measurements for the special-purpose factorial machine shown in figure 5.13. Now perform the same analysis using the compiled factorial function.

    Take the ratio of the number of pushes in the compiled version to the number of pushes in the interpreted version, and do the same for the maximum stack depth. Since the number of operations and the stack depth used to compute $n!$ are linear in $n$, these ratios should approach constants as $n$ becomes large. What are these constants? Independent of the strategy of execution, we incur significant overhead if we insist that errors encountered in execution of a user program be detected and signaled, rather than being allowed to kill the system or produce wrong answers. For example, an out-of-bounds array reference can be detected by checking the validity of the reference before performing it. The overhead of checking, however, can be many times the cost of the array reference itself, and a programmer should weigh speed against safety in determining whether such a check is desirable. A good compiler should be able to produce code with such checks, should avoid redundant checks, and should allow programmers to control the extent and type of error checking in the compiled code.

Compilers for popular languages, such as C and C++, put hardly any error-checking operations into running code, so as to make things run as fast as possible. As a result, it falls to programmers to explicitly provide error checking. Unfortunately, people often neglect to do this, even in critical applications where speed is not a constraint. Their programs lead fast and dangerous lives. For example, the notorious Worm that paralyzed the Internet in 1988 exploited the UNIX$^{\textrm{TM}}$ operating system's failure to check whether the input buffer has overflowed in the finger daemon. (See Spafford 1989.)
実行戦略に関係なく、ユーザープログラムの実行中に遭遇する エラーを、システムの停止や誤った結果の生成を許すのではなく、検出して通知することを要求すると、かなりのオーバーヘッドが発生します。例えば、配列の範囲外参照は、参照を実行する前にその有効性を検査することで検出できます。しかし、この検査のオーバーヘッドは配列参照そのもののコストの何倍にもなりえるため、プログラマはそのような検査が望ましいかどうかを速度と安全性を天秤にかけて判断すべきです。優れたコンパイラは、そのような検査を含むコードを生成でき、冗長な検査を避け、コンパイル済みコードにおけるエラー検査の範囲と種類をプログラマが制御できるようにすべきです。
