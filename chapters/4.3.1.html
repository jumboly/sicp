4.3.1  
Search and amb
探索とamb

To extend JavaScript to support nondeterminism, we introduce a new syntactic form called amb.
JavaScript を拡張して非決定性をサポートするために、 amb と呼ばれる新しい 構文形式 を導入します。
[1]
The expression amb($e_1,\ e_2,\ldots, e_n$) returns the value of one of the $n$ expressions $e_i$ ambiguously. For example, the expression
式 amb($e_1,\ e_2,\ldots, e_n$) は、$n$ 個の式 $e_i$ のいずれか一つの値を曖昧に返します。例えば、式 
list(amb(1, 2, 3), amb("a", "b"));
can have six possible values:
は6つの可能な値を持ちます： 
list(1, "a") list(1, "b") list(2, "a")
list(2, "b") list(3, "a") list(3, "b")
An amb expression with a single choice produces an ordinary (single) value.
選択肢が一つだけの amb 式 は、通常の（単一の）値を生成します。

An amb expression with no choices—the expression amb()—is an expression with no acceptable values. Operationally, we can think of amb() as an expression that when evaluated causes the computation to fail: The computation aborts and no value is produced. Using this idea, we can express the requirement that a particular predicate expression p must be true as follows:
選択肢のない amb 式 —つまり式 amb() —は、 受け入れ可能な値を持たない式です。操作的には、 amb() は評価されると計算を失敗させる式と考えることができます。計算は中断され、値は生成されません。このアイデアを使って、特定の述語式 p が真でなければならないという要求を次のように表現できます： 
function require(p) {
    if (! p) {
        amb();
    } else {}
}

With amb and require, we can implement the an_element_of function used above:
amb と require を使って、上で使用した an_element_of 関数 を実装できます： 
function an_element_of(items) {
    require(! is_null(items));
    return amb(head(items), an_element_of(tail(items)));
}
An application of an_element_of fails if the list is empty. Otherwise it ambiguously returns either the first element of the list or an element chosen from the rest of the list.
an_element_of の適用 は、リストが空の場合に失敗します。それ以外の場合は、リストの最初の要素か、リストの残りから選ばれた要素のいずれかを曖昧に返します。

We can also express infinite ranges of choices. The following function potentially returns any integer greater than or equal to some given $n$:
無限の範囲の選択肢を表現することもできます。次の 関数 は、与えられた $n$ 以上の任意の整数を返す可能性があります： 
function an_integer_starting_from(n) {
    return amb(n, an_integer_starting_from(n + 1));
}
This is like the stream function integers_starting_from described in section 3.5.2, but with an important difference: The stream function returns an object that represents the sequence of all integers beginning with $n$, whereas the amb function returns a single integer.
これは 3.5.2 節で説明したストリーム 関数 integers_starting_from に似ていますが、重要な違いがあります。ストリーム 関数 は $n$ から始まるすべての整数の列を表すオブジェクトを返しますが、amb 関数 は単一の整数を返します。
[2]

Abstractly, we can imagine that evaluating an amb expression causes time to split into branches, where the computation continues on each branch with one of the possible values of the expression. We say that amb represents a nondeterministic choice point. If we had a machine with a sufficient number of processors that could be dynamically allocated, we could implement the search in a straightforward way. Execution would proceed as in a sequential machine, until an amb expression is encountered. At this point, more processors would be allocated and initialized to continue all of the parallel executions implied by the choice. Each processor would proceed sequentially as if it were the only choice, until it either terminates by encountering a failure, or it further subdivides, or it finishes.
抽象的には、amb 式の評価によって 時間が分岐に分かれ、各分岐でその式の可能な値の一つを使って計算が続行されると想像できます。amb は 非決定的選択ポイントを表すと言います。動的に割り当て可能な十分な数のプロセッサを持つマシンがあれば、探索を素直に実装できるでしょう。実行は逐次マシンと同様に進み、amb 式に遭遇するまで続きます。その時点で、さらにプロセッサが割り当てられ、選択が意味するすべての並列実行を継続するよう初期化されます。各プロセッサは、あたかもそれが唯一の選択肢であるかのように逐次的に処理を進め、失敗に遭遇して停止するか、さらに分岐するか、完了するかのいずれかになります。
[3]

On the other hand, if we have a machine that can execute only one process (or a few concurrent processes), we must consider the alternatives sequentially. One could imagine modifying an evaluator to pick at random a branch to follow whenever it encounters a choice point. Random choice, however, can easily lead to failing values. We might try running the evaluator over and over, making random choices and hoping to find a non-failing value, but it is better to systematically search all possible execution paths. The amb evaluator that we will develop and work with in this section implements a systematic search as follows: When the evaluator encounters an application of amb, it initially selects the first alternative. This selection may itself lead to a further choice. The evaluator will always initially choose the first alternative at each choice point. If a choice results in a failure, then the evaluator automagically
一方、一つのプロセス（あるいは少数の並行プロセス）しか実行できないマシンがある場合、代替案を 順番に検討しなければなりません。選択ポイントに遭遇するたびにランダムに分岐先を選ぶように評価器を変更することも考えられます。しかし、ランダムな選択では失敗する値に簡単に行き当たります。ランダムな選択を繰り返して失敗しない値が見つかることを期待して評価器を何度も実行してみることもできますが、すべての可能な実行パスを 体系的に探索する方がよいでしょう。この節で開発して使う amb 評価器は、次のように体系的探索を実装します。評価器が amb の適用に遭遇すると、最初に第一の代替案を選択します。この選択自体がさらなる選択につながることもあります。評価器は各選択ポイントで常に最初の代替案を選びます。選択が失敗に至った場合、評価器は 自動魔法的に（automagically）
[4]
backtracks to the most recent choice point and tries the next alternative. If it runs out of alternatives at any choice point, the evaluator will back up to the previous choice point and resume from there. This process leads to a search strategy known as depth-first search or chronological backtracking.
直近の選択ポイントまでバックトラックして、次の代替案を試みます。ある選択ポイントで代替案が尽きると、評価器は前の選択ポイントまで戻り、そこから再開します。このプロセスは、 深さ優先探索あるいは 時系列バックトラッキングとして知られる探索戦略につながります。
[5]

Driver loop
ドライバループ

The driver loop for the amb evaluator has some unusual properties. It reads a program and prints the value of the first non-failing execution, as in the prime_sum_pair example shown above. If we want to see the value of the next successful execution, we can ask the interpreter to backtrack and attempt to generate a second non-failing execution. This is signaled by typing retry. If any other input except retry is given, the interpreter will start a new problem, discarding the unexplored alternatives in the previous problem. Here is a sample interaction:
amb 評価器の ドライバループにはいくつかの独特な性質があります。 プログラム を読み込み、上で示した prime_sum_pair の例のように、最初に失敗しなかった実行の値を表示します。次の成功した実行の値を見たい場合は、インタプリタにバックトラックして2番目の失敗しない実行を生成するよう求めることができます。 これは retry と入力することで合図します。retry 以外の入力が与えられると、インタプリタは前の問題の未探索の代替案を破棄して、新しい問題を開始します。 以下はやりとりの例です： 
amb-evaluate input:
prime_sum_pair(list(1, 3, 5, 8), list(20, 35, 110));

Starting a new problem
amb-evaluate value:
[3, [20, null]]
amb-evaluate input:
retry

amb-evaluate value:
[3, [110, null]]
amb-evaluate input:
retry

amb-evaluate value:
[8, [35, null]]
amb-evaluate input:
retry

There are no more values of
prime_sum_pair([1, [3, [5, [8, null]]]], [20, [35, [110, null]]])
amb-evaluate input:
prime_sum_pair(list(19, 27, 30), list(11, 36, 58));

Starting a new problem
amb-evaluate value:
[30, [11, null]]

Exercise 4.33
Write a function an_integer_between that returns an integer between two given bounds. This can be used to implement a function that finds Pythagorean triples, i.e., triples of integers $(i,j,k)$ between the given bounds such that $i \leq j$ and $i^2 + j^2 =k^2$, as follows:
与えられた2つの境界値の間の整数を返す 関数 an_integer_between を書いてください。これを使って、与えられた境界値の間の整数の三つ組 $(i,j,k)$ で、$i \leq j$ かつ $i^2 + j^2 =k^2$ を満たす ピタゴラスの三つ組を見つける 関数 を次のように実装できます： 
function a_pythogorean_triple_between(low, high) {      
    const i = an_integer_between(low, high);
    const j = an_integer_between(i, high);
    const k = an_integer_between(j, high);
    require(i * i + j * j === k * k);
    return list(i, j, k);
}

// solution by GitHub user jonathantorres

function an_integer_between(low, high) {
    require(low <= high);
    return amb(low, an_integer_between(low+1, high));
}

Exercise 4.35
Ben Bitdiddle claims that the following method for generating Pythagorean triples is more efficient than the one in exercise 4.33. Is he correct? (Hint: Consider the number of possibilities that must be explored.)
Ben Bitdiddle は、 ピタゴラスの三つ組を生成する次の方法は、練習問題 4.33 のものよりも効率的だと主張しています。彼は正しいでしょうか？ （ヒント：探索しなければならない可能性の数を考えてください。） 
function a_pythagorean_triple_between(low, high) {
    const i = an_integer_between(low, high);
    const hsq = high * high;
    const j = an_integer_between(i, high);
    const ksq = i * i + j * j;
    require(hsq >= ksq);
    const k = math_sqrt(ksq);
    require(is_integer(k));
    return list(i, j, k);
}

[1]
The idea of amb for nondeterministic programming was first described in 1961 by John McCarthy (see McCarthy 1967).
非決定的プログラミングのための amb のアイデアは、1961年に John McCarthy によって初めて記述されました（McCarthy 1967 を参照）。
[2]
In actuality, the distinction between nondeterministically returning a single choice and returning all choices depends somewhat on our point of view. From the perspective of the code that uses the value, the nondeterministic choice returns a single value. From the perspective of the programmer designing the code, the nondeterministic choice potentially returns all possible values, and the computation branches so that each value is investigated separately.
実際には、非決定的に単一の選択肢を返すことと、すべての選択肢を返すことの区別は、見方によってある程度異なります。値を使うコードの観点からは、非決定的選択は単一の値を返します。コードを設計するプログラマの観点からは、非決定的選択はすべての可能な値を返す可能性があり、計算が分岐してそれぞれの値が個別に調査されます。
[3]
One might object that this is a hopelessly inefficient mechanism. It might require millions of processors to solve some easily stated problem this way, and most of the time most of those processors would be idle. This objection should be taken in the context of history. Memory used to be considered just such an expensive commodity. In 1965 a megabyte of RAM cost about $400,000. Now every personal computer has many gigabytes of RAM, and most of the time most of that RAM is unused. It is hard to underestimate the cost of mass-produced electronics.

The integration of automatic search strategies into programming languages has had a long and checkered history. The first suggestions that nondeterministic algorithms might be elegantly encoded in a programming language with search and automatic backtracking came from Robert Floyd (1967). Carl Hewitt (1969) invented a programming language called Planner that explicitly supported automatic chronological backtracking, providing for a built-in depth-first search strategy. Sussman, Winograd, and Charniak (1971) implemented a subset of this language, called MicroPlanner, which was used to support work in problem solving and robot planning. Similar ideas, arising from logic and theorem proving, led to the genesis in Edinburgh and Marseille of the elegant language Prolog (which we will discuss in section 4.4). After sufficient frustration with automatic search, McDermott and Sussman (1972) developed a language called Conniver, which included mechanisms for placing the search strategy under programmer control. This proved unwieldy, however, and Sussman and Stallman (1975) found a more tractable approach while investigating methods of symbolic analysis for electrical circuits. They developed a nonchronological backtracking scheme that was based on tracing out the logical dependencies connecting facts, a technique that has come to be known as dependency-directed backtracking. Although their method was complex, it produced reasonably efficient programs because it did little redundant search. Doyle (1979) and McAllester (1978, 1980) generalized and clarified the methods of Stallman and Sussman, developing a new paradigm for formulating search that is now called truth maintenance. Many problem-solving systems use some form of truth-maintenance system as a substrate. See Forbus and de Kleer 1993 for a discussion of elegant ways to build truth-maintenance systems and applications using truth maintenance. Zabih, McAllester, and Chapman 1987 describes a nondeterministic extension to Scheme that is based on amb; it is similar to the interpreter described in this section, but more sophisticated, because it uses dependency-directed backtracking rather than chronological backtracking. Winston 1992 gives an introduction to both kinds of backtracking.
自動探索戦略をプログラミング言語に統合する歴史は、長く波乱に満ちたものでした。非決定的アルゴリズムを探索と自動バックトラッキングを持つプログラミング言語で優雅に符号化できるという最初の提案は、 Robert Floyd（1967）によるものでした。 Carl Hewitt（1969）は、自動的な時系列バックトラッキングを明示的にサポートし、組み込みの深さ優先探索戦略を提供する Planner というプログラミング言語を発明しました。 Sussman、Winograd、Charniak（1971）はこの言語のサブセットである MicroPlanner を実装し、問題解決やロボット計画の研究をサポートするために使用しました。論理学と定理証明から生じた同様のアイデアが、エジンバラとマルセイユで優雅な言語 Prolog の誕生につながりました（4.4 節で議論します）。自動探索に十分なフラストレーションを感じた後、 McDermott と Sussman（1972）は、探索戦略をプログラマの制御下に置くメカニズムを含む Conniver という言語を開発しました。しかしこれは扱いにくいことが判明し、 Sussman と Stallman（1975）は電気回路のシンボリック解析手法を研究する中で、より扱いやすいアプローチを発見しました。彼らは事実を結びつける論理的依存関係を追跡することに基づく非時系列バックトラッキング方式を開発し、これは 依存性指向バックトラッキングとして知られるようになった技法です。彼らの方法は複雑でしたが、冗長な探索がほとんどないため、合理的に効率的なプログラムを生成しました。 Doyle (1979) と McAllester (1978, 1980) は Stallman と Sussman の方法を一般化・明確化し、現在 真理維持と呼ばれる探索の定式化のための新しいパラダイムを開発しました。 多くの問題解決システムは 何らかの形の真理維持システムを基盤として使用しています。真理維持システムを構築する優雅な方法と真理維持を使ったアプリケーションの議論については、 Forbus and de Kleer 1993 を参照してください。 Zabih, McAllester, and Chapman 1987 は、amb に基づく Scheme の非決定的拡張を記述しています。これはこの節で説明するインタプリタに似ていますが、時系列バックトラッキングではなく依存性指向バックトラッキングを使用するため、より洗練されています。 Winston 1992 は両方の種類のバックトラッキングの入門を提供しています。
