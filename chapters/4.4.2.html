4.4.2  
How the Query System Works
クエリシステムの仕組み

In section 4.4.4 we will present an implementation of the query interpreter as a collection of functions. In this section we give an overview that explains the general structure of the system independent of low-level implementation details. After describing the implementation of the interpreter, we will be in a position to understand some of its limitations and some of the subtle ways in which the query language's logical operations differ from the operations of mathematical logic.
4.4.4節では、クエリインタプリタの実装を 関数 の集まりとして提示します。この節では、低レベルの実装の詳細とは独立した、システムの一般的な構造を説明する概要を示します。インタプリタの実装を説明した後で、その限界のいくつかと、クエリ言語の論理演算が数理論理学の演算とどのような微妙な違いがあるかを理解できるようになります。

It should be apparent that the query evaluator must perform some kind of search in order to match queries against facts and rules in the data base. One way to do this would be to implement the query system as a nondeterministic program, using the amb evaluator of section 4.3 (see exercise 4.75). Another possibility is to manage the search with the aid of streams. Our implementation follows this second approach.
クエリ評価器がデータベース内の事実やルールとクエリを照合するために、何らかの探索を行わなければならないことは明らかでしょう。その一つの方法は、4.3節のamb評価器を使って、クエリシステムを非決定的プログラムとして実装することです（練習問題 4.75を参照）。もう一つの可能性は、ストリームを使って探索を管理することです。私たちの実装はこの2番目のアプローチに従います。

The query system is organized around two central operations, called pattern matching and unification. We first describe pattern matching and explain how this operation, together with the organization of information in terms of streams of frames, enables us to implement both simple and compound queries. We next discuss unification, a generalization of pattern matching needed to implement rules. Finally, we show how the entire query interpreter fits together through a function that classifies queries in a manner analogous to the way evaluate classifies expressions for the interpreter described in section 4.1.
クエリシステムは、パターンマッチングとユニフィケーションと呼ばれる2つの中心的な操作を軸に構成されています。まずパターンマッチングについて説明し、この操作がフレームのストリームという形で情報を整理することと合わせて、単純クエリと複合クエリの両方をどのように実装できるかを説明します。次に、ルールの実装に必要なパターンマッチングの一般化であるユニフィケーションについて議論します。最後に、4.1節で説明したインタプリタにおける evaluate が式を分類するのと類似の方法で、 クエリ を分類する 関数 を通じて、クエリインタプリタ全体がどのように組み合わさっているかを示します。

Pattern matching
パターンマッチング

A pattern matcher is a program that tests whether some datum fits a specified pattern. For example, the datum list(list("a", "b"), "c", list("a", "b")) matches the pattern list($x, "c", $x) with the pattern variable $x bound to list("a", "b"). The same data list matches the pattern list($x, $y, $z) with $x and $z both bound to list("a", "b") and $y bound to "c". It also matches the pattern list(list($x, $y), "c", list($x, $y)) with $x bound to "a" and $y bound to "b". However, it does not match the pattern list($x, "a", $y), since that pattern specifies a list whose second element is the string "a".
パターンマッチャーとは、あるデータが指定されたパターンに適合するかどうかをテストするプログラムです。たとえば、 データ list(list("a", "b"), "c", list("a", "b")) は、パターン list($x, "c", $x) に対して、パターン変数 $x が list("a", "b") に束縛された状態でマッチします。同じ データリスト は、パターン list($x, $y, $z) に対して、 $x と $z がともに list("a", "b") に束縛され、 $y が "c" に束縛された状態でマッチします。また、パターン list(list($x, $y), "c", list($x, $y)) に対しても、 $x が "a" に束縛され、 $y が "b" に束縛された状態でマッチします。しかし、パターン list($x, "a", $y) にはマッチしません。なぜなら、このパターンは第2要素が 文字列"a" であるリストを指定しているからです。

The pattern matcher used by the query system takes as inputs a pattern, a datum, and a frame that specifies bindings for various pattern variables. It checks whether the datum matches the pattern in a way that is consistent with the bindings already in the frame. If so, it returns the given frame augmented by any bindings that may have been determined by the match. Otherwise, it indicates that the match has failed.
クエリシステムで使われるパターンマッチャーは、入力としてパターン、データ、そしてさまざまなパターン変数の束縛を指定するフレームを受け取ります。データがフレーム内の既存の束縛と矛盾しない形でパターンにマッチするかどうかを確認します。マッチする場合は、マッチによって決定された束縛を追加した元のフレームを返します。マッチしない場合は、マッチが失敗したことを示します。

Using the pattern list($x, $y, $x) to match list("a", "b", "a") given an empty frame, for example, will return a frame specifying that $x is bound to "a" and $y is bound to "b". Trying the match with the same pattern, the same datum, and a frame specifying that $y is bound to "a" will fail. Trying the match with the same pattern, the same datum, and a frame in which $y is bound to "b" and $x is unbound will return the given frame augmented by a binding of $x to "a".
パターン list($x, $y, $x) を使って list("a", "b", "a") と たとえば空のフレームで 照合すると、 $x が "a" に束縛され、 $y が "b" に束縛されたフレームが返されます。同じパターン、同じデータ、そして $y が "a" に束縛されたフレームで照合を試みると、失敗します。同じパターン、同じデータ、そして $y が "b" に束縛され $x が未束縛のフレームで照合を試みると、 $x を "a"に束縛する束縛が追加された元のフレームが返されます。

The pattern matcher is all the mechanism that is needed to process simple queries that don't involve rules. For instance, to process the query
パターンマッチャーは、ルールを含まない単純クエリを処理するために必要なメカニズムのすべてです。たとえば、クエリ 
job($x, list("computer", "programmer"))
we scan through all assertions in the data base and select those that match the pattern with respect to an initially empty frame. For each match we find, we use the frame returned by the match to instantiate the pattern with a value for $x.
を処理するには、データベース内のすべてのアサーションをスキャンし、最初は空のフレームに対してパターンにマッチするものを選択します。マッチが見つかるたびに、マッチによって返されたフレームを使って、 $x の値でパターンをインスタンス化します。

Streams of frames
フレームのストリーム

The testing of patterns against frames is organized through the use of streams. Given a single frame, the matching process runs through the data-base entries one by one. For each data-base entry, the matcher generates either a special symbol indicating that the match has failed or an extension to the frame. The results for all the data-base entries are collected into a stream, which is passed through a filter to weed out the failures. The result is a stream of all the frames that extend the given frame via a match to some assertion in the data base.
パターンとフレームの照合は、ストリームを使って構成されます。単一のフレームが与えられると、マッチングプロセスはデータベースのエントリを1つずつ調べていきます。各データベースエントリに対して、マッチャはマッチが失敗したことを示す特別なシンボルか、フレームの拡張のいずれかを生成します。すべてのデータベースエントリに対する結果はストリームに集められ、失敗を取り除くフィルタを通されます。結果は、データベース内の何らかのアサーションとのマッチによって与えられたフレームを拡張する、すべてのフレームのストリームです。
[1]

In our system, a query takes an input stream of frames and performs the above matching operation for every frame in the stream, as indicated in figure 4.8. That is, for each frame in the input stream, the query generates a new stream consisting of all extensions to that frame by matches to assertions in the data base. All these streams are then combined to form one huge stream, which contains all possible extensions of every frame in the input stream. This stream is the output of the query.
私たちのシステムでは、クエリはフレームの入力ストリームを受け取り、 figure 4.8 に示すように、ストリーム内のすべてのフレームに対して上記のマッチング操作を行います。つまり、入力ストリームの各フレームに対して、クエリはデータベース内のアサーションとのマッチによるそのフレームのすべての拡張からなる新しいストリームを生成します。これらのストリームはすべて結合されて1つの巨大なストリームになり、入力ストリームのすべてのフレームのすべての可能な拡張が含まれます。このストリームがクエリの出力です。

To answer a simple query, we use the query with an input stream consisting of a single empty frame. The resulting output stream contains all extensions to the empty frame (that is, all answers to our query). This stream of frames is then used to generate a stream of copies of the original query pattern with the variables instantiated by the values in each frame, and this is the stream that is finally printed.
単純クエリに答えるには、単一の空フレームからなる入力ストリームでクエリを使用します。結果の出力ストリームには、空フレームのすべての拡張（つまり、クエリに対するすべての回答）が含まれます。このフレームのストリームは、各フレームの値で変数をインスタンス化した元のクエリパターンのコピーのストリームを生成するために使われ、このストリームが最終的に表示されます。

Compound queries
複合クエリ

The real elegance of the stream-of-frames implementation is evident when we deal with compound queries. The processing of compound queries makes use of the ability of our matcher to demand that a match be consistent with a specified frame. For example, to handle the and of two queries, such as
フレームのストリームによる実装の真のエレガンスは、複合クエリを扱うときに明らかになります。複合クエリの処理は、マッチが指定されたフレームと矛盾しないことを要求できるマッチャの能力を利用します。たとえば、次のような2つのクエリのandを処理するには、 
and(can_do_job($x, list("computer", "programmer", "trainee")),
    job($person, $x))
(informally, Find all people who can do the job of a computer programmer trainee), we first find all entries that match the pattern
（非公式には「コンピュータプログラマ研修生の仕事ができるすべての人を見つけよ」）、まずパターン 
can_do_job($x, list("computer", "programmer", "trainee"))
This produces a stream of frames, each of which contains a binding for $x. Then for each frame in the stream we find all entries that match
にマッチするすべてのエントリを見つけます。これにより、それぞれが $x の束縛を含むフレームのストリームが生成されます。次に、ストリーム内の各フレームに対して、 
job($person, $x)
in a way that is consistent with the given binding for $x. Each such match will produce a frame containing bindings for $x and $person. The and of two queries can be viewed as a series combination of the two component queries, as shown in figure 4.10.
に与えられた $x の束縛と矛盾しない形でマッチするすべてのエントリを見つけます。そのような各マッチは、 $x と $person の束縛を含むフレームを生成します。2つのクエリのandは、 figure 4.10 に示すように、2つの構成クエリの直列結合と見なすことができます。
The frames that pass through the first query filter are filtered and further extended by the second query.
最初のクエリフィルタを通過したフレームは、2番目のクエリによってさらにフィルタリングされ、拡張されます。

Figure 4.12 shows the analogous method for computing the or of two queries as a parallel combination of the two component queries. The input stream of frames is extended separately by each query. The two resulting streams are then merged to produce the final output stream.
Figure 4.12 は、2つのクエリの orを、2つの構成クエリの並列結合として計算する類似の方法を示しています。入力フレームのストリームは、各クエリによって個別に拡張されます。その後、2つの結果のストリームがマージされて最終的な出力ストリームが生成されます。

Even from this high-level description, it is apparent that the processing of compound queries can be slow. For example, since a query may produce more than one output frame for each input frame, and each query in an and gets its input frames from the previous query, an and query could, in the worst case, have to perform a number of matches that is exponential in the number of queries (see exercise 4.73).
この高レベルの説明からでも、複合クエリの処理が遅くなりうることは明らかです。 例えば、各入力フレームに対してクエリが複数の出力フレームを生成する可能性があり、and内の各クエリは前のクエリから入力フレームを受け取るため、andクエリは最悪の場合、クエリの数に対して指数的な数のマッチを実行しなければならない可能性があります（練習問題 4.73を参照）。
[2]
Though systems for handling only simple queries are quite practical, dealing with complex queries is extremely difficult.
単純なクエリのみを扱うシステムは非常に実用的ですが、複雑なクエリを扱うことは極めて困難です。
[3]

From the stream-of-frames viewpoint, the not of some query acts as a filter that removes all frames for which the query can be satisfied. For instance, given the pattern
フレームのストリームの観点から見ると、あるクエリの notは、そのクエリが満たされるすべてのフレームを除去するフィルタとして動作します。例えば、パターン 
not(job($x, list("computer", "programmer")))
we attempt, for each frame in the input stream, to produce extension frames that satisfy job($x, list("computer", "programmer")). We remove from the input stream all frames for which such extensions exist. The result is a stream consisting of only those frames in which the binding for $x does not satisfy job($x, list("computer", "programmer")). For example, in processing the query
が与えられた場合、入力ストリーム内の各フレームに対して、 job($x, list("computer", "programmer")) を満たす拡張フレームを生成しようと試みます。そのような拡張が存在するすべてのフレームを入力ストリームから除去します。結果は、 $x の束縛が job($x, list("computer", "programmer")) を満たさないフレームのみからなるストリームです。例えば、クエリ 
and(supervisor($x, $y),
    not(job($x, list("computer", "programmer"))))
the first clause will generate frames with bindings for $x and $y. The not clause will then filter these by removing all frames in which the binding for $x satisfies the restriction that $x is a computer programmer.
を処理する際、最初の節は $x と $y の束縛を持つフレームを生成します。次にnot節が、 $x の束縛が $x がコンピュータプログラマであるという制約を満たすすべてのフレームを除去することで、これらをフィルタリングします。
[4]

The javascript_predicate syntactic form is implemented as a similar filter on frame streams. We use each frame in the stream to instantiate any variables in the pattern, then apply the JavaScript predicate. We remove from the input stream all frames for which the predicate fails.
javascript_predicate 構文形式 は、フレームストリームに対する同様のフィルタとして実装されています。ストリーム内の各フレームを使ってパターン内の変数をインスタンス化し、次に JavaScript の述語を適用します。述語が失敗するすべてのフレームを入力ストリームから除去します。

Unification
ユニフィケーション

In order to handle rules in the query language, we must be able to find the rules whose conclusions match a given query pattern. Rule conclusions are like assertions except that they can contain variables, so we will need a generalization of pattern matching—called unification—in which both the pattern and the datum may contain variables.
クエリ言語でルールを扱うためには、与えられたクエリパターンにマッチする結論を持つルールを見つけることができなければなりません。ルールの結論は、変数を含むことができるという点を除けばアサーションと同様です。そのため、パターンとデータの両方が変数を含むことができるパターンマッチングの一般化—ユニフィケーションと呼ばれるもの—が必要になります。

A unifier takes two patterns, each containing constants and variables, and determines whether it is possible to assign values to the variables that will make the two patterns equal. If so, it returns a frame containing these bindings. For example, unifying list($x, "a", $y) and list($y, $z, "a") will specify a frame in which $x, $y, and $z must all be bound to "a". On the other hand, unifying list($x, $y, "a") and list($x, "b", $y) will fail, because there is no value for $y that can make the two patterns equal. (For the second elements of the patterns to be equal, $y would have to be "b"; however, for the third elements to be equal, $y would have to be "a".) The unifier used in the query system, like the pattern matcher, takes a frame as input and performs unifications that are consistent with this frame.
ユニファイアは、それぞれ定数と変数を含む2つのパターンを受け取り、2つのパターンを等しくするような値を変数に割り当てることが可能かどうかを判定します。可能であれば、それらの束縛を含むフレームを返します。例えば、 list($x, "a", $y) と list($y, $z, "a") をユニファイすると、 $x、 $y、 および $z がすべて "a" に束縛されなければならないフレームが指定されます。一方、 list($x, $y, "a") と list($x, "b", $y) のユニフィケーションは失敗します。2つのパターンを等しくする $y の値が存在しないからです。（パターンの2番目の要素が等しくなるためには、 $y は "b" でなければなりませんが、3番目の要素が等しくなるためには、 $y は "a" でなければなりません。）クエリシステムで使われるユニファイアは、パターンマッチャーと同様に、フレームを入力として受け取り、そのフレームと矛盾しないユニフィケーションを実行します。

The unification algorithm is the most technically difficult part of the query system. With complex patterns, performing unification may seem to require deduction. To unify list($x, $x) and list(list("a", $y, "c"), list("a", "b", $z)), for example, the algorithm must infer that $x should be list("a", "b", "c"), $y should be "b", and $z should be "c". We may think of this process as solving a set of equations among the pattern components. In general, these are simultaneous equations, which may require substantial manipulation to solve.
ユニフィケーションアルゴリズムは、クエリシステムの中で技術的に最も難しい部分です。複雑なパターンでは、ユニフィケーションの実行に推論が必要なように思えるかもしれません。例えば、 list($x, $x) と list(list("a", $y, "c"), list("a", "b", $z)) をユニファイするには、アルゴリズムは $x が list("a", "b", "c")、 $y が "b"、 そして $z が "c" であるべきことを推論しなければなりません。このプロセスは、パターンの構成要素間の方程式の集合を解くことと考えることができます。一般に、これらは連立方程式であり、解くためにかなりの操作が必要になることがあります。
[5]
For example, unifying list($x, $x) and list(list("a", $y, "c"), list("a", "b", $z)) may be thought of as specifying the simultaneous equations
例えば、 list($x, $x) と list(list("a", $y, "c"), list("a", "b", $z)) のユニフィケーションは、次の連立方程式を指定するものと考えることができます。
\[\begin{array}{lll} \texttt{\$x} & = & \texttt{list("a", \$y, "c")} \\ \texttt{\$x} & = & \texttt{list("a", "b", \$z)} \\ \end{array}\]
These equations imply that
これらの方程式は次を意味します。
\[\begin{array}{lll} \texttt{list("a", \$y, "c")} & = & \texttt{list("a", "b", \$z)} \end{array}\]
which in turn implies that
これはさらに次を意味し、
\[\begin{array}{lllllll} \texttt{"a"} & = & \texttt{"a"},\qquad \texttt{\$y} & = & \texttt{"b"},\qquad \texttt{"c"} & = & \texttt{\$z} \end{array}\]
and hence that
したがって次が得られます。
\[\begin{array}{lll} \texttt{\$x} & = & \texttt{list("a", "b", "c")} \end{array}\]

In a successful pattern match, all pattern variables become bound, and the values to which they are bound contain only constants. This is also true of all the examples of unification we have seen so far. In general, however, a successful unification may not completely determine the variable values; some variables may remain unbound and others may be bound to values that contain variables.
パターンマッチングが成功すると、すべてのパターン変数が束縛され、束縛された値は定数のみを含みます。これは、これまで見てきたユニフィケーションのすべての例でも同様です。 しかし、一般にはユニフィケーションが成功しても変数の値が完全に決まるとは限りません。一部の変数が未束縛のまま残ったり、変数を含む値に束縛されたりすることがあります。

Consider the unification of list($x, "a") and list(list("b", $y), $z). We can deduce that $x $=$ list("b", $y) and "a" $=$ $z, but we cannot further solve for $x or $y. The unification doesn't fail, since it is certainly possible to make the two patterns equal by assigning values to $x and $y. Since this match in no way restricts the values $y can take on, no binding for $y is put into the result frame. The match does, however, restrict the value of $x. Whatever value $y has, $x must be list("b", $y). A binding of $x to the pattern list("b", $y) is thus put into the frame. If a value for $y is later determined and added to the frame (by a pattern match or unification that is required to be consistent with this frame), the previously bound $x will refer to this value.
list($x, "a") と list(list("b", $y), $z) のユニフィケーションを考えてみましょう。 $x $=$ list("b", $y) および "a" $=$ $z は推論できますが、 $x や $y についてこれ以上解くことはできません。このユニフィケーションは失敗しません。 $x と $y に値を割り当てることで2つのパターンを等しくすることは確かに可能だからです。このマッチは $y が取りうる値を一切制限しないため、 $y の束縛は結果のフレームに入れられません。しかし、このマッチは $x の値を制限します。 $y がどんな値を持っていても、 $x は list("b", $y) でなければなりません。したがって、 $x からパターン list("b", $y) への束縛がフレームに入れられます。もし $y の値が後から（このフレームと矛盾しないことが要求されるパターンマッチまたはユニフィケーションによって）決定されフレームに追加された場合、以前に束縛された $x はその値を参照します。
[6]

Applying rules
ルールの適用

Unification is the key to the component of the query system that makes inferences from rules. To see how this is accomplished, consider processing a query that involves applying a rule, such as
ユニフィケーションは、クエリシステムにおいてルールから推論を行うコンポーネントの鍵です。これがどのように実現されるかを見るために、ルールの適用を伴うクエリの処理を考えてみましょう。例えば次のようなものです。 
lives_near($x, list("Hacker", "Alyssa", "P"))
To process this query, we first use the ordinary pattern-match function described above to see if there are any assertions in the data base that match this pattern. (There will not be any in this case, since our data base includes no direct assertions about who lives near whom.) The next step is to attempt to unify the query pattern with the conclusion of each rule. We find that the pattern unifies with the conclusion of the rule
このクエリを処理するには、まず上で説明した通常のパターンマッチ 関数 を使って、このパターンにマッチするアサーションがデータベースにあるかどうかを調べます。（この場合、誰が誰の近くに住んでいるかについての直接的なアサーションはデータベースに含まれていないため、見つかりません。）次のステップは、クエリパターンを各ルールの結論とユニファイしようと試みることです。パターンは次のルールの結論とユニファイできることが分かります。 
rule(lives_near($person_1, $person_2),
     and(address($person_1, pair($town, $rest_1)),
         address($person_2, list($town, $rest_2)),
         not(same($person_1, $person_2))))
resulting in a frame specifying that $x should be bound to (have the same value as) $person_1 and that $person_2 is bound to list("Hacker", "Alyssa", "P"). Now, relative to this frame, we evaluate the compound query given by the body of the rule. Successful matches will extend this frame by providing a binding for $person_1, and consequently a value for $x, which we can use to instantiate the original query pattern.
その結果、 $xが$person_1に束縛される（同じ値を持つ）べきであり、$person_2がlist("Hacker", "Alyssa", "P")に束縛される ことを指定するフレームが得られます。次に、このフレームを基準として、ルールの本体で与えられた複合クエリを評価します。マッチが成功すると、 $person_1 の束縛を提供することでこのフレームを拡張し、その結果 $x の値が得られ、これを使って元のクエリパターンをインスタンス化できます。

In general, the query evaluator uses the following method to apply a rule when trying to establish a query pattern in a frame that specifies bindings for some of the pattern variables:
  • Unify the query with the conclusion of the rule to form, if successful, an extension of the original frame.
  • Relative to the extended frame, evaluate the query formed by the body of the rule.
一般に、クエリ評価器は、パターン変数の一部に束縛を指定するフレーム内でクエリパターンを確立しようとする際に、次の方法でルールを適用します。
  • クエリをルールの結論とユニファイし、成功すれば元のフレームの拡張を形成します。
  • 拡張されたフレームを基準として、ルールの本体によって形成されるクエリを評価します。

Notice how similar this is to the method for applying a function in the evaluate/apply evaluator for JavaScript:
  • Bind the function's parameters to its arguments to form a frame that extends the original function environment.
  • Relative to the extended environment, evaluate the expression formed by the body of the function.
The similarity between the two evaluators should come as no surprise. Just as function definitions are the means of abstraction in JavaScript, rule definitions are the means of abstraction in the query language. In each case, we unwind the abstraction by creating appropriate bindings and evaluating the rule or function body relative to these.
これが、 evaluate/apply の JavaScript 評価器における 関数 の適用方法とどれほど似ているかに注目してください。
  • 関数 のパラメータをその引数に束縛して、元の 関数 の環境を拡張するフレームを形成します。
  • 拡張された環境を基準として、 関数 の本体によって形成される式を評価します。
2つの評価器の類似性は驚くべきことではありません。 JavaScript において 関数 の定義が抽象化の手段であるのと同様に、クエリ言語においてはルールの定義が抽象化の手段です。いずれの場合も、適切な束縛を作成し、それらを基準としてルールまたは 関数 の本体を評価することで、抽象を展開します。

Simple queries
単純クエリ

We saw earlier in this section how to evaluate simple queries in the absence of rules. Now that we have seen how to apply rules, we can describe how to evaluate simple queries by using both rules and assertions.
この節の前半で、ルールがない場合に単純クエリをどのように評価するかを見ました。ルールの適用方法が分かったので、ルールとアサーションの両方を使って単純クエリを評価する方法を説明できます。

Given the query pattern and a stream of frames, we produce, for each frame in the input stream, two streams:
  • a stream of extended frames obtained by matching the pattern against all assertions in the data base (using the pattern matcher), and
  • a stream of extended frames obtained by applying all possible rules (using the unifier).
Appending these two streams produces a stream that consists of all the ways that the given pattern can be satisfied consistent with the original frame. These streams (one for each frame in the input stream) are now all combined to form one large stream, which therefore consists of all the ways that any of the frames in the original input stream can be extended to produce a match with the given pattern.
クエリパターンとフレームのストリームが与えられると、入力ストリーム内の各フレームに対して、2つのストリームを生成します。
  • パターンをデータベース内のすべてのアサーションに対してマッチさせる（パターンマッチャーを使う）ことで得られる拡張フレームのストリーム
  • 適用可能なすべてのルールを適用する（ユニファイアを使う）ことで得られる拡張フレームのストリーム
これらの2つのストリームを結合すると、与えられたパターンが元のフレームと矛盾なく満たされるすべての方法からなるストリームが得られます。これらのストリーム（入力ストリーム内の各フレームに1つ）はすべて結合されて1つの大きなストリームを形成し、そのストリームは元の入力ストリーム内の任意のフレームを拡張して与えられたパターンとのマッチを生成できるすべての方法からなります。
[7]

The query evaluator and the driver loop
クエリ評価器とドライバループ

Despite the complexity of the underlying matching operations, the system is organized much like an evaluator for any language. The function that coordinates the matching operations is called evaluate_query, and it plays a role analogous to that of the evaluate function for JavaScript. The function evaluate_query takes as inputs a query and a stream of frames. Its output is a stream of frames, corresponding to successful matches to the query pattern, that extend some frame in the input stream, as indicated in figure 4.8. Like evaluate, evaluate_query classifies the different types of expressions (queries) and dispatches to an appropriate function for each. There is a function for each syntactic form (and, or, not, and javascript_predicate) and one for simple queries.
基盤となるマッチング操作の複雑さにもかかわらず、システムは他の言語の 評価器と同じように構成されています。マッチング操作を統括する 関数 は evaluate_query と呼ばれ、 JavaScript の evaluate 関数 と同様の役割を果たします。 関数evaluate_query はクエリとフレームのストリームを入力として受け取ります。その出力は、 figure 4.8 に示すように、入力ストリーム内のあるフレームを拡張する、クエリパターンへの成功したマッチに対応するフレームのストリームです。 evaluate と同様に、 evaluate_query は異なる種類の式（クエリ）を分類し、それぞれに対して適切な 関数 にディスパッチします。各 構文 形式（and、or、not、および javascript_predicate） に対する 関数 と、単純クエリ用の 関数 が1つあります。

The driver loop, which is analogous to the driver_loop function for the other evaluators in this chapter, reads queries typed by the user. For each query, it calls evaluate_query with the query and a stream that consists of a single empty frame. This will produce the stream of all possible matches (all possible extensions to the empty frame). For each frame in the resulting stream, it instantiates the original query using the values of the variables found in the frame. This stream of instantiated queries is then printed.
ドライバループは、この章の他の評価器における driver_loop 関数 に類似しており、 ユーザーが入力した クエリを読み取ります。各クエリに対して、クエリと単一の空フレームからなるストリームを引数として evaluate_query を呼び出します。これにより、すべての可能なマッチ（空フレームのすべての可能な拡張）のストリームが生成されます。結果のストリーム内の各フレームに対して、フレーム内で見つかった変数の値を使って元のクエリをインスタンス化します。このインスタンス化されたクエリのストリームが表示されます。

ドライバは特別なコマンド assert もチェックします。これは、入力がクエリではなくデータベースに追加されるアサーションまたはルールであることを示します。例えば次のようになります。 
assert(job(list("Bitdiddle", "Ben"), list("computer", "wizard")))

assert(rule(wheel($person),
            and(supervisor($middle_manager, $person),

With care, we can arrange our data base so that some of the work of coarse matching can be done when the data base is constructed rather then when we want to select the candidates. Since unification is a generalization of matching, we could simplify the system by using the unifier to produce both streams. Treating the easy case with the simple matcher, however, illustrates how matching (as opposed to full-blown unification) can be useful in its own right.
ユニフィケーションはマッチングの一般化であるため、 ユニファイアを使って両方のストリームを生成することでシステムを簡略化できます。しかし、簡単なケースを単純なマッチャで扱うことは、（本格的なユニフィケーションに対して）マッチングがそれ自体で有用であることを示しています。

The reason we use streams (rather than lists) of frames is that the recursive application of rules can generate infinite numbers of values that satisfy a query. The delayed evaluation embodied in streams is crucial here: The system will print responses one by one as they are generated, regardless of whether there are a finite or infinite number of responses.
フレームに（リストではなく） ストリームを使う理由は、ルールの再帰的な適用がクエリを満たす無限個の値を生成しうるからです。ストリームに組み込まれた遅延評価がここでは重要です。応答が有限個か無限個かにかかわらず、システムは応答が生成されるたびに1つずつ表示します。
