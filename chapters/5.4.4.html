5.4.4  
Running the Evaluator
評価器の実行

With the implementation of the explicit-control evaluator we come to the end of a development, begun in chapter 1, in which we have explored successively more precise models of the evaluation process. We started with the relatively informal substitution model, then extended this in chapter 3 to the environment model, which enabled us to deal with state and change. In the metacircular evaluator of chapter 4, we used JavaScript itself as a language for making more explicit the environment structure constructed during evaluation of an component. Now, with register machines, we have taken a close look at the evaluator's mechanisms for storage management, argument passing, and control. At each new level of description, we have had to raise issues and resolve ambiguities that were not apparent at the previous, less precise treatment of evaluation. To understand the behavior of the explicit-control evaluator, we can simulate it and monitor its performance.
明示的制御評価器の実装をもって、第 1章で始めた一連の開発の締めくくりとなります。この開発の中で、私たちは評価プロセスのモデルを段階的により精密なものにしてきました。 まず比較的非形式的な置換モデルから始め、次に第 3章で環境モデルに拡張して状態と変化を扱えるようにしました。第 4章のメタ循環評価器では、 JavaScript 自体を言語として使い、 コンポーネント の評価中に構築される環境構造をより明確にしました。そして今、レジスタマシンを用いることで、評価器の記憶管理、引数渡し、制御の仕組みを詳しく見てきました。記述の各段階で、以前のより不正確な扱いでは明らかでなかった問題を提起し、あいまいさを解消する必要がありました。明示的制御評価器の動作を理解するために、シミュレーションを行い、その性能を監視することができます。

We will install a driver loop in our evaluator machine. This plays the role of the driver_loop function of section 4.1.4. The evaluator will repeatedly print a prompt, read a program, evaluate the program by going to eval_dispatch, and print the result. If nothing is entered at the prompt, we jump to the label evaluator_done, which is the last entry point in the controller. The following instructions form the beginning of the explicit-control evaluator's controller sequence:
評価器マシンに ドライバループを組み込みます。これは 4.1.4節の driver_loop 関数 と同じ役割を果たします。評価器はプロンプトを表示し、 プログラムを読み込み、 eval_dispatch に移って プログラム を評価し、結果を表示するという動作を繰り返します。 プロンプトで何も入力されなかった場合は、コントローラの最後のエントリポイントであるラベル evaluator_done にジャンプします。 以下の命令列は、明示的制御評価器のコントローラ列の先頭を構成します。
[1] "read_evaluate_print_loop", perform(list(op("initialize_stack"))), assign("comp", list(op("user_read"), constant("EC-evaluate input:"))), assign("comp", list(op("parse"), reg("comp"))), test(list(op("is_null"), reg("comp"))), branch(label("evaluator_done")), assign("env", list(op("get_current_environment"))), assign("val", list(op("scan_out_declarations"), reg("comp"))), save("comp"), // so we can use it to temporarily hold $\texttt{*unassigned*}$ values assign("comp", list(op("list_of_unassigned"), reg("val"))), assign("env", list(op("extend_environment"), reg("val"), reg("comp"), reg("env"))), perform(list(op("set_current_environment"), reg("env"))), restore("comp"), // the program assign("continue", label("print_result")), go_to(label("eval_dispatch")), "print_result", perform(list(op("user_print"), constant("EC-evaluate value:"), reg("val"))), go_to(label("read_evaluate_print_loop")),
We store the current environment, initially the global environment, in the variable current_environment and update it each time around the loop to remember past declarations. The operations get_current_environment and set_current_environment simply get and set this variable.
現在の環境（初期値はグローバル環境）を変数 current_environment に格納し、ループを回るたびに更新して過去の宣言を記憶します。操作 get_current_environment と set_current_environment は、単にこの変数を取得および設定するだけです。 
let current_environment = the_global_environment;

function get_current_environment() {
    return current_environment;
}

function set_current_environment(env) {
    current_environment = env;
}

When we encounter an error in a function (such as the unknown function type error indicated at apply_dispatch), we print an error message and return to the driver loop.
関数 でエラーに遭遇した場合（たとえば apply_dispatch で示される unknown function type エラー）、 エラーメッセージを表示してドライバループに戻ります。
[2] "unknown_component_type", assign("val", constant("unknown syntax")), go_to(label("signal_error")), "unknown_function_type", restore("continue"), // clean up stack (from $\texttt{apply_dispatch}$) assign("val", constant("unknown function type")), go_to(label("signal_error")), "signal_error", perform(list(op("user_print"), constant("EC-evaluator error:"), reg("val"))), go_to(label("read_evaluate_print_loop")),

For the purposes of the simulation, we initialize the stack each time through the driver loop, since it might not be empty after an error (such as an undeclared name) interrupts an evaluation.
シミュレーションのために、ドライバループを通過するたびにスタックを初期化します。エラー （未宣言の名前など） によって評価が中断された後は、スタックが空でない可能性があるためです。
[3]

If we combine all the code fragments presented in sections 5.4.1–5.4.4, we can create an evaluator machine model that we can run using the register-machine simulator of section 5.2.
5.4.1節から5.4.4節までに示したすべてのコード断片を組み合わせると、  5.2節のレジスタマシンシミュレータで実行できる評価器マシンモデルを作成できます。
const eceval = make_machine(list("comp", "env", "val", "fun", "argl", "continue", "unev"), eceval_operations, list("read_evaluate_print_loop", $\langle{}$entire machine controller as given above$\rangle$ "evaluator_done"));
We must define JavaScript functions to simulate the operations used as primitives by the evaluator. These are the same functions we used for the metacircular evaluator in section 4.1, together with the few additional ones defined in footnotes throughout section 5.4.
評価器がプリミティブとして使用する操作をシミュレートするために、 JavaScript の関数 を定義する必要があります。これらは 4.1節のメタ循環評価器で使用した 関数 と同じもので、 5.4節全体の脚注で定義されたいくつかの追加のものも含みます。
const eceval_operations = list(list("is_literal", is_literal), $\langle\mathit{complete}\;\,\mathit{list}\;\,\mathit{of}\;\mathit{operations}\:\,\mathit{for}\;\,\mathit{eceval}\;\,\mathit{machine}\rangle$);

Finally, we can initialize the global environment and run the evaluator:
最後に、グローバル環境を初期化して評価器を実行できます。
const the_global_environment = setup_environment();
start(eceval);

EC-evaluate input:
function append(x, y) {
    return is_null(x)	
           ? y
           : pair(head(x), append(tail(x), y));
}
EC-evaluate value:
undefined
EC-evaluate input:
append(list("a", "b", "c"), list("d", "e", "f"));
EC-evaluate value:
["a", ["b", ["c", ["d", ["e", ["f", null]]]]]]

Of course, evaluating programs in this way will take much longer than if we had directly typed them into JavaScript, because of the multiple levels of simulation involved. Our programs are evaluated by the explicit-control-evaluator machine, which is being simulated by a JavaScript program, which is itself being evaluated by the JavaScript interpreter.
もちろん、この方法で プログラム を評価すると、 JavaScript に直接入力した場合よりもはるかに時間がかかります。なぜなら、複数段階のシミュレーションが関わるためです。私たちの プログラム は明示的制御評価器マシンによって評価され、そのマシンは JavaScript プログラムによってシミュレートされ、そのプログラム自体が JavaScript インタプリタによって評価されているのです。

Monitoring the performance of the evaluator
評価器の性能のモニタリング

Simulation can be a powerful tool to guide the implementation of evaluators. Simulations make it easy not only to explore variations of the register-machine design but also to monitor the performance of the simulated evaluator. For example, one important factor in performance is how efficiently the evaluator uses the stack. We can observe the number of stack operations required to evaluate various programs by defining the evaluator register machine with the version of the simulator that collects statistics on stack use (section 5.2.4), and adding an instruction at the evaluator's print_result entry point to print the statistics:
シミュレーションは、評価器の実装を導くための強力なツールとなりえます。 シミュレーションによって、レジスタマシン設計のバリエーションを探索するだけでなく、シミュレートされた評価器の性能をモニタリングすることも容易になります。たとえば、性能における重要な要因の一つは、評価器がスタックをどれだけ効率的に使用するかです。スタック使用量の統計を収集するバージョンのシミュレータ（5.2.4節）で評価器のレジスタマシンを定義し、評価器の print_result エントリポイントに統計を表示する命令を追加することで、さまざまな プログラム の評価に必要なスタック操作の回数を観察できます。
"print_result", perform(list(op("print_stack_statistics"))), // added instruction // rest is same as before perform(list(op("user_print"), constant("EC-evaluate value:"), reg("val"))), go_to(label("read_evaluate_print_loop")),
Interactions with the evaluator now look like this:
評価器とのやり取りは次のようになります。
EC-evaluate input:
function factorial (n) {
    return n === 1
           ? 1
           : factorial(n - 1) * n;
}
total pushes = 4 
maximum depth = 3
EC-evaluate value:
undefined
EC-evaluate input:
factorial(5);
total pushes = 151 
maximum depth = 28
EC-evaluate value:
120
Note that the driver loop of the evaluator reinitializes the stack at the start of each interaction, so that the statistics printed will refer only to stack operations used to evaluate the previous program.
評価器のドライバループは各やり取りの開始時にスタックを再初期化するため、表示される統計は直前の プログラム の評価に使用されたスタック操作のみを参照することに注意してください。

Exercise 5.27
Use the monitored stack to explore the tail-recursive property of the evaluator (section 5.4.2). Start the evaluator and define the iterative factorial function from section 1.2.1:
モニタ付きスタックを使って、評価器の 末尾再帰特性（5.4.2節）を調べてください。評価器を起動し、1.2.1節の 反復的な factorial 関数 を定義してください。 
function factorial(n) {
    function iter(product, counter) {
        return counter > n
               ? product
               : iter(counter * product,
                      counter + 1);
    }
    return iter(1, 1);
}
Run the function with some small values of $n$. Record the maximum stack depth and the number of pushes required to compute $n!$ for each of these values.
  1. You will find that the maximum depth required to evaluate $n!$ is independent of $n$. What is that depth?
  2. Determine from your data a formula in terms of $n$ for the total number of push operations used in evaluating $n!$ for any $n \geq 1$. Note that the number of operations used is a linear function of $n$ and is thus determined by two constants.
この 関数 をいくつかの小さな $n$ の値で実行してください。それぞれの値について、$n!$ の計算に必要なスタックの最大深さとプッシュ回数を記録してください。
  1. $n!$ の評価に必要な最大深さは $n$ に依存しないことがわかるでしょう。その深さはいくつですか？
  2. データから、任意の $n \geq 1$ に対して $n!$ の評価に使用されるプッシュ操作の総数を $n$ の式で表す公式を求めてください。使用される操作の数は $n$ の線形関数であり、したがって2つの定数で決まることに注意してください。
There is currently no solution available for this exercise. This textbook adaptation is a community effort. Do consider contributing by providing a solution for this exercise, using a Pull Request in Github.

Exercise 5.30
Our evaluator currently catches and signals only two kinds of errors—unknown component types and unknown function types. Other errors will take us out of the evaluator read-evaluate-print loop. When we run the evaluator using the register-machine simulator, these errors are caught by the underlying JavaScript system. This is analogous to the computer crashing when a user program makes an error.
現在の評価器は、未知の コンポーネント 型と未知の 関数 型という2種類のエラーのみを捕捉して通知します。それ以外のエラーは、評価器の read-evaluate-print ループから抜け出してしまいます。レジスタマシンシミュレータを使って評価器を実行する場合、これらのエラーは基盤となる JavaScript システムによって捕捉されます。これは、ユーザープログラムがエラーを起こしたときにコンピュータがクラッシュするのと同様です。
[4]
It is a large project to make a real error system work, but it is well worth the effort to understand what is involved here.
  1. Errors that occur in the evaluation process, such as an attempt to access an unbound name, could be caught by changing the lookup operation to make it return a distinguished condition code, which cannot be a possible value of any user name. The evaluator can test for this condition code and then do what is necessary to go to signal_error. Find all of the places in the evaluator where such a change is necessary and fix them. This is lots of work.
  2. Much worse is the problem of handling errors that are signaled by applying primitive functions such as an attempt to divide by zero or an attempt to extract the head of a string. In a professionally written high-quality system, each primitive application is checked for safety as part of the primitive. For example, every call to head could first check that the argument is a pair. If the argument is not a pair, the application would return a distinguished condition code to the evaluator, which would then report the failure. We could arrange for this in our register-machine simulator by making each primitive function check for applicability and returning an appropriate distinguished condition code on failure. Then the primitive_apply code in the evaluator can check for the condition code and go to signal_error if necessary. Build this structure and make it work. This is a major project.
本格的なエラーシステムを動作させるのは大きなプロジェクトですが、ここで何が関わっているかを理解する価値は十分にあります。
  1. 束縛されていない 名前 にアクセスしようとするなど、評価プロセスで発生するエラーは、ルックアップ操作を変更して、ユーザーの 名前 の値としてありえない特別な条件コードを返すようにすることで捕捉できます。評価器はこの条件コードを検査して、 signal_error に移行するために必要な処理を行えます。評価器のどこでこのような変更が必要かをすべて見つけて修正してください。これは多大な作業です。
  2. さらに厄介なのは、プリミティブな 関数 の適用時に通知されるエラーの処理です。たとえば、ゼロによる除算や、 文字列の head を取得しようとする場合です。プロフェッショナルに書かれた高品質なシステムでは、各プリミティブの適用はプリミティブの一部として安全性がチェックされます。たとえば、 head の呼び出しのたびに、まず引数がペアであることをチェックできます。引数がペアでなければ、適用は特別な条件コードを評価器に返し、評価器が失敗を報告します。レジスタマシンシミュレータでは、各プリミティブ 関数 に適用可能かどうかをチェックさせ、失敗時に適切な特別な条件コードを返すようにすることでこれを実現できます。そうすれば、評価器の primitive_apply コードが条件コードをチェックして、必要に応じて signal_error に移行できます。この構造を構築して動作させてください。これは大きなプロジェクトです。
