3.5.1  
Streams Are Delayed Lists
ストリームは遅延リスト

As we saw in section 2.2.3, sequences can serve as standard interfaces for combining program modules. We formulated powerful abstractions for manipulating sequences, such as map, filter, and accumulate, that capture a wide variety of operations in a manner that is both succinct and elegant.
2.2.3節で見たように、シーケンスはプログラムのモジュールを組み合わせるための標準的なインターフェースとして機能します。私たちはシーケンスを操作するための強力な抽象化、たとえばmap、filter、accumulateといったものを定式化し、多種多様な演算を簡潔かつエレガントな方法で捉えることができました。

Unfortunately, if we represent sequences as lists, this elegance is bought at the price of severe inefficiency with respect to both the time and space required by our computations. When we represent manipulations on sequences as transformations of lists, our programs must construct and copy data structures (which may be huge) at every step of a process.
残念ながら、シーケンスをリストとして表現すると、このエレガントさは計算に必要な時間と空間の両面で著しい非効率さという代償を払って手に入れることになります。シーケンスの操作をリストの変換として表現すると、プログラムはプロセスの各ステップで（場合によっては巨大な）データ構造を構築したりコピーしたりしなければなりません。

To see why this is true, let us compare two programs for computing the sum of all the prime numbers in an interval. The first program is written in standard iterative style:
この理由を理解するために、ある区間に含まれるすべての素数の合計を計算する 2 つのプログラムを比較してみましょう。最初のプログラムは標準的な反復的スタイルで書かれています。
[1] 
function sum_primes(a, b) {
    function iter(count, accum) {
        return count > b
               ? accum
               : is_prime(count)
               ? iter(count + 1, count + accum)
               : iter(count + 1, accum);
    }
    return iter(a, 0);
}
The second program performs the same computation using the sequence operations of section 2.2.3:
2 番目のプログラムは2.2.3節のシーケンス演算を使って同じ計算を行います。 
function sum_primes(a, b) {
    return accumulate((x, y) => x + y,
                      0,
                      filter(is_prime, 
                             enumerate_interval(a, b)));
}

In carrying out the computation, the first program needs to store only the sum being accumulated. In contrast, the filter in the second program cannot do any testing until enumerate_interval has constructed a complete list of the numbers in the interval. The filter generates another list, which in turn is passed to accumulate before being collapsed to form a sum. Such large intermediate storage is not needed by the first program, which we can think of as enumerating the interval incrementally, adding each prime to the sum as it is generated.
計算を実行する際、最初のプログラムは累積中の合計値だけを保持していれば十分です。それに対して、2 番目のプログラムのフィルタは、enumerate_intervalが区間内の数のリストを完全に構築し終えるまで、何のテストも行えません。フィルタはさらに別のリストを生成し、それがaccumulateに渡され、最後に畳み込まれて合計値になります。このような大きな中間ストレージは最初のプログラムには不要で、こちらは区間を少しずつ列挙しながら、生成された素数をその場で合計に加えていくものと考えられます。

The inefficiency in using lists becomes painfully apparent if we use the sequence paradigm to compute the second prime in the interval from 10,000 to 1,000,000 by evaluating the expression
リストを使うことの非効率さは、シーケンスパラダイムを使って 10,000 から 1,000,000 の区間における 2 番目の素数を、次の式を評価して求めようとすると痛感することになります。 
head(tail(filter(is_prime,
                 enumerate_interval(10000, 1000000))));
This expression does find the second prime, but the computational overhead is outrageous. We construct a list of almost a million integers, filter this list by testing each element for primality, and then ignore almost all of the result. In a more traditional programming style, we would interleave the enumeration and the filtering, and stop when we reached the second prime.
この式はたしかに 2 番目の素数を見つけてくれますが、その計算オーバーヘッドは途方もないものです。100 万近い整数のリストを構築し、各要素の素数性をテストしてリストをフィルタにかけ、そして結果のほとんどすべてを捨ててしまうのです。もっと伝統的なプログラミングスタイルであれば、列挙とフィルタリングをインターリーブさせ、2 番目の素数に到達した時点で止めるでしょう。

Streams are a clever idea that allows one to use sequence manipulations without incurring the costs of manipulating sequences as lists. With streams we can achieve the best of both worlds: We can formulate programs elegantly as sequence manipulations, while attaining the efficiency of incremental computation. The basic idea is to arrange to construct a stream only partially, and to pass the partial construction to the program that consumes the stream. If the consumer attempts to access a part of the stream that has not yet been constructed, the stream will automatically construct just enough more of itself to produce the required part, thus preserving the illusion that the entire stream exists. In other words, although we will write programs as if we were processing complete sequences, we design our stream implementation to automatically and transparently interleave the construction of the stream with its use.
ストリームは、シーケンスをリストとして操作する際のコストを払わずに シーケンス操作を使えるようにする巧妙なアイデアです。ストリームを使えば 両方の良いところ取りができます。プログラムをシーケンス操作として エレガントに定式化しながら、インクリメンタルな計算の効率性を 手に入れられるのです。基本的なアイデアは、ストリームを部分的にだけ 構築するようにしておき、その部分的な構築物をストリームを消費する プログラムに渡すことです。消費側がまだ構築されていない部分に アクセスしようとすると、ストリームは必要な部分を生成するのに ちょうど十分なだけ自分自身を自動的に構築し、それによってストリーム全体が 存在しているかのような錯覚を保ちます。言い換えると、あたかも完全な シーケンスを処理しているかのようにプログラムを書きますが、ストリームの 実装の方では、ストリームの構築とその利用が自動的かつ透過的に 交互に行われるように設計するのです。

To accomplish this, we will construct streams using pairs, with the first item of the stream in the head of the pair. However, rather than placing the value of the rest of the stream into the tail of the pair, we will put there a promise to compute the rest if it is ever requested. If we have a data item h and a stream t, we construct a stream whose head is h and whose tail is t by evaluating pair(h, () => t)—the tail t of a stream is wrapped in a function of no arguments, so that its evaluation will be delayed. The empty stream is null, the same as the empty list.
これを実現するために、ペアを使ってストリームを構築します。 ストリームの最初の要素をペアの head に入れるのです。 ただし、ストリームの残りの値をペアの tail に直接入れるのではなく、 要求されたときに残りを計算するためのプロミスをそこに入れます。 データ項目 hとストリーム tがあるとき、head が hで tail が tであるストリームは、 pair(h, () => t)を評価することで構築します— ストリームの tail tは引数なしの関数で ラップされており、 その評価が遅延されるようになっています。 空のストリームは nullであり、空のリストと同じです。

To access the first data item of a nonempty stream, we simply select the head of the pair, as with a list. But to access the tail of a stream, we need to evaluate the delayed expression. For convenience, we define
空でないストリームの先頭のデータ項目にアクセスするには、リストと同じようにペアのheadを選択するだけです。しかしストリームの末尾にアクセスするには、遅延された式を評価する必要があります。便宜上、次の関数を定義します。 
function stream_tail(stream) {
    return tail(stream)();
}
This selects the tail of the pair and applies the function found there to obtain the next pair of the stream (or null if the tail of the stream is empty)—in effect, forcing the function in the tail of the pair to fulfill its promise.
これはペアの末尾を取り出し、そこにある関数を適用してストリームの次のペア（またはストリームの末尾が空であればnull）を得るものです—つまり、ペアの末尾にある関数にプロミスを果たさせるよう強制（forcing）するわけです。

We can make and use streams, in just the same way as we can make and use lists, to represent aggregate data arranged in a sequence. In particular, we can build stream analogs of the list operations from chapter 2, such as list_ref, map, and for_each:
ストリームを作って使う方法は、シーケンスとして並んだ集約データを表現するためにリストを作って使う方法とまったく同じです。特に、章 2のリスト操作（list_ref、map、for_eachなど）に対応するストリーム版を構築できます。
[2] 
function stream_ref(s, n) {
    return n === 0
           ? head(s)
           : stream_ref(stream_tail(s), n - 1);
}
function stream_map(f, s) {
    return is_null(s)
           ? null
           : pair(f(head(s)),
                  () => stream_map(f, stream_tail(s)));
}
function stream_for_each(fun, s) {
    if (is_null(s)) {
        return true;
    } else {
        fun(head(s));
        return stream_for_each(fun, stream_tail(s));
    }
}
The function stream_for_each is useful for viewing streams:
関数stream_for_eachはストリームの内容を見るのに便利です。 
function display_stream(s) {
    return stream_for_each(display, s);
}

To make the stream implementation automatically and transparently interleave the construction of a stream with its use, we have arranged for the tail of a stream to be evaluated when it is accessed by the stream_tail function rather than when the stream is constructed by pair. This implementation choice is reminiscent of our discussion of rational numbers in section 2.1.2, where we saw that we can choose to implement rational numbers so that the reduction of numerator and denominator to lowest terms is performed either at construction time or at selection time. The two rational-number implementations produce the same data abstraction, but the choice has an effect on efficiency. There is a similar relationship between streams and ordinary lists. As a data abstraction, streams are the same as lists. The difference is the time at which the elements are evaluated. With ordinary lists, both the head and the tail are evaluated at construction time. With streams, the tail is evaluated at selection time.
ストリームの実装で、ストリームの構築とその使用が自動かつ透過的に交互に行われるようにするために、ストリームの末尾はpairによってストリームが構築されるときではなく、stream_tail関数によってアクセスされるときに評価されるよう取り決めました。この実装上の選択は、2.1.2節で有理数について議論したことを思い出させます。そこでは、分子と分母を既約分数に約分する処理を、構築時か選択時のどちらで行うかを選べるという話をしました。2 つの有理数の実装は同じデータ抽象を生み出しますが、選択は効率に影響を与えます。ストリームと通常のリストの間にも似た関係があります。データ抽象としては、ストリームはリストと同じです。違いは要素が評価されるタイミングです。通常のリストでは、headとtailのどちらも構築時に評価されます。ストリームでは、tailは選択時に評価されます。

Streams in action
ストリームの実例

To see how this data structure behaves, let us analyze the outrageous prime computation we saw above, reformulated in terms of streams:
このデータ構造がどのようにふるまうかを見るために、先ほど見たとんでもない素数計算を、ストリームを使った形に書き直して分析してみましょう。 
head(stream_tail(stream_filter(
                     is_prime,
                     stream_enumerate_interval(10000, 1000000))));
We will see that it does indeed work efficiently.
これが実際に効率よく動作することを見ていきます。

We begin by calling stream_enumerate_interval with the arguments 10,000 and 1,000,000. The function stream_enumerate_interval is the stream analog of enumerate_interval (section 2.2.3):
まず stream_enumerate_interval を引数 10,000 と 1,000,000 で呼び出すところから始めます。関数 stream_enumerate_interval は、 enumerate_interval （2.2.3節） に対応するストリーム版です。 
function stream_enumerate_interval(low, high) {
    return low > high
           ? null
           : pair(low,
                  () => stream_enumerate_interval(low + 1, high)); 
}
and thus the result returned by stream_enumerate_interval, formed by the pair, is
したがって stream_enumerate_interval が返す結果は、pair によって作られる次のようなペアです。
[3] 
pair(10000, () => stream_enumerate_interval(10001, 1000000));
That is, stream_enumerate_interval returns a stream represented as a pair whose head is 10,000 and whose tail is a promise to enumerate more of the interval if so requested. This stream is now filtered for primes, using the stream analog of the filter function (section 2.2.3):
すなわち stream_enumerate_interval は、head が 10,000 で、 tail が「要求されればさらに区間を列挙する」 というプロミスであるようなペアとして表現されたストリームを返します。 このストリームは次に、filter 関数 （2.2.3節）に 対応するストリーム版を使って、素数だけに絞り込まれます。 
function stream_filter(pred, stream) {
    return is_null(stream)
           ? null
           : pred(head(stream))
           ? pair(head(stream),
                  () => stream_filter(pred, stream_tail(stream)))
           : stream_filter(pred, stream_tail(stream));
}
The function stream_filter tests the head of the stream (which is 10,000). Since this is not prime, stream_filter examines the tail of its input stream. The call to stream_tail forces evaluation of the delayed stream_enumerate_interval, which now returns
関数 stream_filter は、ストリームの head（これは 10,000）を調べます。これは素数ではないので、 stream_filter は入力ストリームの tail を調べます。 stream_tail の呼び出しは、遅延された stream_enumerate_interval の評価を強制し、 今度は次のものが返ります。 
pair(10001, () => stream_enumerate_interval(10002, 1000000));
The function stream_filter now looks at the head of this stream, 10,001, sees that this is not prime either, forces another stream_tail, and so on, until stream_enumerate_interval yields the prime 10,007, whereupon stream_filter, according to its definition, returns
関数 stream_filter は今度はこのストリームの head である 10,001 を見て、これも素数ではないと判断し、 再び stream_tail を強制する、という具合に、 stream_enumerate_interval が素数 10,007 を 生み出すまで処理を続けます。そこで stream_filter は、その定義に従って次のものを返します。 
pair(head(stream), 
     () => stream_filter(pred, stream_tail(stream)));
which in this case is
これは、この場合次のようになります。 
pair(10007,
     () => stream_filter(
              is_prime,
              pair(10008,
                   () => stream_enumerate_interval(10009, 1000000))));
This result is now passed to stream_tail in our original expression. This forces the delayed stream_filter, which in turn keeps forcing the delayed stream_enumerate_interval until it finds the next prime, which is 10,009. Finally, the result passed to head in our original expression is
この結果は今度は、元の式の中の stream_tail に渡されます。これは遅延された stream_filter の評価を強制し、 その stream_filter は、次の素数である 10,009 を 見つけるまで、遅延された stream_enumerate_interval を強制し続けます。 最終的に、元の式の中で head に渡される結果は次のようになります。 
pair(10009,
     () => stream_filter(
              is_prime,
              pair(10010,
                   () => stream_enumerate_interval(10011, 1000000))));
The function head returns 10,009, and the computation is complete. Only as many integers were tested for primality as were necessary to find the second prime, and the interval was enumerated only as far as was necessary to feed the prime filter.
関数 head は 10,009 を返し、計算は完了です。 素数性の検査は 2 番目の素数を見つけるのに必要な整数についてだけ行われ、区間の列挙も 素数フィルタに供給するのに必要な範囲までしか行われませんでした。

In general, we can think of delayed evaluation as demand-driven programming, whereby each stage in the stream process is activated only enough to satisfy the next stage. What we have done is to decouple the actual order of events in the computation from the apparent structure of our functions. We write functions as if the streams existed all at once when, in reality, the computation is performed incrementally, as in traditional programming styles.
一般に、遅延評価は 要求駆動プログラミングと考えることができます。ストリーム処理の各段階は、 次の段階を満たすのにちょうど必要な分だけ起動されるのです。私たちが行ったのは、 計算における実際のイベントの順序を、関数の見かけの構造から切り離すことでした。 私たちは、あたかもストリームが一度にすべて存在するかのように関数を書きますが、 実際には、伝統的なプログラミングスタイルと同様に、計算は段階的に実行されているのです。

An optimization
最適化

When we construct stream pairs, we delay the evaluation of their tail expressions by wrapping these expressions in a function. We force their evaluation when needed, by applying the function.
ストリームペアを構築するとき、末尾の式を関数で包むことによって、その評価を遅延します。 必要になったときに、その関数を適用することで評価を強制します。

This implementation suffices for streams to work as advertised, but there is an important optimization that we shall consider where needed. In many applications, we end up forcing the same delayed object many times. This can lead to serious inefficiency in recursive programs involving streams. (See exercise 3.57.) The solution is to build delayed objects so that the first time they are forced, they store the value that is computed. Subsequent forcings will simply return the stored value without repeating the computation. In other words, we implement the construction of stream pairs as a memoized function similar to the one described in exercise 3.27. One way to accomplish this is to use the following function, which takes as argument a function (of no arguments) and returns a memoized version of the function. The first time the memoized function is run, it saves the computed result. On subsequent evaluations, it simply returns the result.
この実装でもストリームは期待通りに動作しますが、必要に応じて検討すべき重要な最適化があります。 多くのアプリケーションでは、同じ遅延されたオブジェクトを何度も強制することになります。 これはストリームを用いた再帰的なプログラムにおいて深刻な非効率につながりかねません （演習 3.57を参照）。 解決策は、遅延されたオブジェクトを、最初に強制されたときに計算された値を保存するように作ることです。 その後の強制では、計算を繰り返すことなく、保存された値を単に返します。 言い換えれば、ストリームペアの構築を、 演習 3.27で説明したものと同様の、メモ化された関数として実装します。 これを実現する一つの方法は、以下の関数を使うことです。 この関数は引数として（引数なしの）関数を取り、その関数のメモ化されたバージョンを返します。 メモ化された関数が最初に実行されるときに、計算された結果を保存します。 その後の評価では、その結果を単に返すだけです。
[4] 
function memo(fun) {	    
    let already_run = false;
    let result = undefined;
    return () => {
               if (!already_run) {
                   result = fun();
                   already_run = true;
                   return result;
               } else {
                   return result;
               }
           };
}

We can make use of memo whenever we construct a stream pair. For example, instead of
ストリームペアを構築するときにはいつでも、memoを利用できます。たとえば、次のかわりに、 
function stream_map(f, s) {
    return is_null(s)
           ? null
           : pair(f(head(s)),
                  () => stream_map(f, stream_tail(s)));
}
we can define an optimized function stream_map as follows:
最適化された関数stream_mapを次のように定義できます。 
function stream_map_optimized(f, s) {
    return is_null(s)
           ? null
           : pair(f(head(s)),
                  memo(() =>
                         stream_map_optimized(f, stream_tail(s))));
}

There are many possible implementations of streams other than the one described in this section. Delayed evaluation, which is the key to making streams practical, was inherent in Algol 60's call-by-name parameter-passing method. The use of this mechanism to implement streams was first described by Landin (1965). Delayed evaluation for streams was introduced into Lisp by Friedman and Wise (1976). In their implementation, cons (the Lisp equivalent of our pair function) always delays evaluating its arguments, so that lists automatically behave as streams. The memoizing optimization is also known as call-by-need. The Algol community would refer to our original delayed objects as call-by-name thunks and to the optimized versions as call-by-need thunks.
本節で説明したもの以外にも、ストリームの実装には多くの可能性があります。 ストリームを実用的にする鍵である遅延評価は、 Algol 60 の 名前呼び（call-by-name）引数渡し方式に内在していました。 この仕組みをストリームの実装に使うことは、 Landin (1965) によって最初に説明されました。 ストリームのための遅延評価を Lisp に導入したのは、 Friedman and Wise (1976) です。彼らの実装では、 cons（Lispにおける pair関数に相当） が常に引数の評価を遅延するため、リストが自動的にストリームのように振る舞います。 このメモ化による最適化は、 必要呼び（call-by-need）としても知られています。 Algolのコミュニティでは、元の遅延されたオブジェクトを 名前呼びサンク（call-by-name thunks）と呼び、最適化されたバージョンを 必要呼びサンク（call-by-need thunks）と呼んでいました。

Exercises such as 3.51 and 3.52 are valuable for testing our understanding of how delayed evaluation works. On the other hand, intermixing delayed evaluation with printing—and, even worse, with assignment—is extremely confusing, and instructors of courses on computer languages have traditionally tormented their students with examination questions such as the ones in this section. Needless to say, writing programs that depend on such subtleties is odious programming style. Part of the power of stream processing is that it lets us ignore the order in which events actually happen in our programs. Unfortunately, this is precisely what we cannot afford to do in the presence of assignment, which forces us to be concerned with time and change.
