2.4  
Multiple Representations for Abstract Data
抽象データの多重表現

We have introduced data abstraction, a methodology for structuring systems in such a way that much of a program can be specified independent of the choices involved in implementing the data objects that the program manipulates. For example, we saw in section 2.1.1 how to separate the task of designing a program that uses rational numbers from the task of implementing rational numbers in terms of the computer language's primitive mechanisms for constructing compound data. The key idea was to erect an abstraction barrier—in this case, the selectors and constructors for rational numbers (make_rat, numer, denom)—that isolates the way rational numbers are used from their underlying representation in terms of list structure. A similar abstraction barrier isolates the details of the functions that perform rational arithmetic (add_rat, sub_rat, mul_rat, and div_rat) from the higher-level functions that use rational numbers. The resulting program has the structure shown in figure 2.2.
私たちはデータ抽象を導入しました。これは、プログラムが操作するデータオブジェクトの実装に関する選択とは独立して、プログラムの大部分を記述できるようにシステムを構造化する方法論です。たとえば、2.1.1節では、有理数を使うプログラムの設計という課題を、複合データを構成するための言語のプリミティブな仕組みを使った有理数の実装という課題から分離する方法を見ました。その鍵となるアイデアは、 抽象バリア—この場合は有理数のセレクタとコンストラクタ（ make_rat、 numer、denom）—を設けて、有理数の使い方をリスト構造による内部表現から隔離することでした。同様の抽象バリアが、有理数の算術演算を行う 関数 （ add_rat、 sub_rat、 mul_rat、 div_rat） の詳細を、有理数を使うより高水準の 関数 から隔離しています。結果として得られるプログラムは、図 2.2に示す構造を持ちます。

These data-abstraction barriers are powerful tools for controlling complexity. By isolating the underlying representations of data objects, we can divide the task of designing a large program into smaller tasks that can be performed separately. But this kind of data abstraction is not yet powerful enough, because it may not always make sense to speak of the underlying representation for a data object.
これらのデータ抽象バリアは、複雑さを制御するための強力なツールです。データオブジェクトの内部表現を隔離することで、大きなプログラムを設計する課題を、個別に遂行できるより小さな課題に分割できます。しかし、この種のデータ抽象はまだ十分に強力ではありません。データオブジェクトの内部表現について語ることが常に意味をなすとは限らないからです。

For one thing, there might be more than one useful representation for a data object, and we might like to design systems that can deal with multiple representations. To take a simple example, complex numbers may be represented in two almost equivalent ways: in rectangular form (real and imaginary parts) and in polar form (magnitude and angle). Sometimes rectangular form is more appropriate and sometimes polar form is more appropriate. Indeed, it is perfectly plausible to imagine a system in which complex numbers are represented in both ways, and in which the functions for manipulating complex numbers work with either representation.
一つには、データオブジェクトに対して有用な表現が複数存在する場合があり、多重表現を扱えるシステムを設計したいかもしれません。簡単な例として、複素数はほぼ同等な二つの方法で表現できます。直交形式（実部と虚部）と極形式（絶対値と偏角）です。直交形式が適切な場合もあれば、極形式が適切な場合もあります。実際、複素数が両方の方法で表現され、複素数を操作する 関数 がどちらの表現でも動作するシステムを想像するのは完全に妥当です。

More importantly, programming systems are often designed by many people working over extended periods of time, subject to requirements that change over time. In such an environment, it is simply not possible for everyone to agree in advance on choices of data representation. So in addition to the data-abstraction barriers that isolate representation from use, we need abstraction barriers that isolate different design choices from each other and permit different choices to coexist in a single program. Furthermore, since large programs are often created by combining preexisting modules that were designed in isolation, we need conventions that permit programmers to incorporate modules into larger systems additively, that is, without having to redesign or reimplement these modules.
さらに重要なことに、プログラミングシステムは多くの人が長期間にわたって作業し、時間とともに変化する要件に従って設計されることがよくあります。そのような環境では、データ表現の選択について全員が事前に合意することは単純に不可能です。そこで、表現と使用を隔離するデータ抽象バリアに加えて、異なる設計上の選択を互いに隔離し、異なる選択が単一のプログラム内で共存できるようにする抽象バリアが必要です。さらに、大規模なプログラムは、独立して設計された既存のモジュールを組み合わせて作られることが多いため、プログラマがモジュールをより大きなシステムに 加法的に（つまり、これらのモジュールを再設計したり再実装したりすることなく）組み込めるような規約が必要です。

In this section, we will learn how to cope with data that may be represented in different ways by different parts of a program. This requires constructing generic functions—functions that can operate on data that may be represented in more than one way. Our main technique for building generic functions will be to work in terms of data objects that have type tags, that is, data objects that include explicit information about how they are to be processed. We will also discuss data-directed programming, a powerful and convenient implementation strategy for additively assembling systems with generic operations.
このセクションでは、プログラムの異なる部分で異なる方法で表現されうるデータに対処する方法を学びます。これには、 ジェネリック関数—複数の方法で表現されうるデータに対して操作できる関数を構築する必要があります。ジェネリック 関数 を構築するための主な技法は、 型タグを持つデータオブジェクト、つまり、どのように処理されるべきかについての明示的な情報を含むデータオブジェクトを扱うことです。また、 データ指向プログラミングについても議論します。これは、ジェネリック演算を持つシステムを加法的に組み立てるための強力で便利な実装戦略です。

We begin with the simple complex-number example. We will see how type tags and data-directed style enable us to design separate rectangular and polar representations for complex numbers while maintaining the notion of an abstract complex-number data object. We will accomplish this by defining arithmetic functions for complex numbers (add_complex, sub_complex, mul_complex, and div_complex) in terms of generic selectors that access parts of a complex number independent of how the number is represented. The resulting complex-number system, as shown in figure 2.29, contains two different kinds of abstraction barriers. The horizontal abstraction barriers play the same role as the ones in figure 2.2. They isolate higher-level operations from lower-level representations. In addition, there is a vertical barrier that gives us the ability to separately design and install alternative representations.
まず、簡単な複素数の例から始めます。型タグとデータ指向スタイルによって、抽象的な 複素数データオブジェクトの概念を維持しながら、複素数の直交表現と極表現を別々に設計できることを見ていきます。これは、複素数がどのように表現されているかに依存しないジェネリックセレクタを使って、複素数の算術 関数 （ add_complex、 sub_complex、 mul_complex、 div_complex） を定義することで実現します。得られる複素数システムは、 図 2.29 に示すように、二種類の 抽象バリアを含んでいます。水平方向の抽象バリアは、図 2.2のものと同じ役割を果たし、高水準の演算を低水準の表現から隔離します。さらに、垂直方向のバリアがあり、代替の表現を別々に設計し導入する能力を与えてくれます。

In section 2.5 we will show how to use type tags and data-directed style to develop a generic arithmetic package. This provides functions (add, mul, and so on) that can be used to manipulate all sorts of numbers and can be easily extended when a new kind of number is needed. In section 2.5.3, we'll show how to use generic arithmetic in a system that performs symbolic algebra.
2.5節では、型タグとデータ指向スタイルを使ってジェネリック算術パッケージを開発する方法を示します。これにより、あらゆる種類の数を操作でき、新しい種類の数が必要になったときに容易に拡張できる 関数 （add、mulなど）が提供されます。2.5.3節では、記号代数を行うシステムでジェネリック算術を使う方法を示します。
