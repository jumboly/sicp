5.5.1  
Structure of the Compiler
コンパイラの構造

In section 4.1.7 we modified our original metacircular interpreter to separate analysis from execution. We analyzed each component to produce an execution function that took an environment as argument and performed the required operations. In our compiler, we will do essentially the same analysis. Instead of producing execution functions, however, we will generate sequences of instructions to be run by our register machine.
4.1.7節では、元のメタ循環インタプリタを修正して、 解析と実行を分離しました。各 コンポーネント を解析して、環境を引数として受け取り必要な操作を実行する実行 関数 を生成しました。コンパイラでも本質的に同じ解析を行います。ただし、実行 関数 を生成する代わりに、レジスタマシンで実行される命令列を生成します。

The function compile is the top-level dispatch in the compiler. It corresponds to the evaluate function of section 4.1.1, the analyze function of section 4.1.7, and the eval_dispatch entry point of the explicit-control-evaluator in section 5.4.1. The compiler, like the interpreters, uses the component-syntax functions defined in section 4.1.2.
関数 compileは、コンパイラにおけるトップレベルのディスパッチです。これは4.1.1節のevaluate 関数 、 4.1.7節の analyze 関数 、そして 5.4.1節の明示的制御評価器における eval_dispatch エントリポイントに対応します。コンパイラはインタプリタと同様に、 4.1.2節で定義された コンポーネント構文関数 を使用します。
[1]
The function compile performs a case analysis on the syntactic type of the component to be compiled. For each type of component, it dispatches to a specialized code generator:
関数compile は、コンパイルする コンポーネント の構文的な型に基づいてケース分析を行います。 コンポーネント の型ごとに、専用の コードジェネレータにディスパッチします： 
function compile(component, target, linkage) {
    return is_literal(component)
           ? compile_literal(component, target, linkage)
           : is_name(component)
           ? compile_name(component, target, linkage)
           : is_application(component)
           ? compile_application(component, target, linkage)
           : is_operator_combination(component)
           ? compile(operator_combination_to_application(component),
                     target, linkage)
           : is_conditional(component)
           ? compile_conditional(component, target, linkage)
           : is_lambda_expression(component)
           ? compile_lambda_expression(component, target, linkage)
           : is_sequence(component)
           ? compile_sequence(sequence_statements(component),
                              target, linkage)
           : is_block(component)
           ? compile_block(component, target, linkage)
           : is_return_statement(component)
           ? compile_return_statement(component, target, linkage)
           : is_function_declaration(component)
           ? compile(function_decl_to_constant_decl(component),
                     target, linkage)
           : is_declaration(component)
           ? compile_declaration(component, target, linkage)
           : is_assignment(component)
           ? compile_assignment(component, target, linkage)
           : error(component, "unknown component type -- compile");
}

Targets and linkages
ターゲットとリンケージ

The function compile and the code generators that it calls take two arguments in addition to the component to compile. There is a target, which specifies the register in which the compiled code is to return the value of the component. There is also a linkage descriptor, which describes how the code resulting from the compilation of the component should proceed when it has finished its execution. The linkage descriptor can require the code to do one of the following three things:
  • proceed to the next instruction in sequence (this is specified by the linkage descriptor "next"),
  • jump to the current value of the continue register as part of returning from a function call (this is specified by the linkage descriptor "return"), or
  • jump to a named entry point (this is specified by using the designated label as the linkage descriptor).
関数compile とそれが呼び出すコードジェネレータは、コンパイルする コンポーネント に加えて2つの引数を受け取ります。1つは ターゲットで、コンパイルされたコードが コンポーネント の値を返すレジスタを指定します。もう1つは リンケージ記述子で、 コンポーネント のコンパイルで生成されたコードが、実行を終えた後にどう進むべきかを記述します。リンケージ記述子は、コードに次の3つのうちいずれかを要求します：
  • 列中の次の命令に進む（これはリンケージ記述子 "next" で指定されます）
  • 関数呼び出しからのリターンの一部として、continueレジスタの現在の値にジャンプする （これはリンケージ記述子 "return" で指定されます）
  • 名前付きエントリポイントにジャンプする（これは指定されたラベルをリンケージ記述子として使うことで指定されます）

For example, compiling the literal 5 with a target of the val register and a linkage of "next" should produce the instruction
たとえば、 リテラル 5 を、ターゲットをvalレジスタ、リンケージを "next" としてコンパイルすると、次の命令が生成されるはずです。 
assign("val", constant(5))
Compiling the same expression with a linkage of "return" should produce the instructions
同じ式をリンケージ "return" でコンパイルすると、次の命令が生成されるはずです。 
assign("val", constant(5)),
go_to(reg("continue"))
In the first case, execution will continue with the next instruction in the sequence. In the second case, we will jump to whatever entry point is stored in the continue register. In both cases, the value of the expression will be placed into the target val register.
最初のケースでは、実行は列中の次の命令に続きます。2番目のケースでは、 continueレジスタに格納されているエントリポイントにジャンプします。 いずれの場合も、式の値はターゲットレジスタvalに格納されます。
Our compiler uses the "return" linkage when compiling the return expression of a return statement. Just as in the explicit-control evaluator, returning from a function call happens in three steps:
  1. reverting the stack to the marker and restoring continue (which holds a continuation set up at the beginning of the function call)
  2. computing the return value and placing it in val
  3. jumping to the entry point in continue
Compilation of a return statement explicitly generates code for reverting the stack and restoring continue. The return expression is compiled with target val and linkage "return" so that the generated code for computing the return value places the return value in val and ends by jumping to continue.
コンパイラは、return文のreturn式をコンパイルするときに"return"リンケージを使用します。 明示的制御評価器と同様に、関数呼び出しからのリターンは3つのステップで行われます：
  1. スタックをマーカーまで戻し、continueを復元する（これは関数呼び出しの最初に設定された継続を保持しています）
  2. 戻り値を計算し、valに格納する
  3. continueのエントリポイントにジャンプする
return文のコンパイルでは、スタックの復帰とcontinueの復元を行うコードを明示的に生成します。 return式は、ターゲットval、リンケージ"return"でコンパイルされるため、 戻り値を計算するための生成コードは戻り値をvalに格納し、 continueにジャンプして終了します。

Instruction sequences and stack usage
命令列とスタックの使用

Each code generator returns an instruction sequence containing the object code it has generated for the component. Code generation for a compound component is accomplished by combining the output from simpler code generators for subcomponents, just as evaluation of a compound component is accomplished by evaluating the subcomponents.
各コードジェネレータは、その コンポーネント に対して生成したオブジェクトコードを含む命令列を返します。 複合コンポーネント のコード生成は、 サブコンポーネント に対するより単純なコードジェネレータの出力を組み合わせることで実現されます。これは、 複合コンポーネント の評価が、 サブコンポーネント を評価することで実現されるのと同じです。

The simplest method for combining instruction sequences is a function called append_instruction_sequences, which takes as arguments two instruction sequences that are to be executed sequentially. It appends them and returns the combined sequence. That is, if $seq_1$ and $seq_2$ are sequences of instructions, then evaluating
命令列を組み合わせる最も単純な方法は、 append_instruction_sequences という 関数 です。 これは順に実行される2つの命令列 を引数として受け取り、それらを連結して結合された列を返します。つまり、$seq_1$と$seq_2$が命令列であるとき、
append_instruction_sequences($seq$$_1$, $seq$$_2$)
produces the sequence
を評価すると、次の列が生成されます。
$seq$$_1$ $seq$$_2$

Whenever registers might need to be saved, the compiler's code generators use preserving, which is a more subtle method for combining instruction sequences. The function preserving takes three arguments: a set of registers and two instruction sequences that are to be executed sequentially. It appends the sequences in such a way that the contents of each register in the set is preserved over the execution of the first sequence, if this is needed for the execution of the second sequence. That is, if the first sequence modifies the register and the second sequence actually needs the register's original contents, then preserving wraps a save and a restore of the register around the first sequence before appending the sequences. Otherwise, preserving simply returns the appended instruction sequences. Thus, for example,
レジスタの退避が必要になる可能性がある場合、コンパイラのコードジェネレータは preservingを使います。これは命令列を組み合わせるためのより巧妙な方法です。 関数preserving は3つの引数、すなわちレジスタの集合と、順に実行される2つの命令列を受け取ります。この関数は、2番目の列の実行に必要であれば、集合内の各レジスタの内容が1番目の列の実行中に保存されるように列を連結します。つまり、1番目の列がレジスタを変更し、2番目の列が実際にそのレジスタの元の内容を必要とする場合、preservingは1番目の列の前後にそのレジスタのsaveとrestoreを挿入してから列を連結します。 そうでなければ、preservingは単に連結された命令列を返します。したがって、たとえば
preserving(list($reg$$_1$, $reg$$_2$), $seq$$_1$, $seq$$_2$)
produces one of the following four sequences of instructions, depending on how $seq$$_1$ and $seq$$_2$ use $reg$$_1$ and $reg$$_2$:
を評価すると、 $seq$$_1$と$seq$$_2$が$reg$$_1$と$reg$$_2$をどのように使うかに応じて、次の4つの命令列のいずれかが生成されます：

\[ \begin{array}{l|l|l|l} \textit{seq}_1 & \texttt{save(}\textit{reg}_1\texttt{),} & \texttt{save(}\textit{reg}_2\texttt{),} & \texttt{save(}\textit{reg}_2\texttt{),} \\ \textit{seq}_2 & \textit{seq}_1 & \textit{seq}_1 & \texttt{save(}\textit{reg}_1\texttt{),} \\ & \texttt{restore(}\textit{reg}_1\texttt{),} & \texttt{restore(}\textit{reg}_2\texttt{),} & \textit{seq}_1 \\ & \textit{seq}_2 & \textit{seq}_2 & \texttt{restore(}\textit{reg}_1\texttt{),} \\ & & & \texttt{restore(}\textit{reg}_2\texttt{),} \\ & & & \textit{seq}_2 \end{array} \]

By using preserving to combine instruction sequences the compiler avoids unnecessary stack operations. This also isolates the details of whether or not to generate save and restore instructions within the preserving function, separating them from the concerns that arise in writing each of the individual code generators. In fact no save or restore instructions are explicitly produced by the code generators, except that the code for calling a function saves continue and the code for returning from a function restores it: These corresponding save and restore instructions are explicitly generated by different calls to compile, not as a matched pair by preserving (as we will see in section 5.5.3).
preservingを使って命令列を組み合わせることで、コンパイラは不要な スタック操作を回避します。これにより、save命令とrestore命令を生成するかどうかの詳細がpreserving 関数 の内部に隔離され、個々のコードジェネレータの記述で生じる関心事から分離されます。 実際、save命令やrestore命令はコード ジェネレータが明示的に生成することはありません。ただし、関数呼び出しのコードがcontinueを退避し、関数からのリターンのコードがそれを復元するという例外があります。これらの対応するsave命令とrestore命令は、preservingによる対として生成されるのではなく、compileへの異なる呼び出しによって明示的に生成されます（5.5.3節で見ることになります）。

In principle, we could represent an instruction sequence simply as a list of instructions. The function append_instruction_sequences could then combine instruction sequences by performing an ordinary list append. However, preserving would then be a complex operation, because it would have to analyze each instruction sequence to determine how the sequence uses its registers. The function preserving would be inefficient as well as complex, because it would have to analyze each of its instruction sequence arguments, even though these sequences might themselves have been constructed by calls to preserving, in which case their parts would have already been analyzed. To avoid such repetitious analysis we will associate with each instruction sequence some information about its register use. When we construct a basic instruction sequence we will provide this information explicitly, and the functions that combine instruction sequences will derive register-use information for the combined sequence from the information associated with the sequences being combined.

An instruction sequence will contain three pieces of information:
  • the set of registers that must be initialized before the instructions in the sequence are executed (these registers are said to be needed by the sequence),
  • the set of registers whose values are modified by the instructions in the sequence, and
  • the actual instructions in the sequence.
We will represent an instruction sequence as a list of its three parts. The constructor for instruction sequences is thus

  • 列中の命令が実行される前に初期化されていなければならないレジスタの集合（これらのレジスタはその列に必要であると言います）
  • 列中の命令によって値が変更されるレジスタの集合
  • 列中の実際の命令
命令列をこれら3つの部分のリストとして表現します。命令列のコンストラクタは次の通りです。 
function make_instruction_sequence(needs, modifies, instructions) {
    return list(needs, modifies, instructions);
}
