5.5.3  
Compiling Applications and Return Statements
関数適用と return 文 のコンパイル

The essence of the compilation process is the compilation of function applications. The code for an application compiled with a given target and linkage has the form
コンパイル処理の本質は、関数適用のコンパイルです。与えられたターゲットとリンケージでコンパイルされた関数適用のコードは、次の形式になります。
$\langle{}$compilation of function expression, target fun, linkage "next"$\rangle$ $\langle{}$evaluate argument expressions and construct argument list in argl$\rangle$ $\langle{}$compilation of function call with given target and linkage$\rangle$
The registers env, fun, and argl may have to be saved and restored during evaluation of the function and argument expressions. Note that this is the only place in the compiler where a target other than val is specified.
レジスタ env、fun、および argl は、関数式と引数式の評価中に退避と復元が必要になる場合があります。コンパイラの中で val 以外のターゲットが指定されるのは、ここだけであることに注意してください。

The required code is generated by compile_application. This recursively compiles the function expression, to produce code that puts the function to be applied into fun, and compiles the argument expressions, to produce code that evaluates the individual argument expressions of the application. The instruction sequences for the argument expressions are combined (by construct_arglist) with code that constructs the list of arguments in argl, and the resulting argument-list code is combined with the function code and the code that performs the function call (produced by compile_function_call). In appending the code sequences, the env register must be preserved around the evaluation of the function expression (since evaluating the function expression might modify env, which will be needed to evaluate the argument expressions), and the fun register must be preserved around the construction of the argument list (since evaluating the argument expressions might modify fun, which will be needed for the actual function application). The continue register must also be preserved throughout, since it is needed for the linkage in the function call.
必要なコードは compile_application によって生成されます。この関数は、適用される関数を fun に格納するコードを生成するために関数式を再帰的にコンパイルし、関数適用の個々の引数式を評価するコードを生成するために引数式をコンパイルします。引数式の命令列は、argl に引数リストを構築するコードと（construct_arglist によって）結合され、その結果の引数リストコードが関数コードおよび関数呼び出しを実行するコード（compile_function_call によって生成）と結合されます。コード列を結合する際、env レジスタは関数式の評価の前後で保存されなければなりません（関数式の評価が env を変更する可能性があり、引数式の評価に必要だからです）。また、fun レジスタは引数リストの構築の前後で保存されなければなりません（引数式の評価が fun を変更する可能性があり、実際の関数適用に必要だからです）。continue レジスタも全体を通じて保存されなければなりません。関数呼び出しのリンケージに必要だからです。 
function compile_application(exp, target, linkage) {
    const fun_code = compile(function_expression(exp), "fun", "next");
    const argument_codes = map(arg => compile(arg, "val", "next"),
                               arg_expressions(exp));
    return preserving(list("env", "continue"),
                      fun_code,
                      preserving(list("fun", "continue"),
                          construct_arglist(argument_codes),
                          compile_function_call(target, linkage)));
}

The code to construct the argument list will evaluate each argument expression into val and then combine that value with the argument list being accumulated in argl using pair. Since we adjoin the arguments to the front of argl in sequence, we must start with the last argument and end with the first, so that the arguments will appear in order from first to last in the resulting list. Rather than waste an instruction by initializing argl to the empty list to set up for this sequence of evaluations, we make the first code sequence construct the initial argl. The general form of the argument-list construction is thus as follows:
引数リストを構築するコードは、各引数式を val に評価し、その値を argl に蓄積されている引数リストと pair を使って結合します。引数を順に argl の先頭に付加するので、最後の引数から始めて最初の引数で終わらなければなりません。こうすることで、結果のリストには引数が先頭から末尾の順に並びます。この一連の評価のために argl を空リストに初期化する命令を無駄にするのではなく、最初のコード列で初期の argl を構築するようにします。したがって、引数リスト構築の一般的な形式は次のようになります。
$\langle{}$compilation of last argument, targeted to val$\rangle$ assign("argl", list(op("list"), reg("val"))), $\langle{}$compilation of next argument, targeted to val$\rangle$ assign("argl", list(op("pair"), reg("val"), reg("argl"))), $\ldots$ $\langle{}$compilation of first argument, targeted to val$\rangle$ assign("argl", list(op("pair"), reg("val"), reg("argl"))),
The argl register must be preserved around each argument evaluation except the first (so that arguments accumulated so far won't be lost), and env must be preserved around each argument evaluation except the last (for use by subsequent argument evaluations).
argl レジスタは各引数の評価の前後で保存されなければなりません。ただし最初の評価は除きます（これまでに蓄積された引数が失われないようにするためです）。また、env は各引数の評価の前後で保存されなければなりません。ただし最後の評価は除きます（後続の引数の評価に使用するためです）。

Compiling this argument code is a bit tricky, because of the special treatment of the first argument expression to be evaluated and the need to preserve argl and env in different places. The construct_arglist function takes as arguments the code that evaluates the individual argument expressions. If there are no argument expressions at all, it simply emits the instruction
この引数コードのコンパイルは少し複雑です。最初に評価される引数式の特別な扱いと、異なる箇所で argl と env を保存する必要があるためです。construct_arglist 関数は、個々の引数式を評価するコードを引数として受け取ります。引数式がまったくない場合は、単に次の命令を出力します。 
assign(argl, constant(null))
Otherwise, construct_arglist creates code that initializes argl with the last argument, and appends code that evaluates the rest of the arguments and adjoins them to argl in succession. In order to process the arguments from last to first, we must reverse the list of argument code sequences from the order supplied by compile_application.
そうでなければ、construct_arglist は最後の引数で argl を初期化するコードを作成し、残りの引数を評価して順次 argl に付加するコードを追加します。引数を最後から最初の順に処理するために、compile_application から供給された順序の引数コード列のリストを反転しなければなりません。 
function construct_arglist(arg_codes) {
    if (is_null(arg_codes)) {
        return make_instruction_sequence(null, list("argl"),
                   list(assign("argl", constant(null))));
    } else {
        const rev_arg_codes = reverse(arg_codes);
        const code_to_get_last_arg =
            append_instruction_sequences(
                head(rev_arg_codes),
                make_instruction_sequence(list("val"), list("argl"),
                    list(assign("argl", 
                                list(op("list"), reg("val"))))));
        return is_null(tail(rev_arg_codes))
               ? code_to_get_last_arg
               : preserving(list("env"),
                     code_to_get_last_arg,
                     code_to_get_rest_args(tail(rev_arg_codes)));
    }
}
function code_to_get_rest_args(arg_codes) {
    const code_for_next_arg =
        preserving(list("argl"),
            head(arg_codes),
            make_instruction_sequence(list("val", "argl"), list("argl"),
                list(assign("argl", list(op("pair"),
                                         reg("val"), reg("argl"))))));
    return is_null(tail(arg_codes))
           ? code_for_next_arg
           : preserving(list("env"),
                        code_for_next_arg,
                        code_to_get_rest_args(tail(arg_codes)));
}

Applying functions
関数 の適用

After evaluating the elements of a function application, the compiled code must apply the function in fun to the arguments in argl. The code performs essentially the same dispatch as the apply function in the metacircular evaluator of section 4.1.1 or the apply_dispatch entry point in the explicit-control evaluator of section 5.4.1. It checks whether the function to be applied is a primitive function or a compiled function. For a primitive function, it uses apply_primitive_function; we will see shortly how it handles compiled functions. The function-application code has the following form:
関数適用の要素を評価した後、コンパイル済みコードは fun 内の関数を argl 内の引数に適用しなければなりません。このコードは、4.1.1節のメタ循環評価器の apply 関数や、5.4.1節の明示的制御評価器の apply_dispatch エントリポイントと本質的に同じディスパッチを行います。適用される関数がプリミティブ関数かコンパイル済み関数かを検査します。プリミティブ関数の場合は apply_primitive_function を使います。コンパイル済み関数の処理方法はすぐ後で見ます。関数適用のコードは次の形式を持ちます。
$\texttt{ }\texttt{ }$test(list(op("primitive_function"), reg("fun"))), branch(label("primitive_branch")), "compiled_branch", $\langle{}$code to apply compiled function with given target and appropriate linkage$\rangle$ "primitive_branch", assign($target$, list(op("apply_primitive_function"), reg("fun"), reg("argl"))), $\langle{}$linkage$\rangle$ "after_call"
Observe that the compiled branch must skip around the primitive branch. Therefore, if the linkage for the original function call was "next", the compound branch must use a linkage that jumps to a label that is inserted after the primitive branch. (This is similar to the linkage used for the true branch in compile_conditional.)
コンパイル済み分岐はプリミティブ分岐をスキップしなければならないことに注意してください。したがって、元の関数呼び出しのリンケージが "next" の場合、複合分岐はプリミティブ分岐の後に挿入されたラベルにジャンプするリンケージを使わなければなりません。（これは compile_conditional の真の分岐に使われるリンケージと同様です。） 
function compile_function_call(target, linkage) {
    const primitive_branch = make_label("primitive_branch");
    const compiled_branch = make_label("compiled_branch");
    const after_call = make_label("after_call");
    const compiled_linkage = linkage === "next" ? after_call : linkage;
    return append_instruction_sequences(
        make_instruction_sequence(list("fun"), null,
            list(test(list(op("is_primitive_function"), reg("fun"))),
                 branch(label(primitive_branch)))),
        append_instruction_sequences(
            parallel_instruction_sequences(
                append_instruction_sequences(
                    compiled_branch,
                    compile_fun_appl(target, compiled_linkage)),
                append_instruction_sequences(
                    primitive_branch,
                    end_with_linkage(linkage,
                        make_instruction_sequence(list("fun", "argl"),
                                                  list(target),
                            list(assign(
                                   target,
                                   list(op("apply_primitive_function"),
                                        reg("fun"), reg("argl")))))))),
            after_call));
}
The primitive and compound branches, like the true and false branches in compile_conditional, are appended using parallel_instruction_sequences rather than the ordinary append_instruction_sequences, because they will not be executed sequentially.
プリミティブ分岐と複合分岐は、compile_conditional の真と偽の分岐と同様に、通常の append_instruction_sequences ではなく parallel_instruction_sequences を使って結合されます。これらは順次実行されないからです。

Applying compiled functions
コンパイル済み関数の適用

The handling of function application and return is the most subtle part of the compiler. A compiled function (as constructed by compile_lambda_expression) has an entry point, which is a label that designates where the code for the function starts. The code at this entry point computes a result in val and ends by executing the instructions from a compiled return statement.
関数適用と return の処理は、コンパイラの中で最も微妙な部分です。コンパイル済み関数（compile_lambda_expression によって構築される）にはエントリポイントがあります。これは関数のコードが始まる場所を示すラベルです。このエントリポイントのコードは val に結果を計算し、コンパイル済みの return 文の命令を実行して終了します。

The code for a compiled-function application uses the stack in the same way as the explicit-control evaluator (section 5.4.1): before jumping to the compiled function's entry point, it saves the continuation of the function call to the stack, followed by a mark that allows reverting the stack to the state right before the call with the continuation on top.
コンパイル済み関数適用のコードは、明示的制御評価器（5.4.1節）と同じようにスタックを使用します。コンパイル済み関数のエントリポイントにジャンプする前に、関数呼び出しの継続をスタックに退避し、その後にマークを追加します。このマークによって、スタックを呼び出し直前の状態に戻し、継続を最上部に置くことができます。
$\texttt{ }\texttt{ }$// set up for return from function save("continue"), push_marker_to_stack(), // jump to the function's entry point assign("val", list(op("compiled_function_entry"), reg("fun"))), go_to(reg("val")),
Compiling a return statement (with compile_return_statement) generates corresponding code for reverting the stack and restoring and jumping to continue.
return 文のコンパイル（compile_return_statement による）は、スタックを元に戻し、continue を復元してジャンプする対応するコードを生成します。
$\texttt{ }\texttt{ }$revert_stack_to_marker(), restore("continue"), $\langle{}$evaluate the return expression and store the result in val$\rangle$ go_to(reg("continue")), // $\texttt{"return"}$-linkage code
Unless a function enters an infinite loop, it will end by executing the above return code, resulting from either a return statement in the program or one inserted by compile_lambda_body to return undefined.
関数が無限ループに入らない限り、上記の return コードを実行して終了します。これはプログラム中の return 文か、compile_lambda_body が undefined を返すために挿入した return 文のいずれかによるものです。
[1]

$\texttt{ }\texttt{ }$assign("continue", label("fun_return")), // where function should return to save("continue"), // will be restored by the function push_marker_to_stack(), // allows the function to revert stack to find $\texttt{fun_return}$ assign("val", list(op("compiled_function_entry"), reg("fun"))), go_to(reg("val")), // eventually reverts stack, restores and jumps to $\texttt{continue}$ "fun_return", // the function returns to here assign($\mathit{target}$, reg("val")), // included if target is not $\texttt{val}$ go_to(label($linkage$)), // linkage code

or like this—saving the caller's continuation at the start in order to restore and go to it at the end—if the linkage is "return" (that is, if the application is in a return statement and its value is the result to be returned):
あるいは、リンケージが "return" の場合（つまり、適用が return 文の中にあり、その値が返すべき結果である場合）は次のようになります。この場合、呼び出し元の継続を最初に退避し、最後に復元してそこにジャンプします：
$\texttt{ }\texttt{ }$save("continue"), // save the caller's continuation assign("continue", label("fun_return")), // where function should return to save("continue"), // will be restored by the function push_marker_to_stack(), // allows the function to revert stack to find $\texttt{fun_return}$ assign("val", list(op("compiled_function_entry"), reg("fun"))), go_to(reg("val")), // eventually reverts stack, restores and jumps to $\texttt{continue}$ "fun_return", // the function returns to here assign($\mathit{target}$, reg("val")), // included if target is not $\texttt{val}$ restore("continue"), // restore the caller's continuation go_to(reg("continue")), // linkage code
This code sets up continue so that the function will return to a label fun_return and jumps to the function's entry point. The code at fun_return transfers the function's result from val to the target register (if necessary) and then jumps to the location specified by the linkage. (The linkage is always "return" or a label, because compile_function_call replaces a "next" linkage for the compound-function branch by an after_call label.)
このコードは continue を設定して、関数がラベル fun_return に戻るようにし、関数のエントリポイントにジャンプします。fun_return のコードは、関数の結果を val からターゲットレジスタに転送し（必要な場合）、リンケージで指定された場所にジャンプします。（リンケージは常に "return" またはラベルです。compile_function_call が複合関数分岐の "next" リンケージを after_call ラベルに置き換えるからです。）
Before jumping to the function's entry point, we save continue and execute push_marker_to_stack() to enable the function to return to the intended location in the program with the expected stack. Matching revert_stack_to_marker() and restore("continue") instructions are generated by compile_return_statement for each return statement in the body of the function.
関数のエントリポイントにジャンプする前に、continue を退避し、push_marker_to_stack() を実行して、関数が期待されるスタックの状態でプログラム内の意図した場所に戻れるようにします。対応する revert_stack_to_marker() と restore("continue") の命令は、関数本体の各 return 文に対して compile_return_statement によって生成されます。
[2]

In fact, if the target is not val, the above is exactly the code our compiler will generate.
実際、ターゲットが val でない場合、上記はまさにコンパイラが生成するコードそのものです。
[3]
Usually, however, the target is val (the only time the compiler specifies a different register is when targeting the evaluation of a function expression to fun), so the function result is put directly into the target register and there is no need to jump to a special location that copies it. Instead we simplify the code by setting up continue so that the called function will return directly to the place specified by the caller's linkage:
しかし通常、ターゲットは val です（コンパイラが異なるレジスタを指定するのは、関数式の評価のターゲットを fun にする場合だけです）。したがって、関数の結果はターゲットレジスタに直接格納され、それをコピーする特別な場所にジャンプする必要はありません。代わりに、continue を設定して呼び出された関数が呼び出し元のリンケージで指定された場所に直接戻るようにすることでコードを簡略化します：
$\langle{}$set up continue for linkage and push the marker$\rangle$ assign("val", list(op("compiled_function_entry"), reg("fun"))), go_to(reg("val")),
If the linkage is a label, we set up continue so that the function will continue at that label. (That is, the go_to(reg("continue")) the called function ends with becomes equivalent to the go_to(label($linkage$)) at fun_return above.)
リンケージがラベルの場合、continue を設定して関数がそのラベルに継続するようにします。（つまり、呼び出された関数の最後の go_to(reg("continue")) が、上記の fun_return にある go_to(label($linkage$)) と等価になります。）
assign("continue", label($linkage$)), save("continue"), push_marker_to_stack(), assign("val", list(op("compiled_function_entry"), reg("fun"))), go_to(reg("val")),
If the linkage is "return", we don't need to assign continue: It already holds the desired location. (That is, the go_to(reg("continue")) the called function ends with goes directly to the place where the go_to(reg("continue")) at fun_{\hspace{0pt}}return  would have gone.)
リンケージが "return" の場合は、continue に代入する必要はありません。すでに目的の場所を保持しているからです。（つまり、呼び出された関数の最後の go_to(reg("continue")) が、上記の fun_{\hspace{0pt}}return  にある go_to(reg("continue")) が行くはずだった場所に直接行くことになります。） 
save("continue"),
push_marker_to_stack(),
assign("val", list(op("compiled_function_entry"), reg("fun"))),
go_to(reg("val")),
With this implementation of the "return" linkage, the compiler generates tail-recursive code. A function call in a return statement whose value is the result to be returned does a direct transfer, without saving unnecessary information on the stack.
この "return" リンケージの実装により、コンパイラは 末尾再帰的なコードを生成します。return 文の中の関数呼び出しで、その値が返すべき結果である場合、スタックに不要な情報を退避することなく直接転送を行います。

Suppose instead that we had handled the case of a function call with a linkage of "return" and a target of val in the same way as for a non-val target. This would destroy tail recursion. Our system would still return the same value for any function call. But each time we called a function, we would save continue and return after the call to undo the (useless) save. These extra saves would accumulate during a nest of function calls.
代わりに、関数呼び出しでリンケージが "return" でターゲットが val の場合を、val 以外のターゲットの場合と同じように処理していたとします。これは末尾再帰を破壊することになります。システムはどの関数呼び出しに対しても同じ値を返すでしょう。しかし、関数を呼び出すたびに continue を退避し、呼び出し後に（無駄な）退避を元に戻すことになります。これらの余分な退避は、関数呼び出しのネストの間に蓄積されていきます。
[4]

The function compile_fun_appl generates the above function-application code by considering four cases, depending on whether the target for the call is val and whether the linkage is "return". Observe that the instruction sequences are declared to modify all the registers, since executing the function body can change the registers in arbitrary ways.
関数 compile_fun_appl は、呼び出しのターゲットが val かどうかと、リンケージが "return" かどうかに応じて4つのケースを考慮し、上記の関数適用コードを生成します。命令列はすべてのレジスタを変更すると宣言されていることに注目してください。関数本体の実行がレジスタを任意に変更する可能性があるからです。
[5] function compile_fun_appl(target, linkage) { const fun_return = make_label("fun_return"); return target === "val" && linkage !== "return" ? make_instruction_sequence(list("fun"), all_regs, list(assign("continue", label(linkage)), save("continue"), push_marker_to_stack(), assign("val", list(op("compiled_function_entry"), reg("fun"))), go_to(reg("val")))) : target !== "val" && linkage !== "return" ? make_instruction_sequence(list("fun"), all_regs, list(assign("continue", label(fun_return)), save("continue"), push_marker_to_stack(), assign("val", list(op("compiled_function_entry"), reg("fun"))), go_to(reg("val")), fun_return, assign(target, reg("val")), go_to(label(linkage)))) : target === "val" && linkage === "return" ? make_instruction_sequence(list("fun", "continue"), all_regs, list(save("continue"), push_marker_to_stack(), assign("val", list(op("compiled_function_entry"), reg("fun"))), go_to(reg("val")))) : // $\texttt{target !== "val" \&\& linkage === "return"}$ error(target, "return linkage, target not val -- compile"); }

We have shown how to generate tail-recursive linkage code for a function application when the linkage is "return"—that is, when the application is in a return statement and its value is the result to be returned. Similarly, as explained in section 5.4.1, the stack-marker mechanism used here (and in the explicit-control evaluator) for the call and return produces tail-recursive behavior only in that situation. These two aspects of the code generated for function application combine to ensure that when a function ends by returning the value of a function call, no stack accumulates.
リンケージが "return" の場合、つまり適用が return 文の中にあり、その値が返すべき結果である場合に、関数適用のための末尾再帰的なリンケージコードを生成する方法を示しました。同様に、5.4.1節 で説明したように、呼び出しと戻りのためにここで（および明示的制御評価器で）使用されるスタックマーカーの仕組みは、 その状況でのみ末尾再帰的な動作を生み出します。関数適用のために生成されるコードのこれら2つの側面が組み合わさって、関数が関数呼び出しの値を返して終了する場合にスタックが蓄積されないことが保証されます。

Compiling return statements
return 文のコンパイル

The code for a return statement takes the following form, regardless of the given linkage and target:
return 文のコードは、与えられたリンケージやターゲットに関係なく、次の形式を取ります：
revert_stack_to_marker(), restore("continue"), // saved by $\texttt{compile\char`_fun\char`_appl}$ $\langle{}$evaluate the return expression and store the result in val$\rangle$ go_to(reg("continue")) // $\texttt{"return"}$-linkage code
The instructions to revert the stack using the marker and then restore continue correspond to the instructions generated by compile_fun_appl to save continue and mark the stack. The final jump to continue is generated by the use of the "return" linkage when compiling the return expression. The function compile_return_statement is different from all other code generators in that it ignores the target and linkage arguments—it always compiles the return expression with target val and linkage "return".
マーカーを使ってスタックを元に戻し、continue を復元する命令は、compile_fun_appl が continue を退避してスタックにマークを付けるために生成した命令に対応しています。continue への最後のジャンプは、return 式をコンパイルする際に "return" リンケージを使用することで生成されます。関数 compile_return_statement は他のすべてのコード生成器とは異なり、ターゲットとリンケージの引数を無視します。常に return 式をターゲット val、リンケージ "return" でコンパイルします。 
function compile_return_statement(stmt, target, linkage) {
    return append_instruction_sequences(
               make_instruction_sequence(null, list("continue"),
                   list(revert_stack_to_marker(),
                        restore("continue"))),
               compile(return_expression(stmt), "val", "return"));
}

Making a compiler generate tail-recursive code is desirable, especially in the functional paradigm. However, compilers for common languages, including C and C++, do not always do this, and therefore these languages cannot represent iterative processes in terms of function call alone. The difficulty with tail recursion in these languages is that their implementations use the stack to store function arguments and local names as well as return addresses. The JavaScript implementations described in this book store arguments and names in memory to be garbage-collected. The reason for using the stack for names and arguments is that it avoids the need for garbage collection in languages that would not otherwise require it, and is generally believed to be more efficient. Sophisticated compilers can, in fact, use the stack for arguments without destroying tail recursion. (See Hanson 1990 for a description.) There is also some debate about whether stack allocation is actually more efficient than garbage collection in the first place, but the details seem to hinge on fine points of computer architecture. (See Appel 1987 and Miller and Rozas 1994 for opposing views on this issue.)
コンパイラに末尾再帰的なコードを生成させることは、特に関数型パラダイムでは望ましいことです。しかし、C や C++ を含む一般的な言語のコンパイラは必ずしもこれを行わず、そのためこれらの言語では関数呼び出しだけで反復プロセスを表現することができません。 これらの言語で末尾再帰が困難なのは、その実装がスタックを使って関数の引数やローカル名前、および戻りアドレスを格納しているからです。本書で説明する JavaScript の実装は、引数と名前をガベージコレクションされるメモリに格納します。名前と引数にスタックを使う理由は、そうでなければガベージコレクションを必要としない言語でガベージコレクションの必要性を回避でき、一般的により効率的であると考えられているからです。洗練された コンパイラは、実際にはスタックを引数に使いながら末尾再帰を破壊しないことができます。（説明は Hanson 1990 を参照してください。）スタック割り当てがそもそもガベージコレクションよりも実際に効率的かどうかについても議論がありますが、詳細はコンピュータアーキテクチャの微妙な点に依存するようです。（この問題に関する対立する見解については Appel 1987 および Miller and Rozas 1994 を参照してください。）
