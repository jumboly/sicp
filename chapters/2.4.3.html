2.4.3  
Data-Directed Programming and Additivity
データ指向プログラミングと加法性

The general strategy of checking the type of a datum and calling an appropriate function is called dispatching on type. This is a powerful strategy for obtaining modularity in system design. On the other hand, implementing the dispatch as in section 2.4.2 has two significant weaknesses. One weakness is that the generic interface functions (real_part, imag_part, magnitude, and angle) must know about all the different representations. For instance, suppose we wanted to incorporate a new representation for complex numbers into our complex-number system. We would need to identify this new representation with a type, and then add a clause to each of the generic interface functions to check for the new type and apply the appropriate selector for that representation.
データの型をチェックして適切な 関数 を呼び出すという一般的な戦略は、 型によるディスパッチと呼ばれます。これはシステム設計においてモジュール性を得るための強力な戦略です。一方で、2.4.2節のようにディスパッチを実装すると、二つの大きな弱点があります。一つ目の弱点は、ジェネリックインターフェース 関数 （ real_part、 imag_part、 magnitude、angle）がすべての異なる表現について知っていなければならないことです。たとえば、複素数システムに新しい表現を組み込みたいとします。この新しい表現を型で識別し、各ジェネリックインターフェース 関数 に、新しい型をチェックしてその表現に適切なセレクタを適用する節を追加する必要があります。

Another weakness of the technique is that even though the individual representations can be designed separately, we must guarantee that no two functions in the entire system have the same name. This is why Ben and Alyssa had to change the names of their original functions from section 2.4.1.
この技法のもう一つの弱点は、個々の表現を別々に設計できるにもかかわらず、システム全体で同じ名前を持つ 関数 が二つとないことを保証しなければならないことです。これが、BenとAlyssaが2.4.1節の元の 関数 の名前を変更しなければならなかった理由です。

The issue underlying both of these weaknesses is that the technique for implementing generic interfaces is not additive. The person implementing the generic selector functions must modify those functions each time a new representation is installed, and the people interfacing the individual representations must modify their code to avoid name conflicts. In each of these cases, the changes that must be made to the code are straightforward, but they must be made nonetheless, and this is a source of inconvenience and error. This is not much of a problem for the complex-number system as it stands, but suppose there were not two but hundreds of different representations for complex numbers. And suppose that there were many generic selectors to be maintained in the abstract-data interface. Suppose, in fact, that no one programmer knew all the interface functions or all the representations. The problem is real and must be addressed in such programs as large-scale data-base-management systems.
これらの弱点の両方に共通する問題は、ジェネリックインターフェースを実装する技法が加法的でないことです。ジェネリックセレクタ 関数 を実装する人は、新しい表現が導入されるたびにそれらの 関数 を修正しなければならず、個々の表現を接続する人は名前の衝突を避けるために自分のコードを修正しなければなりません。いずれの場合も、コードに加えなければならない変更は簡単ですが、それでも変更は必要であり、不便さとエラーの元になります。現状の複素数システムではこれは大きな問題ではありませんが、複素数の異なる表現が二つではなく数百あったとしたらどうでしょう。そして、抽象データインターフェースで維持すべきジェネリックセレクタが多数あったとしたら。実際、すべてのインターフェース 関数 やすべての表現を知っているプログラマが一人もいないとしたら。この問題は現実的であり、大規模データベース管理システムのようなプログラムでは対処しなければなりません。

What we need is a means for modularizing the system design even further. This is provided by the programming technique known as data-directed programming. To understand how data-directed programming works, begin with the observation that whenever we deal with a set of generic operations that are common to a set of different types we are, in effect, dealing with a two-dimensional table that contains the possible operations on one axis and the possible types on the other axis. The entries in the table are the functions that implement each operation for each type of argument presented. In the complex-number system developed in the previous section, the correspondence between operation name, data type, and actual function was spread out among the various conditional clauses in the generic interface functions. But the same information could have been organized in a table, as shown in figure 2.34.
私たちに必要なのは、システム設計をさらにモジュール化する手段です。これを提供するのが、データ指向プログラミングとして知られるプログラミング技法です。データ指向プログラミングがどのように機能するかを理解するために、まず次の観察から始めましょう。異なる型の集合に共通するジェネリック演算の集合を扱うとき、実質的には、一方の軸に可能な演算を、もう一方の軸に可能な型を含む二次元テーブルを扱っていることになります。テーブルの各エントリは、提示される各型の引数に対して各演算を実装する 関数 です。前のセクションで開発した複素数システムでは、演算名、データ型、そして実際の 関数 の間の対応関係は、ジェネリックインターフェース 関数 の様々な条件節に散らばっていました。しかし、同じ情報は、 図 2.34 に示すように、テーブルにまとめることもできたはずです。

Data-directed programming is the technique of designing programs to work with such a table directly. Previously, we implemented the mechanism that interfaces the complex-arithmetic code with the two representation packages as a set of functions that each perform an explicit dispatch on type. Here we will implement the interface as a single function that looks up the combination of the operation name and argument type in the table to find the correct function to apply, and then applies it to the contents of the argument. If we do this, then to add a new representation package to the system we need not change any existing functions; we need only add new entries to the table.
データ指向プログラミングとは、このような テーブルを直接扱うようにプログラムを設計する技法です。以前は、複素数の算術コードと二つの表現パッケージを接続するメカニズムを、それぞれ型に対して明示的なディスパッチを行う 関数 の集合として実装しました。ここでは、テーブル内で演算名と引数の型の組み合わせを検索して適用すべき正しい 関数 を見つけ、それを引数の中身に適用する、単一の 関数 としてインターフェースを実装します。こうすれば、新しい表現パッケージをシステムに追加するとき、既存の 関数 を変更する必要はなく、テーブルに新しいエントリを追加するだけで済みます。

To implement this plan, assume that we have two functions, put and get, for manipulating the operation-and-type table:
この計画を実装するために、 演算と型のテーブルを操作するための二つの 関数 putとgetがあると仮定します：
  • put($op$, $type$, $item$)
    installs the $item$ in the table, indexed by the $op$ and the $type$.
    $op$と$type$ をインデックスとして、 $item$ をテーブルに登録します。
  • get($op$, $type$)
    looks up the $op$, $type$ entry in the table and returns the item found there. If no item is found, get returns a unique primitive value that is referred to by the name undefined and recognized by the primitive predicate is_undefined.
    テーブル内の $op$、$type$ のエントリを検索し、見つかった項目を返します。項目が見つからない場合、getは undefinedという名前で参照され、プリミティブな述語 is_undefinedによって認識される、一意のプリミティブ値を返します。
    [1]
For now, we can assume that put and get are included in our language. In chapter 3 (section 3.3.3) we will see how to implement these and other operations for manipulating tables.
今のところ、putとgetは言語に含まれていると仮定できます。第 3章（3.3.3節）で、これらおよびテーブルを操作するための他の演算の実装方法を見ます。

Here is how data-directed programming can be used in the complex-number system. Ben, who developed the rectangular representation, implements his code just as he did originally. He defines a collection of functions or a package, and interfaces these to the rest of the system by adding entries to the table that tell the system how to operate on rectangular numbers. This is accomplished by calling the following function:
以下に、データ指向プログラミングを複素数システムにどのように使えるかを示します。直交表現を開発したBenは、元々と同じようにコードを実装します。彼は 関数 のコレクション、つまり パッケージを定義し、直交数に対する操作方法をシステムに伝えるエントリをテーブルに追加することで、これらをシステムの残りの部分と接続します。これは以下の 関数 を呼び出すことで実現されます： 
function install_rectangular_package() {
    // internal functions
    function real_part(z) { return head(z); }
    function imag_part(z) { return tail(z); }
    function make_from_real_imag(x, y) { return pair(x, y); }
    function magnitude(z) {
        return math_sqrt(square(real_part(z)) + square(imag_part(z)));
    }
    function angle(z) {
        return math_atan2(imag_part(z), real_part(z));
    }
    function make_from_mag_ang(r, a) {
        return pair(r * math_cos(a), r * math_sin(a));
    }

    // interface to the rest of the system
    function tag(x) { return attach_tag("rectangular", x); }
    put("real_part", list("rectangular"), real_part);
    put("imag_part", list("rectangular"), imag_part);
    put("magnitude", list("rectangular"), magnitude);
    put("angle", list("rectangular"), angle);
    put("make_from_real_imag", "rectangular",
        (x, y) => tag(make_from_real_imag(x, y)));
    put("make_from_mag_ang", "rectangular",
        (r, a) => tag(make_from_mag_ang(r, a)));
    return "done";
}

Notice that the internal functions here are the same functions from section 2.4.1 that Ben wrote when he was working in isolation. No changes are necessary in order to interface them to the rest of the system. Moreover, since these function declarations are internal to the installation function, Ben needn't worry about name conflicts with other functions outside the rectangular package. To interface these to the rest of the system, Ben installs his real_part function under the operation name real_part and the type list("rectangular"), and similarly for the other selectors.
ここでの内部 関数 は、Benが独立して作業していたときに2.4.1節で書いたものと同じ 関数 であることに注目してください。システムの残りの部分と接続するために変更を加える必要はありません。さらに、これらの 関数宣言 はインストール 関数 の内部にあるため、Benは直交パッケージの外にある他の 関数 との名前の衝突を心配する必要がありません。これらをシステムの残りの部分と接続するために、Benは自分の real_part 関数 を、演算名 real_part と型 list("rectangular") の下にインストールし、他のセレクタも同様にします。
[2]
The interface also defines the constructors to be used by the external system.
インターフェースはまた、外部システムが使うコンストラクタも定義します。
[3]
These are identical to Ben's internally defined constructors, except that they attach the tag.
これらはBenが内部で定義したコンストラクタと同一ですが、タグを付ける点が異なります。

Alyssa's polar package is analogous:
Alyssaの 極パッケージも同様です： 
function install_polar_package() {
    // internal functions
    function magnitude(z) { return head(z); }
    function angle(z) { return tail(z); }
    function make_from_mag_ang(r, a) { return pair(r, a); }
    function real_part(z) {
        return magnitude(z) * math_cos(angle(z));
    }
    function imag_part(z) {
        return magnitude(z) * math_sin(angle(z));
    }
    function make_from_real_imag(x, y) {
        return pair(math_sqrt(square(x) + square(y)),
                    math_atan2(y, x));
    }

    // interface to the rest of the system
    function tag(x) { return attach_tag("polar", x); }
    put("real_part", list("polar"), real_part);
    put("imag_part", list("polar"), imag_part);
    put("magnitude", list("polar"), magnitude);
    put("angle", list("polar"), angle);
    put("make_from_real_imag", "polar", 
        (x, y) => tag(make_from_real_imag(x, y)));
    put("make_from_mag_ang", "polar",
        (r, a) => tag(make_from_mag_ang(r, a)));
    return "done";
}

Even though Ben and Alyssa both still use their original functions defined with the same names as each other's (e.g., real_part), these declarations are now internal to different functions (see section 1.1.8), so there is no name conflict.
BenとAlyssaがどちらもまだ互いと同じ名前で定義された元の 関数 （たとえば real_part） を使っていても、これらの宣言は異なる 関数 の内部にあるため（1.1.8節を参照）、名前の衝突はありません。

The complex-arithmetic selectors access the table by means of a general operation function called apply_generic, which applies a generic operation to some arguments. The function apply_generic looks in the table under the name of the operation and the types of the arguments and applies the resulting function if one is present:

Message passing
メッセージパッシング

The key idea of data-directed programming is to handle generic operations in programs by dealing explicitly with operation-and-type tables, such as the table in figure 2.34. The style of programming we used in section 2.4.2 organized the required dispatching on type by having each operation take care of its own dispatching. In effect, this decomposes the operation-and-type table into rows, with each generic operation function representing a row of the table.
データ指向プログラミングの鍵となるアイデアは、 図 2.34 のテーブルのような、演算と型のテーブルを明示的に扱うことで、プログラム内のジェネリック演算を処理することです。2.4.2節で使ったプログラミングスタイルは、各演算が自身のディスパッチを担当するようにして、型に対する必要なディスパッチを組織化しました。実質的に、これは演算と型のテーブルを行に分解し、各ジェネリック演算 関数 がテーブルの一行を表すようにしています。

An alternative implementation strategy is to decompose the table into columns and, instead of using intelligent operations that dispatch on data types, to work with intelligent data objects that dispatch on operation names. We can do this by arranging things so that a data object, such as a rectangular number, is represented as a function that takes as input the required operation name and performs the operation indicated. In such a discipline, make_from_real_imag could be written as
代替の実装戦略は、テーブルを列に分解し、データ型に対してディスパッチする賢い演算を使う代わりに、演算名に対してディスパッチする賢いデータオブジェクトを使うことです。これは、直交数のようなデータオブジェクトを、必要な演算名を入力として受け取り、指定された演算を実行する 関数 として表現するようにすれば実現できます。この方式では、 make_from_real_imag は次のように書けるでしょう。 
function make_from_real_imag(x, y) {
    function dispatch(op) {
        return op === "real_part"
               ? x
               : op === "imag_part"
               ? y
               : op === "magnitude"
               ? math_sqrt(square(x) + square(y))
               : op === "angle"
               ? math_atan2(y, x)
               : error(op, "unknown op -- make_from_real_imag");
    }
    return dispatch;
}
The corresponding apply_generic function, which applies a generic operation to an argument, now simply feeds the operation's name to the data object and lets the object do the work:
対応する apply_generic 関数 は、ジェネリック演算を引数に適用するもので、今や単に演算の名前をデータオブジェクトに渡し、オブジェクトに仕事をさせるだけです：
[5] 
function apply_generic(op, arg) { return head(arg)(op); }
Note that the value returned by make_from_real_imag is a function—the internal dispatch function. This is the function that is invoked when apply_generic requests an operation to be performed.
make_from_real_imag が返す値は 関数 —内部のdispatch 関数 であることに注目してください。これは apply_generic が演算の実行を要求するときに呼び出される 関数 です。

This style of programming is called message passing. The name comes from the image that a data object is an entity that receives the requested operation name as a message. We have already seen an example of message passing in section 2.1.3, where we saw how pair, head, and tail could be defined with no data objects but only functions. Here we see that message passing is not a mathematical trick but a useful technique for organizing systems with generic operations. In the remainder of this chapter we will continue to use data-directed programming, rather than message passing, to discuss generic arithmetic operations. In chapter 3 we will return to message passing, and we will see that it can be a powerful tool for structuring simulation programs.
このプログラミングスタイルはメッセージパッシングと呼ばれます。この名前は、データオブジェクトが要求された演算名をメッセージとして受け取るエンティティであるというイメージに由来します。メッセージパッシングの例はすでに2.1.3節で見ました。そこでは、 pair、 head、 tail をデータオブジェクトなしに 関数 だけで定義できることを見ました。ここでは、メッセージパッシングが数学的なトリックではなく、ジェネリック演算を持つシステムを組織化するための有用な技法であることが分かります。この章の残りでは、ジェネリック算術演算を議論するために、メッセージパッシングではなくデータ指向プログラミングを引き続き使います。第 3章ではメッセージパッシングに戻り、シミュレーションプログラムを構造化するための強力なツールとなりうることを見ます。

Exercise 2.76
As a large system with generic operations evolves, new types of data objects or new operations may be needed. For each of the three strategies—generic operations with explicit dispatch, data-directed style, and message-passing-style—describe the changes that must be made to a system in order to add new types or new operations. Which organization would be most appropriate for a system in which new types must often be added? Which would be most appropriate for a system in which new operations must often be added?
ジェネリック演算を持つ大規模なシステムが進化するにつれて、新しい型のデータオブジェクトや新しい演算が必要になることがあります。三つの戦略—明示的な ディスパッチによるジェネリック演算、データ指向スタイル、メッセージパッシングスタイル—のそれぞれについて、新しい型や新しい演算を追加するためにシステムに加えなければならない変更を説明してください。新しい型を頻繁に追加しなければならないシステムには、どの組織化が最も適切ですか？ 新しい演算を頻繁に追加しなければならないシステムには、どれが最も適切ですか？
  • Generic operations with explicit dispatch: For every new type, we need to touch every generic interface function, and add a new case.
  • Data-directed style: Here the implementation of the generic interface functions can be neatly packaged in install libraries for each new type. We can also have install libraries for new operations.
  • Message-passing-style: Like in the data-directed style, we need to write a library for each new type. In this case, the library consists of a dispatch function with a case for every generic interface function.
Overall, it's probably best to use a data-directed style when we need to frequently add new operations, and message-passing, when we frequently add new types.
