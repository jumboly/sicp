2.5.2  
Combining Data of Different Types
異なる型のデータの組み合わせ

We have seen how to define a unified arithmetic system that encompasses ordinary numbers, complex numbers, rational numbers, and any other type of number we might decide to invent, but we have ignored an important issue. The operations we have defined so far treat the different data types as being completely independent. Thus, there are separate packages for adding, say, two ordinary numbers, or two complex numbers. What we have not yet considered is the fact that it is meaningful to define operations that cross the type boundaries, such as the addition of a complex number to an ordinary number. We have gone to great pains to introduce barriers between parts of our programs so that they can be developed and understood separately. We would like to introduce the cross-type operations in some carefully controlled way, so that we can support them without seriously violating our module boundaries.
ここまで、通常の数、複素数、有理数、そしてこの先考案するかもしれないあらゆる種類の数を包含する統一的な算術システムの定義方法を見てきましたが、重要な問題を無視してきました。これまでに定義した演算は、異なるデータ型を完全に独立したものとして扱っています。つまり、たとえば2つの通常の数を加算するパッケージと、2つの複素数を加算するパッケージは別々に存在しています。まだ考慮していなかったのは、型の境界をまたぐ演算を定義することに意味があるという事実です。たとえば、複素数と通常の数の加算などです。私たちはプログラムの各部分の間に障壁を導入して、それぞれを独立に開発・理解できるようにするために多大な努力を払ってきました。型をまたぐ演算を、モジュールの境界を大きく侵害することなくサポートできるよう、慎重に制御された方法で導入したいと考えています。

One way to handle cross-type operations is to design a different function for each possible combination of types for which the operation is valid. For example, we could extend the complex-number package so that it provides a function for adding complex numbers to ordinary numbers and installs this in the table using the tag list("complex", "javascript_number"):
型をまたぐ演算を扱う1つの方法は、演算が有効な型の組み合わせごとに異なる 関数を設計することです。たとえば、複素数パッケージを拡張して、複素数と通常の数を加算する 関数 を提供し、タグ list("complex", "javascript_number") を使ってテーブルに登録できます：
[1] 
// to be included in the complex package
function add_complex_to_javascript_num(z, x) {
   return make_complex_from_real_imag(real_part(z) + x, imag_part(z));
}
put("add", list("complex", "javascript_number"),
    (z, x) => tag(add_complex_to_javascript_num(z, x)));

This technique works, but it is cumbersome. With such a system, the cost of introducing a new type is not just the construction of the package of functions for that type but also the construction and installation of the functions that implement the cross-type operations. This can easily be much more code than is needed to define the operations on the type itself. The method also undermines our ability to combine separate packages additively, or least to limit the extent to which the implementors of the individual packages need to take account of other packages. For instance, in the example above, it seems reasonable that handling mixed operations on complex numbers and ordinary numbers should be the responsibility of the complex-number package. Combining rational numbers and complex numbers, however, might be done by the complex package, by the rational package, or by some third package that uses operations extracted from these two packages. Formulating coherent policies on the division of responsibility among packages can be an overwhelming task in designing systems with many packages and many cross-type operations.
この手法は機能しますが、煩雑です。このようなシステムでは、新しい型を導入するコストは、その型用の 関数 のパッケージを構築するだけにとどまらず、型をまたぐ演算を実装する 関数 の構築とインストールも必要になります。これは、その型自体の演算を定義するのに必要なコード量よりも、はるかに多くなりがちです。また、この方法は、個別のパッケージを加法的に組み合わせる能力、少なくとも各パッケージの実装者が他のパッケージについて考慮しなければならない範囲を限定する能力を損ないます。たとえば、上の例では、複素数と通常の数の混合演算の処理は複素数パッケージの責任とするのが妥当に思えます。しかし、有理数と複素数の組み合わせは、複素数パッケージが行うかもしれませんし、有理数パッケージが行うかもしれませんし、あるいはこれら二つのパッケージから抽出した演算を使う第三のパッケージが行うかもしれません。多くのパッケージと多くの型をまたぐ演算を持つシステムを設計する際に、パッケージ間の責任分担について一貫した方針を定めることは、非常に困難な作業になりえます。

Coercion
型変換

In the general situation of completely unrelated operations acting on completely unrelated types, implementing explicit cross-type operations, cumbersome though it may be, is the best that one can hope for. Fortunately, we can usually do better by taking advantage of additional structure that may be latent in our type system. Often the different data types are not completely independent, and there may be ways by which objects of one type may be viewed as being of another type. This process is called coercion. For example, if we are asked to arithmetically combine an ordinary number with a complex number, we can view the ordinary number as a complex number whose imaginary part is zero. This transforms the problem to that of combining two complex numbers, which can be handled in the ordinary way by the complex-arithmetic package.
完全に無関係な演算が完全に無関係な型に作用するという一般的な状況では、明示的な型をまたぐ演算を実装するのは、煩雑ではあっても、望みうる最善の方法です。しかし幸いなことに、型システムに潜む追加の構造を活用することで、通常はもっとうまくやれます。多くの場合、異なるデータ型は完全に独立しているわけではなく、ある型のオブジェクトを別の型として見なす方法があるかもしれません。このプロセスは型変換（coercion）と呼ばれます。たとえば、通常の数と複素数を算術的に組み合わせるよう求められた場合、通常の数を虚部がゼロの複素数と見なすことができます。これにより問題は二つの複素数の組み合わせに変換され、複素数算術パッケージの通常の方法で処理できます。

In general, we can implement this idea by designing coercion functions that transform an object of one type into an equivalent object of another type. Here is a typical coercion function, which transforms a given ordinary number to a complex number with that real part and zero imaginary part:
一般に、このアイデアは、ある型のオブジェクトを別の型の同等のオブジェクトに変換する 型変換 関数 を設計することで実装できます。以下は典型的な型変換 関数 で、与えられた通常の数を、その実部を持ち虚部がゼロの複素数に変換します： 
function javascript_number_to_complex(n) {
    return make_complex_from_real_imag(contents(n), 0);
}
We install these coercion functions in a special coercion table, indexed under the names of the two types: 
put_coercion("javascript_number", "complex",
             javascript_number_to_complex);
(We assume that there are put_coercion and get_coercion functions available for manipulating this table.) Generally some of the slots in the table will be empty, because it is not generally possible to coerce an arbitrary data object of each type into all other types. For example, there is no way to coerce an arbitrary complex number to an ordinary number, so there will be no general complex_to_javascript_number function included in the table.
（このテーブルを操作するための put_coercion と get_coercion 関数 が利用可能であると仮定します。）一般に、テーブルの一部のスロットは空になります。なぜなら、各型の任意のデータオブジェクトを他のすべての型に型変換できるとは限らないからです。たとえば、任意の複素数を通常の数に型変換する方法はないので、テーブルに汎用の complex_to_javascript_number 関数 は含まれません。

Once the coercion table has been set up, we can handle coercion in a uniform manner by modifying the apply_generic function of section 2.4.3. When asked to apply an operation, we first check whether the operation is defined for the arguments' types, just as before. If so, we dispatch to the function found in the operation-and-type table. Otherwise, we try coercion. For simplicity, we consider only the case where there are two arguments.
型変換テーブルが設定されたら、2.4.3節の apply_generic 関数 を修正することで、型変換を統一的に扱えるようになります。演算の適用を求められたとき、まず以前と同様に、その演算が引数の型に対して定義されているかどうかを確認します。定義されていれば、演算と型のテーブルで見つかった 関数 にディスパッチします。そうでなければ、型変換を試みます。簡単のために、引数が二つの場合だけを考えます。
[2]
We check the coercion table to see if objects of the first type can be coerced to the second type. If so, we coerce the first argument and try the operation again. If objects of the first type cannot in general be coerced to the second type, we try the coercion the other way around to see if there is a way to coerce the second argument to the type of the first argument. Finally, if there is no known way to coerce either type to the other type, we give up. Here is the function:
型変換テーブルを調べて、第1の型のオブジェクトを第2の型に型変換できるかどうかを確認します。できる場合は、第1引数を型変換して演算を再度試みます。第1の型のオブジェクトを一般に第2の型に型変換できない場合は、逆方向の型変換を試み、第2引数を第1引数の型に型変換する方法があるかどうかを確認します。最後に、どちらの型も他方の型に型変換する既知の方法がなければ、諦めます。以下がその 関数 です： 
function apply_generic(op, args) {
    const type_tags = map(type_tag, args);
    const fun = get(op, type_tags);
    if (! is_undefined(fun)) {
        return apply(fun, map(contents, args));
    } else {
        if (length(args) === 2) {
            const type1 = head(type_tags);
            const type2 = head(tail(type_tags));
            const a1 = head(args);
            const a2 = head(tail(args));
            const t1_to_t2 = get_coercion(type1, type2);
            const t2_to_t1 = get_coercion(type2, type1);
            return ! is_undefined(t1_to_t2)
                   ? apply_generic(op, list(t1_to_t2(a1), a2))
                   : ! is_undefined(t2_to_t1)
                   ? apply_generic(op, list(a1, t2_to_t1(a2)))
                   : error(list(op, type_tags),
                           "no method for these types");
        } else {
            return error(list(op, type_tags),
                         "no method for these types");
        }
    }
}

This coercion scheme has many advantages over the method of defining explicit cross-type operations, as outlined above. Although we still need to write coercion functions to relate the types (possibly $n^2$ functions for a system with $n$ types), we need to write only one function for each pair of types rather than a different function for each collection of types and each generic operation.
この型変換の仕組みは、上で述べた明示的な型をまたぐ演算を定義する方法に比べて、多くの利点があります。型を関連付けるための型変換 関数 を書く必要は依然としてありますが（$n$個の型を持つシステムでは最大$n^2$個の 関数 ）、型の組み合わせごとにジェネリック演算ごとに異なる 関数 を書くのではなく、型のペアごとに一つの 関数 を書くだけで済みます。
[3]
What we are counting on here is the fact that the appropriate transformation between types depends only on the types themselves, not on the operation to be applied.
ここで頼りにしているのは、型間の適切な変換が型自体にのみ依存し、適用される演算には依存しないという事実です。

On the other hand, there may be applications for which our coercion scheme is not general enough. Even when neither of the objects to be combined can be converted to the type of the other it may still be possible to perform the operation by converting both objects to a third type. In order to deal with such complexity and still preserve modularity in our programs, it is usually necessary to build systems that take advantage of still further structure in the relations among types, as we discuss next.
一方で、この型変換の仕組みでは十分に汎用的でないアプリケーションもあるかもしれません。組み合わせるオブジェクトのどちらも他方の型に変換できない場合でも、両方のオブジェクトを第三の型に変換することで演算を実行できる可能性はあります。このような複雑さに対処しつつプログラムのモジュール性を維持するためには、通常、型間の関係におけるさらなる構造を活用するシステムを構築する必要があります。これについては次で議論します。

Hierarchies of types
型の階層

The coercion scheme presented above relied on the existence of natural relations between pairs of types. Often there is more global structure in how the different types relate to each other. For instance, suppose we are building a generic arithmetic system to handle integers, rational numbers, real numbers, and complex numbers. In such a system, it is quite natural to regard an integer as a special kind of rational number, which is in turn a special kind of real number, which is in turn a special kind of complex number. What we actually have is a so-called hierarchy of types, in which, for example, integers are a subtype of rational numbers (i.e., any operation that can be applied to a rational number can automatically be applied to an integer). Conversely, we say that rational numbers form a supertype of integers. The particular hierarchy we have here is of a very simple kind, in which each type has at most one supertype and at most one subtype. Such a structure, called a tower, is illustrated in figure 2.39.
上で示した型変換の方式は、型のペア間に自然な関係が存在することに依存していました。多くの場合、異なる型どうしの関係には、よりグローバルな構造があります。例えば、整数、有理数、実数、複素数を扱うジェネリック算術システムを構築しているとしましょう。このようなシステムでは、整数を有理数の特殊な場合と見なし、有理数を実数の特殊な場合、実数を複素数の特殊な場合と見なすのは、ごく自然なことです。これは実際には、いわゆる型の階層と呼ばれるものです。例えば、整数は有理数の サブタイプです（つまり、有理数に適用できる演算はすべて、自動的に整数にも適用できます）。逆に、有理数は整数の スーパータイプであると言います。ここでの階層は非常に単純な種類のもので、各型には高々1つのスーパータイプと高々1つのサブタイプしかありません。このような構造はタワーと呼ばれ、図 2.39に示されています。

If we have a tower structure, then we can greatly simplify the problem of adding a new type to the hierarchy, for we need only specify how the new type is embedded in the next supertype above it and how it is the supertype of the type below it. For example, if we want to add an integer to a complex number, we need not explicitly define a special coercion function integer_to_complex. Instead, we define how an integer can be transformed into a rational number, how a rational number is transformed into a real number, and how a real number is transformed into a complex number. We then allow the system to transform the integer into a complex number through these steps and then add the two complex numbers.
タワー構造があれば、階層に新しい型を追加する問題を大幅に簡略化できます。新しい型がその上の最も近いスーパータイプにどう埋め込まれるか、そしてその下の型のスーパータイプとしてどう機能するかを指定するだけでよいからです。例えば、整数と複素数を加算したい場合、特別な型変換 関数 integer_to_complex を明示的に定義する必要はありません。代わりに、整数を有理数に変換する方法、有理数を実数に変換する方法、実数を複素数に変換する方法を定義します。そうすれば、システムがこれらのステップを経て整数を複素数に変換し、2つの複素数を加算できるようになります。

We can redesign our apply_generic function in the following way: For each type, we need to supply a raise function, which raises objects of that type one level in the tower. Then when the system is required to operate on objects of different types it can successively raise the lower types until all the objects are at the same level in the tower. (Exercises 2.83 and  2.84 concern the details of implementing such a strategy.)
apply_generic 関数 を次のように再設計できます。各型に対して、その型のオブジェクトをタワーの1レベル上に引き上げる（raise） raise 関数 を用意する必要があります。そうすると、システムが異なる型のオブジェクトに対して演算を行う必要があるとき、すべてのオブジェクトがタワーの同じレベルになるまで、低い型を順次引き上げることができます。（練習問題 2.83と 2.84で、このような戦略の実装の詳細を扱います。）

Another advantage of a tower is that we can easily implement the notion that every type inherits all operations defined on a supertype. For instance, if we do not supply a special function for finding the real part of an integer, we should nevertheless expect that real_part will be defined for integers by virtue of the fact that integers are a subtype of complex numbers. In a tower, we can arrange for this to happen in a uniform way by modifying apply_generic. If the required operation is not directly defined for the type of the object given, we raise the object to its supertype and try again. We thus crawl up the tower, transforming our argument as we go, until we either find a level at which the desired operation can be performed or hit the top (in which case we give up).
タワーのもう1つの利点は、すべての型がスーパータイプに定義された演算を継承するという概念を容易に実装できることです。例えば、整数の実部を求める特別な 関数 を用意しなくても、整数が複素数のサブタイプであるという事実により、 real_part は整数に対しても定義されることが期待できるはずです。タワーでは、 apply_generic を修正することで、これを統一的に実現できます。要求された演算が与えられたオブジェクトの型に対して直接定義されていない場合、オブジェクトをスーパータイプに引き上げて再試行します。このようにして、引数を変換しながらタワーを上に向かってたどり、目的の演算が実行できるレベルを見つけるか、最上部に到達するか（その場合はあきらめます）のどちらかになります。

Yet another advantage of a tower over a more general hierarchy is that it gives us a simple way to lower a data object to the simplest representation. For example, if we add $2+3i$ to $4-3i$, it would be nice to obtain the answer as the integer 6 rather than as the complex number $6+0i$. Exercise 2.85 discusses a way to implement such a lowering operation. (The trick is that we need a general way to distinguish those objects that can be lowered, such as $6+0i$, from those that cannot, such as $6+2i$.)
より一般的な階層に対するタワーのさらなる利点は、データオブジェクトを最も単純な表現に引き下げる簡単な方法が得られることです。例えば、$2+3i$と$4-3i$を加算した場合、答えを複素数$6+0i$ではなく整数6として得られると便利です。練習問題 2.85では、このような引き下げ操作の実装方法を議論します。（ポイントは、$6+0i$のように引き下げ可能なオブジェクトと、$6+2i$のように引き下げできないオブジェクトを区別する一般的な方法が必要だということです。）

Inadequacies of hierarchies
階層の不十分さ

If the data types in our system can be naturally arranged in a tower, this greatly simplifies the problems of dealing with generic operations on different types, as we have seen. Unfortunately, this is usually not the case. Figure 2.40 illustrates a more complex arrangement of mixed types, this one showing relations among different types of geometric figures. We see that, in general, a type may have more than one subtype. Triangles and quadrilaterals, for instance, are both subtypes of polygons. In addition, a type may have more than one supertype. For example, an isosceles right triangle may be regarded either as an isosceles triangle or as a right triangle. This multiple-supertypes issue is particularly thorny, since it means that there is no unique way to raise a type in the hierarchy. Finding the correct supertype in which to apply an operation to an object may involve considerable searching through the entire type network on the part of a function such as apply_generic. Since there generally are multiple subtypes for a type, there is a similar problem in coercing a value down the type hierarchy. Dealing with large numbers of interrelated types while still preserving modularity in the design of large systems is very difficult, and is an area of much current research.
これまで見てきたように、システムのデータ型がタワーとして自然に並べられる場合、異なる型に対するジェネリック演算の問題は大幅に簡略化されます。残念ながら、通常はそうではありません。図 2.40は、混合型のより複雑な配置を示しており、異なる種類の幾何学的図形間の関係を表しています。一般に、 1つの型が複数のサブタイプを持つことがあります。例えば、三角形と四辺形はどちらも多角形のサブタイプです。さらに、1つの型が複数のスーパータイプを持つこともあります。例えば、直角二等辺三角形は二等辺三角形とも直角三角形とも見なせます。この複数スーパータイプの問題は特に厄介です。階層内で型を引き上げる一意な方法がないことを意味するからです。オブジェクトに演算を適用するための正しいスーパータイプを見つけるには、 apply_generic のような 関数 が型ネットワーク全体をかなり探索する必要があるかもしれません。一般に1つの型には複数のサブタイプがあるため、型の階層を下方向に型変換する場合にも同様の問題があります。大規模システムの設計でモジュール性を保ちながら、多数の相互に関連する型を扱うのは非常に難しく、現在も盛んに研究されている分野です。

           ? undefined
           : can_coerce_to(type_tags, head(type_tags))

    return map(arg => type_tag(arg) === target_type
                      ? arg
                      : get_coercion(type_tag(arg), target_type)(arg),

    const fun = get(op, type_tags);

Developing a useful, general framework for expressing the relations among different types of entities (what philosophers call ontology) seems intractably difficult. The main difference between the confusion that existed in 1984 and the confusion that exists now is that now a variety of inadequate ontological theories have been embodied in a plethora of correspondingly inadequate programming languages. For example, much of the complexity of object-oriented programming languages—and the subtle and confusing differences among contemporary object-oriented languages—centers on the treatment of generic operations on interrelated types. Readers familiar with object-oriented programming will notice that we have much to say in chapter 3 about local state, but we do not even mention classes or inheritance.
