5.4.2  
Evaluating Function Applications
関数適用の評価

A function application is specified by a combination containing a function expression and argument expressions. The function expression is a subexpression whose value is a function, and the argument expressions are subexpressions whose values are the arguments to which the function should be applied. The metacircular evaluate handles applications by calling itself recursively to evaluate each element of the combination, and then passing the results to apply, which performs the actual function application. The explicit-control evaluator does the same thing; these recursive calls are implemented by go_to instructions, together with use of the stack to save registers that will be restored after the recursive call returns. Before each call we will be careful to identify which registers must be saved (because their values will be needed later).
関数適用は、関数式と引数式を含む組み合わせによって指定されます。関数式は値が関数であるような部分式であり、引数式は関数が適用されるべき引数の値を持つ部分式です。メタ循環評価器の evaluate は、組み合わせの各要素を評価するために自身を再帰的に呼び出し、その結果を実際の関数適用を行う apply に渡すことで適用を処理します。明示的制御評価器も同じことを行いますが、これらの再帰呼び出しは go_to 命令と、再帰呼び出しから戻った後に復元されるレジスタを保存するためのスタックの使用によって実装されます。各呼び出しの前に、 どのレジスタを保存する必要があるか（その値が後で必要になるため）を慎重に特定します。
[1]

As in the metacircular evaluator, operator combinations are transformed into applications of primitive functions corresponding to the operators. This takes place at ev_operator_combination, which performs this transformation in place in comp and falls through to ev_application.
メタ循環評価器と同様に、演算子の組み合わせは演算子に対応するプリミティブ関数の適用に変換されます。これは ev_operator_combination で行われ、comp 内でこの変換をその場で実行し、そのまま ev_application に流れ込みます。
[2]

We begin the evaluation of an application by evaluating the function expression to produce a function, which will later be applied to the evaluated argument expressions. To evaluate the function expression, we move it to the comp register and go to eval_dispatch. The environment in the env register is already the correct one in which to evaluate the function expression. However, we save env because we will need it later to evaluate the argument expressions. We also extract the argument expressions into unev and save this on the stack. We set up continue so that eval_dispatch will resume at ev_appl_did_function_expression after the function expression has been evaluated. First, however, we save the old value of continue, which tells the controller where to continue after the application.
適用の評価は、関数式を評価して関数を生成することから始まります。この関数は後で評価済みの引数式に適用されます。関数式を評価するために、それを comp レジスタに移動し、eval_dispatch に移行します。env レジスタ内の環境は、関数式を評価するための正しい環境です。しかし、後で引数式を評価するときに必要になるため、env を保存します。また、引数式を unev に取り出してスタックに保存します。関数式の評価後に eval_dispatch が ev_appl_did_function_expression で再開するように continue を設定します。ただしその前に、適用の後でどこに継続するかをコントローラに伝える continue の古い値を保存します。 
"ev_operator_combination",
  assign("comp", list(op("operator_combination_to_application"),
                      reg("comp"), reg("env"))),
"ev_application",
  save("continue"),
  save("env"),
  assign("unev", list(op("arg_expressions"), reg("comp"))),
  save("unev"),
  assign("comp", list(op("function_expression"), reg("comp"))),
  assign("continue", label("ev_appl_did_function_expression")),
  go_to(label("eval_dispatch")),

Upon returning from evaluating the function expression, we proceed to evaluate the argument expressions of the application and to accumulate the resulting arguments in a list, held in argl. (This is like the evaluation of a sequence of statements, except that we collect the values.) First we restore the unevaluated argument expressions and the environment. We initialize argl to an empty list. Then we assign to the fun register the function that was produced by evaluating the function expression. If there are no argument expressions, we go directly to apply_dispatch. Otherwise we save fun on the stack and start the argument-evaluation loop:
関数式の評価から戻ったら、適用の引数式を評価し、結果の引数を argl に保持されるリストに蓄積していきます。（これは文の列の評価に似ていますが、値を収集する点が異なります。）まず、未評価の引数式と環境を復元します。argl を空リストに初期化します。次に、関数式の評価によって生成された関数を fun レジスタに代入します。引数式がなければ、直接 apply_dispatch に移行します。そうでなければ、fun をスタックに保存し、引数評価ループを開始します。
[3] 
"ev_appl_did_function_expression",
  restore("unev"), // the argument expressions
  restore("env"),
  assign("argl", list(op("empty_arglist"))),
  assign("fun", reg("val")), // the function
  test(list(op("is_null"), reg("unev"))),
  branch(label("apply_dispatch")),
  save("fun"),

Each cycle of the argument-evaluation loop evaluates an argument expression from the list in unev and accumulates the result into argl. To evaluate an argument expression, we place it in the comp register and go to eval_dispatch, after setting continue so that execution will resume with the argument-accumulation phase. But first we save the arguments accumulated so far (held in argl), the environment (held in env), and the remaining argument expressions to be evaluated (held in unev). A special case is made for the evaluation of the last argument expression, which is handled at ev_appl_last_arg.
引数評価ループの各サイクルでは、unev 内のリストから引数式を1つ評価し、結果を argl に蓄積します。引数式を評価するために、それを comp レジスタに配置し、引数蓄積フェーズで実行が再開されるように continue を設定してから eval_dispatch に移行します。ただしその前に、これまでに蓄積された引数（argl に保持）、環境（env に保持）、評価すべき残りの引数式（unev に保持）を保存します。最後の引数式の評価は特別扱いされ、ev_appl_last_arg で処理されます。 
"ev_appl_argument_expression_loop",
  save("argl"),
  assign("comp", list(op("head"), reg("unev"))),
  test(list(op("is_last_argument_expression"), reg("unev"))),
  branch(label("ev_appl_last_arg")),
  save("env"),
  save("unev"),
  assign("continue", label("ev_appl_accumulate_arg")),
  go_to(label("eval_dispatch")),

When an argument expression has been evaluated, the value is accumulated into the list held in argl. The argument expression is then removed from the list of unevaluated argument expressions in unev, and the argument-evaluation loop continues.
引数式が評価されると、その値は argl に保持されるリストに蓄積されます。その引数式は unev 内の未評価の引数式のリストから取り除かれ、引数評価ループが続行されます。 
"ev_appl_accumulate_arg",
  restore("unev"),
  restore("env"),
  restore("argl"),
  assign("argl", list(op("adjoin_arg"), reg("val"), reg("argl"))),
  assign("unev", list(op("tail"), reg("unev"))),
  go_to(label("ev_appl_argument_expression_loop")),

Evaluation of the last argument expression is handled differently, as is the last statement in a sequence. There is no need to save the environment or the list of unevaluated argument expressions before going to eval_dispatch, since they will not be required after the last argument expression is evaluated. Thus, we return from the evaluation to a special entry point ev_appl_accum_last_arg, which restores the argument list, accumulates the new argument, restores the saved function, and goes off to perform the application.
最後の引数式の評価は、列の最後の文と同様に、異なる方法で処理されます。最後の引数式が評価された後は環境や未評価の引数式のリストは不要なので、eval_dispatch に移行する前にそれらを保存する必要はありません。したがって、評価からは特別なエントリポイント ev_appl_accum_last_arg に戻ります。このエントリポイントは引数リストを復元し、新しい引数を蓄積し、保存された関数を復元して、適用の実行に移ります。
[4] 
"ev_appl_last_arg",
  assign("continue", label("ev_appl_accum_last_arg")),
  go_to(label("eval_dispatch")),
"ev_appl_accum_last_arg",
  restore("argl"),
  assign("argl", list(op("adjoin_arg"), reg("val"), reg("argl"))),
  restore("fun"),
  go_to(label("apply_dispatch")),

The details of the argument-evaluation loop determine the order in which the interpreter evaluates the argument expressions of a combination (e.g., left to right or right to left—see exercise ). This order is not determined by the metacircular evaluator, which inherits its control structure from the underlying JavaScript in which it is implemented.
引数評価ループの詳細が、 インタプリタが組み合わせの引数式をどの順序で評価するか（例えば、左から右か右から左か—練習問題 を参照）を決定します。この順序は、基盤の JavaScript から制御構造を受け継ぐメタ循環評価器では決定されませんでした。
[5]
Because we use head in ev_appl_argument_expression_loop to extract successive argument expressions from unev and tail at ev_appl_accumulate_arg to extract the rest of the argument expressions, the explicit-control evaluator will evaluate the argument expressions of a combination in left-to-right order, as required by the ECMAScript specification.
ev_appl_argument_expression_loop で head を使って unev から引数式を順次取り出し、ev_appl_accumulate_arg で tail を使って残りの引数式を取り出すため、明示的制御評価器はECMAScript仕様で要求されるとおり、組み合わせの引数式を左から右の順序で評価します。

Function Application
関数適用

The entry point apply_dispatch corresponds to the apply function of the metacircular evaluator. By the time we get to apply_dispatch, the fun register contains the function to apply and argl contains the list of evaluated arguments to which it must be applied. The saved value of continue (originally passed to eval_dispatch and saved at ev_application), which tells where to return with the result of the function application, is on the stack. When the application is complete, the controller transfers to the entry point specified by the saved continue, with the result of the application in val. As with the metacircular apply, there are two cases to consider. Either the function to be applied is a primitive or it is a compound function.
エントリポイント apply_dispatch は、メタ循環評価器の apply 関数に対応します。apply_dispatch に到達する時点で、fun レジスタには適用する関数が、argl には適用先の評価済み引数のリストが格納されています。関数適用の結果をどこに返すかを示す continue の保存された値（もともと eval_dispatch に渡され、ev_application で保存されたもの）はスタック上にあります。適用が完了すると、コントローラは適用の結果を val に入れて、保存された continue で指定されるエントリポイントに転送します。メタ循環評価器の apply と同様に、考慮すべき場合が2つあります。適用する関数がプリミティブ関数であるか、複合関数であるかです。 
"apply_dispatch",
  test(list(op("is_primitive_function"), reg("fun"))),
  branch(label("primitive_apply")),
  test(list(op("is_compound_function"), reg("fun"))),
  branch(label("compound_apply")),
  go_to(label("unknown_function_type")),

We assume that each primitive is implemented so as to obtain its arguments from argl and place its result in val. To specify how the machine handles primitives, we would have to provide a sequence of controller instructions to implement each primitive and arrange for primitive_apply to dispatch to the instructions for the primitive identified by the contents of fun. Since we are interested in the structure of the evaluation process rather than the details of the primitives, we will instead just use an apply_primitive_function operation that applies the function in fun to the arguments in argl. For the purpose of simulating the evaluator with the simulator of section 5.2 we use the function apply_primitive_function, which calls on the underlying JavaScript system to perform the application, just as we did for the metacircular evaluator in section 4.1.1. After computing the value of the primitive application, we restore continue and go to the designated entry point.
各 プリミティブ関数は、argl から引数を取得し、結果を val に格納するように実装されていると仮定します。マシンがプリミティブ関数をどのように処理するかを指定するには、各プリミティブ関数を実装するコントローラ命令の列を提供し、fun の内容で識別されるプリミティブ関数の命令に primitive_apply がディスパッチするようにする必要があります。プリミティブ関数の詳細よりも評価プロセスの構造に関心があるので、代わりに、fun 内の関数を argl 内の引数に適用する apply_primitive_function 操作を使用します。5.2節のシミュレータで評価器をシミュレートする目的で、4.1.1節のメタ循環評価器で行ったのと同様に、基盤のJavaScriptシステムを呼び出して適用を実行する関数 apply_primitive_function を使用します。プリミティブ関数の適用の値を計算した後、continue を復元し、指定されたエントリポイントに移行します。 
"primitive_apply",
  assign("val", list(op("apply_primitive_function"),
                     reg("fun"), reg("argl"))),
  restore("continue"),
  go_to(reg("continue")),

The sequence of instructions labeled compound_apply specifies the application of compound functions. To apply a compound function, we proceed in a way similar to what we did in the metacircular evaluator. We construct a frame that binds the function's parameters to the arguments, use this frame to extend the environment carried by the function, and evaluate in this extended environment the body of the function.
compound_apply というラベルの付いた命令列は、 複合関数の適用を指定します。複合関数を適用するには、メタ循環評価器で行ったのと同様の方法で進めます。関数のパラメータを引数に束縛するフレームを構築し、このフレームを使って関数が持つ環境を拡張し、この拡張された環境で関数の本体を評価します。

At this point the compound function is in register fun and its arguments are in argl. We extract the function's parameters into unev and its environment into env. We then replace the environment in env with the environment constructed by extending it with bindings of the parameters to the given arguments. We then extract the body of the function into comp. The natural next step would be to restore the saved continue and proceed to eval_dispatch to evaluate the body and go to the restored continuation with the result in val, as is done for the last statement of a sequence. But there is a complication!
この時点で、複合関数はレジスタ fun に、その引数は argl にあります。関数のパラメータを unev に、その環境を env に取り出します。次に、env 内の環境を、パラメータと与えられた引数の束縛で拡張して構築された環境に置き換えます。その後、関数の本体を comp に取り出します。自然な次のステップは、保存された continue を復元し、列の最後の文の場合と同様に、本体を評価するために eval_dispatch に進み、結果を val に入れて復元された継続に移行することでしょう。しかし、複雑な問題があります！

The complication has two aspects. One is that at any point in the evaluation of the body, a return statement may require the function to return the value of the return expression as the value of the body. But a return statement may be nested arbitrarily deeply in the body; so the stack at the moment the return statement is encountered is not necessarily the stack that is needed for a return from the function. One way to make it possible to adjust the stack for the return is to put a \emph{marker} on the stack that can be found by the return code. This is implemented by the push_marker_to_stack instruction. The return code can then use the revert_stack_to_marker instruction to restore the stack to the place indicated by the marker before evaluating the return expression.
この複雑さには2つの側面があります。1つは、本体の評価中のどの時点でも、 return 文が、return 式の値を本体の値として関数に返すよう要求する可能性があることです。しかし return 文は本体内に任意の深さで入れ子になり得るため、return 文に遭遇した時点のスタックは、関数からの復帰に必要なスタックとは限りません。復帰のためにスタックを調整可能にする1つの方法は、リターンコードが見つけられるマーカーをスタックに置くことです。これは push_marker_to_stack 命令で実装されます。リターンコードは revert_stack_to_marker 命令を使って、return 式を評価する前にスタックをマーカーが示す場所に復元できます。
[6]

The other aspect of the complication is that if the evaluation of the body terminates without executing a return statement, the value of the body must be undefined. To handle this, we set up the continue register to point to the entry point return_undefined before going off to eval_dispatch to evaluate the body. If a return statement is not encountered during evaluation of the body, evaluation of the body will continue at return_undefined.
複雑さのもう1つの側面は、本体の評価が return 文を実行せずに終了した場合、本体の値は undefined でなければならないということです。これに対処するため、本体を評価するために eval_dispatch に移行する前に、continue レジスタがエントリポイント return_undefined を指すように設定します。本体の評価中に return 文に遭遇しなければ、本体の評価は return_undefined で継続されます。 
"compound_apply",
  assign("unev", list(op("function_parameters"), reg("fun"))),
  assign("env", list(op("function_environment"), reg("fun"))),
  assign("env", list(op("extend_environment"), 
                     reg("unev"), reg("argl"), reg("env"))),
  assign("comp", list(op("function_body"), reg("fun"))),
  push_marker_to_stack(),
  assign("continue", label("return_undefined")),
  go_to(label("eval_dispatch")),

The only places in the interpreter where the env register is assigned a new value are compound_apply and ev_block (section 5.4.3). Just as in the metacircular evaluator, the new environment for evaluation of a function body is constructed from the environment carried by the function, together with the argument list and the corresponding list of names to be bound.
インタプリタ内で env レジスタに新しい値が代入される場所は、compound_apply と ev_block（5.4.3節）だけです。メタ循環評価器と同様に、関数本体の評価のための新しい環境は、関数が持つ環境と、引数リストおよび束縛される名前の対応リストから構築されます。

When a return statement is evaluated at ev_return, we use the revert_stack_to_marker instruction to restore the stack to its state at the beginning of the function call by removing all values from the stack down to and including the marker. As a consequence, restore("continue") will restore the continuation of the function call, which was saved at ev_application. We then proceed to evaluate the return expression, whose result will be placed in val and thus be the value returned from the function when we continue after the evaluation of the return expression.
ev_return で return 文が評価されるとき、revert_stack_to_marker 命令を使って、マーカーを含むそれ以降のすべての値をスタックから取り除くことで、スタックを関数呼び出しの開始時の状態に復元します。その結果、restore("continue") は ev_application で保存された関数呼び出しの継続を復元します。次に return 式の評価に進みます。その結果は val に格納され、return 式の評価後に継続するときに関数から返される値となります。 
"ev_return",
  revert_stack_to_marker(),
  restore("continue"),
  assign("comp", list(op("return_expression"), reg("comp"))),
  go_to(label("eval_dispatch")),

If no return statement is encountered during evaluation of the function body, evaluation continues at return_undefined, the continuation that was set up at compound_apply. To return undefined from the function, we put undefined into val and go to the entry point that was put onto the stack at ev_application. Before we can restore that continuation from the stack, however, we must remove the marker that was saved at compound_apply.
関数本体の評価中に return 文に遭遇しなかった場合、 compound_apply で設定された継続である return_undefined で評価が続行されます。関数から undefined を返すために、val に undefined を入れ、ev_application でスタックに積まれたエントリポイントに移行します。ただし、スタックからその継続を復元する前に、compound_apply で保存されたマーカーを取り除く必要があります。 
"return_undefined",
  revert_stack_to_marker(),
  restore("continue"),
  assign("val", constant(undefined)),
  go_to(reg("continue")),

return 文と
Tail Recursion
末尾再帰

In chapter 1 we said that the process described by a function such as
第 1章で、次のような 関数 が記述するプロセスは 
function sqrt_iter(guess, x) {
    return is_good_enough(guess, x)
           ? guess
           : sqrt_iter(improve(guess, x), x);
}
is an iterative process. Even though the function is syntactically recursive (defined in terms of itself), it is not logically necessary for an evaluator to save information in passing from one call to sqrt_iter to the next.
反復的プロセスであると述べました。この 関数 は構文的には再帰的（自分自身を使って定義されている）ですが、 sqrt_iter の1回の呼び出しから次の呼び出しに移る際に、評価器が情報を保存する必要は論理的にはありません。
[7]
An evaluator that can execute a function such as sqrt_iter without requiring increasing storage as the function continues to call itself is called a tail-recursive evaluator.
sqrt_iter のような 関数 を、その 関数 が自身を呼び出し続けても記憶領域の増加を必要とせずに実行できる評価器を、 末尾再帰的評価器と呼びます。

The metacircular implementation of the evaluator in chapter 4 isn't tail-recursive. It implements a return statement as a constructor of a return value object containing the value to be returned and inspects the result of a function call to see whether it is such an object. If the evaluation of a function body produces a return value object, the return value of the function is the contents of that object; otherwise, the return value is undefined. Both the construction of the return value object and the eventual inspection of the result of the function call are deferred operations, which lead to an accumulation of information on the stack.
第 4章の評価器のメタ循環実装は末尾再帰的ではありません。return 文を、返されるべき値を含む戻り値オブジェクトのコンストラクタとして実装し、関数呼び出しの結果がそのようなオブジェクトかどうかを検査します。関数本体の評価が戻り値オブジェクトを生成した場合、関数の戻り値はそのオブジェクトの内容であり、そうでなければ戻り値は undefined です。戻り値オブジェクトの構築と、関数呼び出しの結果の最終的な検査の両方が遅延された演算であり、スタック上の情報の蓄積につながります。

Our explicit-control evaluator is tail-recursive, because it does not need to wrap up return values for inspection and thus avoids the buildup of stack from deferred operations. At ev_return, in order to evaluate the expression that computes the return value of a function, we transfer directly to eval_dispatch with nothing more on the stack than right before the function call. We accomplish this by undoing any saves to the stack by the function (which are useless because we are returning) using revert_stack_to_marker. Then, rather than arranging for eval_dispatch to come back here and then restoring continue from the stack and continuing at that entry point, we restore continue from the stack before going to eval_dispatch so that eval_dispatch will continue at that entry point after evaluating the expression. Finally, we transfer to eval_dispatch without saving any information on the stack. Thus, when we proceed to evaluate a return expression, the stack is the same as just before the call to the function whose return value we are about to compute. Hence, evaluating a return expression—even if it is a function call (as in sqrt_iter, where the conditional expression reduces to a call to sqrt_iter)—will not cause any information to accumulate on the stack.
私たちの明示的制御評価器は末尾再帰的です。検査のために戻り値をラップする必要がなく、そのため遅延された演算によるスタックの蓄積を回避します。ev_return では、関数の戻り値を計算する式を評価するために、関数呼び出しの直前と同じ状態のスタックで eval_dispatch に直接転送します。これは、関数によるスタックへの保存（返ろうとしているので不要）を revert_stack_to_marker を使って取り消すことで実現します。そして、eval_dispatch がここに戻って来てから continue をスタックから復元してそのエントリポイントで継続するのではなく、eval_dispatch に移行する前に continue をスタックから復元し、eval_dispatch が式を評価した後にそのエントリポイントで継続するようにします。最後に、スタックに何も情報を保存せずに eval_dispatch に転送します。したがって、return 式の評価に進むとき、スタックは戻り値を計算しようとしている関数の呼び出しの直前と同じです。よって、return 式の評価は—たとえそれが関数呼び出しであっても（sqrt_iter のように、条件式が sqrt_iter の呼び出しに帰着する場合）—スタック上に情報が蓄積されることはありません。
[8]

If we did not think to take advantage of the fact that it is unnecessary to hold on to the useless information on the stack while evaluating a return expression, we might have taken the straightforward approach of evaluating the return expression, coming back to restore the stack, and finally continuing at the entry point that is waiting for the result of the function call:
return 式の評価中にスタック上の不要な情報を保持し続ける必要がないという事実を活用することを思いつかなければ、return 式を評価し、戻って来てスタックを復元し、最後に関数呼び出しの結果を待っているエントリポイントで継続するという素直なアプローチを取っていたかもしれません。
"ev_return", // alternative implementation: not tail-recursive assign("comp", list(op("return_expression"), reg("comp"))), assign("continue", label("ev_restore_stack")), go_to(label("eval_dispatch")), "ev_restore_stack", revert_stack_to_marker(), // undo saves in current function restore("continue"), // undo save at $\texttt{ev\char`_application}$ go_to(reg("continue")),

This may seem like a minor change to our previous code for evaluation of return statements: The only difference is that we delay undoing any register saves to the stack until after the evaluation of the return expression. The interpreter will still give the same value for any expression. But this change is fatal to the tail-recursive implementation, because we must now come back after evaluating the return expression in order to undo the (useless) register saves. These extra saves will accumulate during a nest of function calls. Consequently, processes such as sqrt_iter will require space proportional to the number of iterations rather than requiring constant space. This difference can be significant. For example, with tail recursion, an infinite loop can be expressed using only the function-call and return mechanisms:
これは、return 文の評価に関する以前のコードからのわずかな変更に見えるかもしれません。 唯一の違いは、return 式の評価の後までスタックへのレジスタ保存の取り消しを遅らせることです。 インタプリタはどの式に対しても同じ値を返します。しかしこの変更は末尾再帰的な実装にとって致命的です。なぜなら、return 式を評価した後に（不要な）レジスタの保存を取り消すために戻って来なければならないからです。 これらの余分な保存は、 関数呼び出しのネストの間に蓄積されます。 したがって、 sqrt_iter のようなプロセスは、一定の空間で済む代わりに、反復回数に比例する空間を必要とするようになります。 この違いは重大になり得ます。例えば、 末尾再帰があれば、無限ループは 関数呼び出しと return の機構 だけで表現できます。 
function count(n) {
    display(n);
    return count(n + 1);
}
Without tail recursion, such a function would eventually run out of stack space, and expressing a true iteration would require some control mechanism other than function call.
末尾再帰がなければ、このような 関数 は最終的にスタック空間を使い果たし、真の反復を表現するには 関数 呼び出し以外の何らかの制御機構が必要になるでしょう。

Note that our JavaScript implementation requires the use of return in order to be tail-recursive. Because the undoing of the register saves takes place at ev_return, removing return from the count function above will cause it to eventually run out of stack space. This explains the use of return in the infinite driver loops in chapter 4.
私たちのJavaScript実装では、末尾再帰的であるために return の使用が必要であることに注意してください。レジスタ保存の取り消しは ev_return で行われるため、上の count 関数から return を除去すると、最終的にスタック空間を使い果たします。これが、第 4章の無限ドライバループで return を使用している理由です。
